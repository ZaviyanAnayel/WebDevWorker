1. Why the Composition API Exists

In Vue 2 and the Vue 3 Options API, component logic is organized by option type: data, methods, computed, and watchers. For small components this works beautifully, but as a component grows, a single feature's logic gets scattered across all four sections. A search filter, for example, might have its query string in data, its filtering logic in computed, and its debounced fetch in watch — three places to read to understand one feature.

The Composition API solves this by organizing code by logical concern instead of by option type. Everything related to the search filter — state, derived values, and side effects — lives together inside setup() or a <script setup> block. It also fixes the two biggest pain points of mixins: naming collisions and invisible dependencies. With composables, every piece of reused logic is an explicit function call whose inputs and outputs you can see.

It is also a far better story for TypeScript. The Options API relies on this magic that type inference struggles with; the Composition API is plain functions and variables, so types flow naturally. Since Vue 3.2, <script setup> is the recommended authoring style, and this guide assumes it throughout.

<script setup>
import { ref, computed } from 'vue'

// All state for ONE feature, declared together
const query = ref('')
const items = ref(['Vue', 'React', 'Svelte', 'Solid'])

const filtered = computed(() =>
  items.value.filter(i => i.toLowerCase().includes(query.value.toLowerCase()))
)
</script>

<template>
  <input v-model="query" placeholder="Filter frameworks..." />
  <ul>
    <li v-for="item in filtered" :key="item">{{ item }}</li>
  </ul>
</template>

The snippet above is the entire feature: two pieces of state and one derived value, declared in four lines. In the Options API the same logic would span data and computed with this wiring between them. That density is the whole point — related logic stays related.

2. ref() vs reactive(): Managing State

ref() wraps any value — primitive or object — in a reactive container with a .value property. reactive() turns a plain object (or array) into a deeply reactive proxy you access directly, with no .value. The rule of thumb: use ref for primitives and for anything you will reassign wholesale; use reactive for grouped object state like a form.

The .value requirement trips up every beginner, but there is a reason for it: JavaScript cannot make a reassigned variable reactive, so ref stores the value on an object whose property access can be tracked. In templates, Vue unwraps refs automatically, so {{ count }} works without .value — one of the small kindnesses of <script setup>.

Destructuring a reactive object breaks reactivity because you pull plain values out of the proxy. If you need individual properties, use toRefs() to convert each property into a ref. For large or performance-sensitive data that should not be deeply observed, reach for shallowRef() or shallowReactive().

<script setup>
import { ref, reactive, toRefs } from 'vue'

// Primitive: ref is the only option
const count = ref(0)
const increment = () => count.value++

// Grouped state: reactive reads naturally
const form = reactive({ email: '', password: '', remember: false })
const resetForm = () => {
  form.email = ''
  form.password = ''
  form.remember = false
}

// Safe destructuring with toRefs
const { email, password } = toRefs(form)
</script>

3. computed() and watch(): Derived State and Side Effects

computed() creates a value derived from reactive state, cached until its dependencies change. It is the right tool whenever a template expression gets complex or a value is consumed in multiple places. Computed properties are lazy — they only recalculate when something actually reads them after a dependency changed — which makes them cheap even in hot render paths.

watch() is for side effects: fetching data when an ID changes, persisting to localStorage, or syncing with a third-party library. It takes an explicit source (a ref, a getter function, or an array of sources) and a callback receiving (newValue, oldValue). Use the { deep: true } option to observe nested mutations and { immediate: true } to run the callback on setup.

watchEffect() is the automatic alternative: it runs immediately and re-runs whenever any reactive value read inside it changes. It is perfect for one-off synchronization logic, but for most data-fetching you want watch — explicit sources make behavior predictable and give you old values for comparison. Inside either watcher, onInvalidate() registers cleanup, typically to cancel a stale request when the source changes again.

<script setup>
import { ref, computed, watch, onInvalidate } from 'vue'

const price = ref(100)
const quantity = ref(2)

// Derived state: cached, only recalculates when price/quantity change
const total = computed(() => price.value * quantity.value)
const summary = computed(() => `${quantity.value} items at $${price.value} = $${total.value}`)

// Side effect: react to a specific change, with cleanup
const productId = ref(1)
const product = ref(null)

watch(productId, async (id, _oldId, onCleanup) => {
  let cancelled = false
  onCleanup(() => { cancelled = true }) // cancel stale request
  const res = await fetch(`/api/products/${id}`)
  if (!cancelled) product.value = await res.json()
}, { immediate: true })
</script>

4. Lifecycle Hooks and Component Communication

Lifecycle hooks in the Composition API are imported functions called inside setup(): onMounted, onUpdated, and onUnmounted cover the vast majority of needs, with onBeforeMount and onErrorCaptured for special cases. There is no onCreated — code at the top of <script setup> already runs during creation. Unlike the Options API, you can register the same hook multiple times, which keeps feature-related setup code together.

Component communication uses compiler macros in <script setup>. defineProps() declares incoming props (with full TypeScript support via a type argument), defineEmits() declares events, and defineExpose() controls what a parent can reach through a template ref. For deeply nested data like themes or locale, provide() and inject() pass values down the tree without prop drilling.

One rule that bites newcomers: hooks and provide must be called synchronously during setup. You cannot call onMounted inside a setTimeout or after an await at the top level and expect it to register — by then the component instance context is gone.

<script setup>
import { ref, onMounted, onUnmounted, provide, defineProps, defineEmits } from 'vue'

const props = defineProps({ userId: { type: Number, required: true } })
const emit = defineEmits(['loaded'])

// provide() for descendants — no prop drilling
provide('theme', 'dark')

const user = ref(null)
let timer = null

onMounted(async () => {
  const res = await fetch(`/api/users/${props.userId}`)
  user.value = await res.json()
  emit('loaded', user.value)
  timer = setInterval(() => console.log('tick'), 5000)
})

onUnmounted(() => clearInterval(timer))
</script>

5. Composables: Reusable Logic

A composable is a plain function that uses Composition API primitives and returns reactive state and methods — the Composition API's answer to mixins, without their drawbacks. Because a composable is just a function call, its inputs are explicit arguments and its outputs are explicitly returned; there are no magic merged properties and no naming collisions. The convention is a use prefix: useCounter, useFetch, useLocalStorage.

The canonical example is data fetching. A useFetch(url) composable encapsulates the loading/error/data trio plus the watcher that refetches when the URL changes — logic you would otherwise copy into every list component. Each call creates independent state, so two components using useFetch never share data unless you deliberately hoist the state to module scope, which is also how tiny global stores are born.

VueUse, the community composable collection, is worth knowing: it ships battle-tested composables for local storage, event listeners, async state, and hundreds more. Before writing your own, check whether VueUse already covers it — but write your own for domain logic, where the reuse is inside your app.

// composables/useFetch.js
import { ref, watch } from 'vue'

export function useFetch(url) {
  const data = ref(null)
  const error = ref(null)
  const loading = ref(true)

  const load = async (target) => {
    loading.value = true
    error.value = null
    try {
      const res = await fetch(target)
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      data.value = await res.json()
    } catch (e) {
      error.value = e
    } finally {
      loading.value = false
    }
  }

  // Accepts a ref so callers can change the URL reactively
  const source = typeof url === 'function' ? url : () => url
  watch(source, load, { immediate: true })

  return { data, error, loading, reload: () => load(source()) }
}

// const { data: users, loading, error } = useFetch(() => `/api/users?page=${page.value}`)

6. Frequently Asked Questions (FAQs)

Should I use ref or reactive for form state?

Use reactive for grouped form state — form.email reads more naturally than form.value.email, and you typically mutate fields rather than replace the whole object. Use ref for primitives like strings and numbers, and for any value you plan to reassign wholesale. Many teams standardize on ref everywhere for consistency; either convention works if applied consistently.

Is the Options API deprecated in Vue 3?

No. The Options API is fully supported and will remain so — it is still a fine choice for simple components and for developers coming from Vue 2. The Composition API is recommended for complex components, shared logic, and TypeScript-heavy codebases because it colocates related logic and types cleanly.
