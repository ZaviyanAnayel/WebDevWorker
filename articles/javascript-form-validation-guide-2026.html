1. Why Client-Side Validation Still Matters

Client-side validation is about user experience, not security. It catches typos, empty fields, and malformed emails in milliseconds instead of a server round-trip, turning a frustrating submit-and-wait cycle into instant, inline guidance. Every form that skips it ships a worse product — but every form that relies on it alone ships a vulnerable one.

The non-negotiable rule: always validate on the server too. Client-side checks are trivially bypassed — disable JavaScript, edit the DOM, or send a raw HTTP request. Treat browser validation as a courtesy layer that improves UX; treat server validation as the security boundary that protects your data. Both layers should enforce the same rules.

Modern browsers give you a surprising amount for free: typed inputs, declarative constraints, and a full JavaScript API for custom logic. The professional approach is layered — start with semantic HTML attributes (zero JS), enhance with the Constraint Validation API for custom rules, and only reach for a framework when forms get genuinely complex. Most forms never need more than the platform.

2. Built-in HTML Validation: Free Power

Before writing a line of JavaScript, HTML alone can enforce required fields, lengths, patterns, ranges, and types — with localized error bubbles rendered by the browser. Semantic input types (email, url, tel, number, date) also trigger the right mobile keyboards, which is a UX win no script can replicate:

<form id="signup" novalidate> <!-- we drive validation via JS below -->
  <label>Email
    <input type="email" name="email" required autocomplete="email">
  </label>
  <label>Username (3-16 chars, letters/numbers/_)
    <input type="text" name="username" required minlength="3" maxlength="16"
           pattern="[A-Za-z0-9_]+" title="Letters, numbers, and underscores only">
  </label>
  <label>Age
    <input type="number" name="age" min="13" max="120" required>
  </label>
  <label>Password
    <input type="password" name="password" required minlength="12"
           autocomplete="new-password">
  </label>
  <button type="submit">Create account</button>
</form>

The pattern attribute takes a regular expression (anchored automatically — no ^$ needed), and title supplies the hint shown when it fails. Remove novalidate and the browser blocks invalid submits with its own UI; keep it when you want full control over messaging while still using the underlying validity state.

One gotcha: type="number" is poor for things like phone numbers or ZIP codes — spinners, locale decimal quirks, and lost leading zeros. Use type="text" with inputmode="numeric" and a pattern for digit strings that aren't quantities. And always pair every input with a real <label>: placeholders are not labels, and screen readers need the association.

3. The Constraint Validation API in JavaScript

Every form control exposes the Constraint Validation API: checkValidity(), reportValidity(), setCustomValidity(message), and the validity state object. This is the bridge between declarative HTML constraints and your custom logic — and the key method is setCustomValidity:

const form = document.getElementById('signup');
const email = form.elements.email;
const password = form.elements.password;

// Custom rule layered on top of built-in constraints
email.addEventListener('input', () => {
  const disposable = /@(tempmail|mailinator|guerrillamail)\./i;
  email.setCustomValidity(
    disposable.test(email.value)
      ? 'Please use a permanent email address.'
      : '' // empty string = valid; anything else = invalid
  );
});

form.addEventListener('submit', (e) => {
  // reportValidity() shows native bubbles and returns false if invalid
  if (!form.reportValidity()) {
    e.preventDefault();
    return;
  }
  // Optional: inspect exactly WHY a field failed
  for (const field of form.elements) {
    if (field.validity && !field.validity.valid) {
      console.log(field.name, { ...field.validity });
    }
  }
});

The critical detail: a non-empty string passed to setCustomValidity marks the field invalid, and it stays invalid until you clear it with an empty string. That's why custom checks belong on the input event — re-evaluate on every keystroke, or a corrected field stays stuck in the invalid state.

Use these flags to write precise messages instead of generic ones: "Enter a valid email address" beats "Invalid input" every time. The flags also let you style states with CSS — input:invalid, input:user-invalid (only after interaction), and input:valid give you visual feedback with zero JavaScript.

4. Custom Rules That Feel Native

Real forms need rules HTML can't express: passwords that match, dates in the future, "at least one checkbox," or async checks like username availability. The pattern is always the same — compute validity in JS, then funnel it through setCustomValidity so the native submit-blocking and :invalid styling keep working:

const pw = form.elements.password;
const confirm = form.elements.confirmPassword;

function checkPasswordsMatch() {
  confirm.setCustomValidity(
    confirm.value && confirm.value !== pw.value
      ? 'Passwords do not match.'
      : ''
  );
}
pw.addEventListener('input', checkPasswordsMatch);
confirm.addEventListener('input', checkPasswordsMatch);

// Async rule: username availability (debounced)
let checkToken = 0;
username.addEventListener('input', () => {
  const token = ++checkToken;
  clearTimeout(username._t);
  username._t = setTimeout(async () => {
    if (token !== checkToken) return; // stale response guard
    const taken = await isUsernameTaken(username.value);
    if (token !== checkToken) return;
    username.setCustomValidity(taken ? 'That username is taken.' : '');
    if (taken) username.reportValidity();
  }, 400);
});

For cross-field and group rules, validate the group and attach the message to the most relevant control — or to a hidden field if the rule spans several inputs. Keep validators as pure functions (value => errorMessage | null) so they're unit-testable without a DOM, then wire each to its field with a three-line adapter.

Structure scales matters: collect your rules in one place, run them all on submit, and show a summary linking to each invalid field for long forms. A validation module with named, tested rules beats fifty anonymous inline handlers scattered through event listeners.

5. Validation UX: Timing, Messages, and Accessibility

Timing is the difference between helpful and hostile. Validating on every keystroke punishes users mid-thought — flagging an email as invalid while they're still typing it. The proven rhythm: validate on blur (when they leave the field) and on submit, then switch that field to live input validation once it's been marked invalid, so users see the error clear the moment they fix it.

Messages must say how to fix, not just what's wrong. "Invalid input" helps nobody; "Password needs at least 12 characters, including a number" does. Put constraints where users can see them before they fail — hint text under the field beats an error after it. And never clear a user's input as punishment for a validation failure; preserve everything they typed.

Accessibility is non-negotiable. Associate errors with fields via aria-describedby, set aria-invalid="true" on invalid controls, and announce dynamic errors in an aria-live="polite" region so screen reader users hear them. Move focus to the first invalid field on submit. Color alone must never be the only error signal — pair red borders with icons and text, for color-blind users and for everyone scanning quickly.

6. Frequently Asked Questions (FAQs)

Is client-side validation enough to secure my form?

No. Client-side validation improves user experience but is trivially bypassed by disabling JavaScript or sending raw HTTP requests. Always re-validate every rule on the server, which is the real security boundary. The browser layer is a courtesy; the server layer is the lock.

How do I show a custom error message for a field?

Call field.setCustomValidity('Your message') — any non-empty string marks the field invalid and the message appears in the native bubble. Clear it with setCustomValidity('') when the value becomes valid, typically re-checking on every input event.

Should I validate on every keystroke or on submit?

Validate on blur and on submit by default, then switch a field to live input validation after it has been marked invalid once. Validating pristine fields on every keystroke flags half-typed values and feels hostile; validating only on submit delays feedback.

What does the novalidate attribute do?

It disables the browser's automatic submit-blocking and native error bubbles, while leaving the Constraint Validation API fully available. Use it when you want complete control over error UI but still want checkValidity(), validity flags, and setCustomValidity().

How do I style invalid fields with CSS?

Use the :invalid and :valid pseudo-classes, or :user-invalid which only applies after the user has interacted with the field — avoiding red borders on pristine forms. Combine with aria-invalid for assistive technology and never rely on color alone.
