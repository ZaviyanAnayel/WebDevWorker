1. The First Rule of ARIA (and When to Break It)

The first rule of ARIA is simple and oft-quoted: don't use ARIA if a native HTML element does the job. A real <button> gives you the button role, keyboard handling, focusability, and correct announcements in every screen reader for free. Rebuilding it from a <div> with role="button" means reimplementing all of that by hand — and almost everyone gets part of it wrong.

So when is ARIA justified? Three situations. First, custom widgets with no native equivalent: tabs, tree views, sliders, and toggle switches built from generic elements need roles and states to be understandable. Second, repairing semantics you cannot change: a third-party component or CMS output that renders divs where landmarks belong. Third, dynamic content announcements: live regions telling screen reader users that a cart updated or a form saved.

The corollary rule: ARIA never adds behavior. role="button" does not make a div clickable or keyboard-focusable — you must add tabindex="0" and key handlers yourself. If that sounds like work, it is: which is exactly why native elements win whenever they exist.

2. Landmark Roles: Giving Pages Structure

Landmark roles give assistive technology users a map of the page. Screen readers offer landmark navigation — jump to the navigation, the main content, the search — but only if landmarks exist and are correctly labeled. Native HTML5 elements (<header>, <nav>, <main>, <footer>) expose these roles automatically, which is another reason to prefer them over divs.

Use each landmark once per page where it makes sense: one main, one top-level navigation for primary nav. When multiples are unavoidable — two navs, several asides — distinguish them with aria-label ("Primary", "Footer") so users hear "navigation landmark, Primary" instead of three identical "navigation" entries. The banner and contentinfo roles belong to the site header and footer, not to every article header.

The search role deserves special mention: wrapping your site search in role="search" (or a form with that role) gives screen reader users a direct jump to the one control many of them use first.

<!-- Landmarks: native elements preferred, labels where duplicated -->
<header>
  <nav aria-label="Primary">
    <a href="/">Home</a> <a href="/articles/">Guides</a>
  </nav>
  <form role="search" aria-label="Site search">
    <input type="search" name="q" aria-label="Search guides" />
    <button type="submit">Search</button>
  </form>
</header>

<main id="main-content">
  <article>...</article>
  <aside aria-label="Related guides">...</aside>
</main>

<footer>
  <nav aria-label="Footer">...</nav>
</footer>

3. Labels: aria-label vs aria-labelledby vs aria-describedby

Three attributes name things, and mixing them up is the most common ARIA error. aria-label sets the accessible name directly as a string — perfect for icon-only buttons where no visible text exists. aria-labelledby references the IDs of other elements, combining their text into the name — ideal when visible text already labels the control, because the accessible name then always matches what sighted users see. aria-describedby adds supplementary description announced after the name — hints, format requirements, error details.

The priority rule: prefer visible text via aria-labelledby over invisible aria-label whenever visible text exists. Speech-input users say what they see — if the button shows "Search" but its aria-label says "Find content", voice commands fail. Matching names prevent that entire class of bug.

Watch the gotchas: aria-label on a div or span does nothing (they are not nameable elements), and an empty aria-label="" can actively hide content. Name interactive elements; describe with aria-describedby; leave static text alone.

<!-- Icon-only button: aria-label is the only option -->
<button aria-label="Close dialog">
  <svg aria-hidden="true"><!-- X icon --></svg>
</button>

<!-- Visible text exists: reference it, don't duplicate it -->
<h2 id="billing-heading">Billing address</h2>
<div role="group" aria-labelledby="billing-heading">
  <label>Street <input name="street" /></label>
  <label>City <input name="city" /></label>
</div>

<!-- Description announced after the name -->
<label for="pwd">Password</label>
<input type="password" id="pwd" aria-describedby="pwd-rules" />
<p id="pwd-rules">Minimum 12 characters, including a number.</p>

4. Live Regions & Dynamic Content

Screen readers announce what has focus — but modern apps change content without moving focus: cart counts, toast notifications, validation results, chat messages. Live regions bridge that gap: mark a container with aria-live and the screen reader announces its text changes automatically.

Choose politeness deliberately. aria-live="polite" waits for a pause — right for status updates, save confirmations, and search result counts. aria-live="assertive" interrupts immediately — reserve it for genuine emergencies like session timeouts or critical errors, because interrupting a screen reader mid-sentence is genuinely disruptive. role="status" and role="alert" are polite and assertive shortcuts with the same semantics.

Two implementation rules prevent the classic failures. First, the live region must exist in the DOM before the update — dynamically injecting both the region and its text in one operation is silently ignored by some screen readers. Second, keep announcements concise and atomic: aria-atomic="true" ensures the whole message is read, not just the changed fragment.

<!-- Live region present from page load, updated by JS -->
<div id="cart-status" role="status" aria-live="polite" aria-atomic="true"></div>
<div id="form-errors" role="alert" aria-live="assertive"></div>

<script>
// Polite: announced when the screen reader pauses
function updateCart(count) {
  document.getElementById('cart-status').textContent =
    `${count} items in cart, $${total.toFixed(2)}`;
}

// Assertive: interrupts — use sparingly
function criticalError(msg) {
  document.getElementById('form-errors').textContent = msg;
}
</script>

5. States, Properties & Costly Mistakes

Widget roles come with required states and properties, and omitting them is worse than using no ARIA at all — a half-implemented tablist confuses more than a plain list of links. Each ARIA design pattern (tabs, accordion, dialog, switch, slider) has a contract: specific roles, required keyboard behavior, and states like aria-selected, aria-expanded, or aria-checked that must be kept in sync with the visual state on every interaction.

The expensive mistakes share a theme: states that lie. An aria-expanded="false" on an open menu, a toggle whose aria-checked never updates, a dialog missing aria-modal="true" and focus trapping. Screen reader users trust these states completely — a lying state is not a minor bug, it is misinformation.

Before hand-rolling any widget, check whether the platform now offers it natively: <dialog>, <details>/<summary>, popover attributes, and native form controls cover most needs in 2026. And whenever you do build custom, test with a real screen reader — the accessibility tree in devtools shows what you exposed, but only assistive technology shows what the user experiences.

PatternKey roles / statesNative alternative?
Tabstablist, tab, tabpanel + aria-selectedNo — custom (or links)
Accordionbutton + aria-expanded, regionYes — details/summary
Dialogdialog + aria-modal, labelledbyYes — <dialog> element
Toggle switchswitch + aria-checkedYes — checkbox styled
Tooltiparia-describedby on triggerPartial — title is unreliable
 
<!-- Accessible tabs: roles, states, and keyboard contract -->
<div role="tablist" aria-label="Product views">
  <button role="tab" id="tab-1" aria-selected="true"
          aria-controls="panel-1">Overview</button>
  <button role="tab" id="tab-2" aria-selected="false" tabindex="-1"
          aria-controls="panel-2">Specs</button>
</div>
<div role="tabpanel" id="panel-1" aria-labelledby="tab-1">...</div>
<div role="tabpanel" id="panel-2" aria-labelledby="tab-2" hidden>...</div>

6. Frequently Asked Questions (FAQs)

What does ARIA stand for?

ARIA stands for Accessible Rich Internet Applications. It is a W3C specification that adds semantic information to HTML — roles, states, and properties — so assistive technologies can understand custom interface components.

Can ARIA fix inaccessible HTML?

Rarely. ARIA enhances semantics but cannot fix broken fundamentals like missing keyboard support, unreachable content, or poor contrast. The rule is: fix the native HTML first, then add ARIA only where native semantics fall short.

What is the difference between aria-label and aria-labelledby?

aria-label provides a text string directly in the attribute, while aria-labelledby references the IDs of visible elements whose text becomes the label. Prefer aria-labelledby when visible text exists — it keeps the accessible name and visual label in sync for all users.

Do I need ARIA on native HTML elements?

No — native elements already expose correct roles and states. Adding role=button to a real button is redundant at best and harmful at worst if you get the details wrong. ARIA is for custom components built from divs and spans.

How do I test my ARIA implementation?

Test with at least one real screen reader (NVDA on Windows, VoiceOver on macOS/iOS), navigate by keyboard only, and inspect the accessibility tree in browser devtools. Automated checkers validate syntax, but only assistive technology confirms the experience.
