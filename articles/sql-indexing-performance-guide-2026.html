1. How Indexes Work: The B-Tree in Plain English

Without an index, the database answers WHERE email = 'x' by scanning every row — a full table scan that gets linearly slower as the table grows. An index is a separate, sorted data structure (usually a B-tree) mapping column values to row locations, turning that scan into a logarithmic lookup. The classic analogy is a book's index: finding a topic via the index versus reading the book cover to cover.

A B-tree stays balanced as data changes, so lookups cost roughly log(n) operations whether the table has ten thousand rows or ten million. Primary keys are indexed automatically, which is why lookups by ID are always fast. Every other fast lookup in your application exists because somebody created an index — or suffers because nobody did.

Indexes are not free: each one consumes disk space and must be updated on every INSERT, UPDATE, and DELETE touching its columns. That is why indexing is an engineering tradeoff rather than a reflex — you pay a small write cost to buy large read speedups, and the art is choosing indexes whose read savings dwarf their write costs.

2. Creating the Right Indexes

Start with the obvious: index every foreign key, every column in WHERE clauses of frequent queries, and columns used in JOIN conditions and ORDER BY. A single-column index on users(email) makes login lookups instant; one on orders(customer_id) makes "show my orders" fast. These cover the large majority of real-world slow queries.

Composite indexes handle multi-column filters, but column order matters because of the leftmost-prefix rule: an index on (status, created_at) accelerates queries filtering on status alone or status-plus-created_at, but not queries filtering only on created_at. Put equality-tested columns first, then at most one range-tested column — additional columns after a range rarely help.

Covering indexes go one step further: when the index contains every column the query needs, the database answers without touching the table at all (an "index-only scan"). In PostgreSQL you can append extra payload columns with INCLUDE; in MySQL, adding them to the index key achieves the same. Measure before and after — covering indexes are powerful but wider than they look.

-- Single-column index for a frequent lookup
CREATE INDEX idx_users_email ON users(email);

-- Composite index: equality column first, range column last
-- Speeds up: WHERE status = 'shipped'
-- Speeds up: WHERE status = 'shipped' AND created_at > '2026-01-01'
-- Does NOT help: WHERE created_at > '2026-01-01'  (leftmost prefix!)
CREATE INDEX idx_orders_status_created ON orders(status, created_at);

-- Covering index: query answered from the index alone
CREATE INDEX idx_products_cat_price ON products(category_id, price, title);

3. Reading EXPLAIN Like a Database Engineer

EXPLAIN is how you stop guessing and start seeing. Prefix any SELECT with EXPLAIN (or EXPLAIN ANALYZE in PostgreSQL to also execute it) and the database reveals its plan: which indexes it will use, how many rows it expects to touch, and where the time goes. Run it on every query that feels slow before changing anything.

Learn to read three fields first. In MySQL, type: ALL means a full table scan (bad on large tables), while ref, range, and const mean index usage (good). The key column names the chosen index — NULL means none. In PostgreSQL, look for Seq Scan versus Index Scan in the plan. The rows estimate and Extra info ("Using index" is excellent; "Using filesort" or "Using temporary" deserve scrutiny) complete the picture.

A healthy plan for a filtered query on a big table shows an index access touching a small fraction of rows. If EXPLAIN shows a full scan on a million-row table for a query that should return ten rows, you have found your missing index. Add it, re-run EXPLAIN, and confirm the plan changed before declaring victory.

-- MySQL: inspect the plan before optimizing
EXPLAIN SELECT id, title, price
FROM products
WHERE category_id = 5 AND price < 100
ORDER BY price;

-- What good looks like (simplified):
-- type: range        ← index range scan, not ALL
-- key:  idx_products_cat_price  ← our composite index is used
-- rows: 42           ← touches dozens of rows, not millions
-- Extra: Using index  ← covering index, table never touched

-- PostgreSQL equivalent with execution stats:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM products WHERE category_id = 5;

4. Anti-Patterns That Silently Disable Indexes

The most expensive index is the one the optimizer cannot use. Wrapping an indexed column in a function — WHERE YEAR(created_at) = 2026 — forces the database to compute the function per row instead of seeking the index; rewrite as a range (created_at >= '2026-01-01' AND created_at < '2027-01-01') and the index works again. The same applies to arithmetic on columns and most string functions in the WHERE clause.

Leading wildcards are the next classic: LIKE 'ali%' can use an index on the column, but LIKE '%ali%' cannot, because the B-tree is sorted from the left. If substring search is a real requirement, reach for a full-text index rather than hoping a B-tree will cope. Similarly, mixing types — comparing an integer column to a string literal — triggers implicit conversion that bypasses the index on some engines.

OR conditions across different columns, NOT IN, and != comparisons frequently defeat index usage too. Sometimes the fix is rewriting (UNION of two indexed queries instead of OR); sometimes the optimizer is simply right that a scan is cheaper, as with low-selectivity flags like a boolean. EXPLAIN tells you which case you are in — trust it over rules of thumb.

-- BAD: function on the indexed column kills the index
SELECT * FROM orders WHERE YEAR(created_at) = 2026;

-- GOOD: sargable range lets the index seek
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

-- BAD: leading wildcard cannot use a B-tree index
SELECT * FROM users WHERE name LIKE '%ali%';

-- GOOD: trailing wildcard CAN use the index
SELECT * FROM users WHERE name LIKE 'ali%';
-- For real substring search, add a FULLTEXT index instead.

5. Index Maintenance & Monitoring

Indexes are not "set and forget." Every index taxes writes, so audit for dead weight: PostgreSQL's pg_stat_user_indexes reveals indexes with zero scans, and MySQL's performance schema (sys.schema_unused_indexes) does the same. An unused index costs write performance and disk for literally nothing — drop it with confidence after confirming across a full business cycle.

Statistics drive the optimizer's choices, and stale statistics drive bad choices. PostgreSQL's autovacuum usually keeps them fresh, but after bulk loads run ANALYZE manually; MySQL updates statistics more eagerly but still benefits from ANALYZE TABLE after major changes. If EXPLAIN suddenly picks a terrible plan, stale stats are a prime suspect.

For ongoing vigilance, enable the slow query log (MySQL) or pg_stat_statements (PostgreSQL) and review the top queries by total time weekly. Performance work compounds: the same handful of queries usually dominate load, and each index you add for them pays dividends on every future request. Optimize the vital few, not the trivial many.

-- PostgreSQL: find indexes that are never used
SELECT schemaname, relname AS table_name, indexrelname AS index_name
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE '%pkey%';

-- MySQL: find unused indexes via performance schema
SELECT * FROM sys.schema_unused_indexes;

-- Refresh optimizer statistics after bulk changes
ANALYZE products;          -- PostgreSQL
-- ANALYZE TABLE products; -- MySQL equivalent

6. Frequently Asked Questions (FAQs)

Can you have too many indexes?

Yes. Every index slows down INSERT, UPDATE, and DELETE operations and consumes disk space. Index foreign keys and columns used in WHERE, JOIN, and ORDER BY clauses, then audit for unused indexes with pg_stat_user_indexes or MySQL's sys.schema_unused_indexes and drop the dead weight.

What order should columns go in a composite index?

Put the most selective equality-tested columns first, followed by at most one range-tested column. This follows the leftmost-prefix rule: queries using a prefix of the index still benefit, while queries filtering only on later columns do not.

Why isn't my query using its index?

Common causes: a function wrapped around the indexed column, a leading-wildcard LIKE, a data-type mismatch triggering implicit conversion, stale optimizer statistics, or low selectivity where the optimizer correctly judges a scan cheaper. EXPLAIN reveals which one.

Do indexes slow down writes?

Slightly — every write must update each index on the affected columns. For read-heavy applications the tradeoff is overwhelmingly worthwhile. For write-heavy tables, index deliberately and drop anything unused.

How do I find queries that need indexes?

Enable the slow query log or pg_stat_statements, rank queries by total execution time, and EXPLAIN the top offenders. Look for full scans (type ALL in MySQL, Seq Scan in PostgreSQL) on large tables — those are your missing-index candidates.
