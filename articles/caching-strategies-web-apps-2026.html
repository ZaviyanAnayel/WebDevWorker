1. Browser Caching: Cache-Control, ETags, and Validators

The browser cache is the fastest cache you will ever use, because a cache hit means zero network requests at all. When a visitor returns to your site, resources served from the local disk cache load in milliseconds, which is why getting your HTTP cache headers right is the single highest-leverage performance change most teams can make. Every response your server sends should carry an explicit caching policy instead of leaving the decision to browser heuristics.

The Cache-Control header is the modern control plane. public, max-age=31536000, immutable tells browsers and shared caches to store fingerprinted assets — files whose names change whenever their content changes, like app.a3f9c2.js — for a full year without revalidation. For HTML documents that change on every deploy, use no-cache, which counterintuitively still caches the response but forces revalidation with the server before each reuse.

Validators make revalidation cheap. An ETag is a fingerprint of the response body, while Last-Modified is a timestamp. On the next request the browser sends If-None-Match or If-Modified-Since, and if nothing changed the server replies 304 Not Modified with an empty body. You skip the full payload transfer while keeping content fresh.

// Cache policy by asset type (Express)
app.use(express.static("public", {
  setHeaders(res, path) {
    if (/\.[a-f0-9]{8}\.(js|css)$/.test(path)) {
      // Fingerprinted assets: cache for 1 year, never revalidate
      res.setHeader("Cache-Control", "public, max-age=31536000, immutable");
    } else if (path.endsWith(".html")) {
      // HTML entry points: always revalidate
      res.setHeader("Cache-Control", "public, max-age=0, must-revalidate");
    }
  }
}));

2. CDN Edge Caching and Cache Keys

A content delivery network puts your cache physically close to users by storing copies on edge servers in hundreds of cities. The first visitor in a region pays the origin round-trip; everyone after that gets the response from the edge in tens of milliseconds. For global audiences this routinely cuts time-to-first-byte by 60 to 80 percent, which directly improves Core Web Vitals and conversion rates.

Everything hinges on the cache key — the set of request attributes used to look up a cached object. By default most CDNs key on the URL including the query string, so /api/products?sort=price and /api/products?sort=name are stored as separate objects. Include cookies or authorization headers in the key only when the response truly varies per user; keying on a session cookie by accident is the classic reason a CDN cache hit ratio collapses to near zero.

Set TTLs in layers: long at the edge for truly static assets, short for semi-dynamic pages, and zero for personalized HTML. Use surrogate keys so one purge call can invalidate every cached object related to a product, article, or user. Most providers expose purge-by-tag APIs that propagate globally within seconds, which makes deploys safe even with aggressive caching.

// Cloudflare Worker: cache API responses per URL, ignore cookies
addEventListener("fetch", (event) => {
  event.respondWith(handle(event.request));
});

async function handle(req) {
  const cache = caches.default;
  const key = new Request(req.url, { method: "GET" }); // strip cookies from key
  let res = await cache.match(key);
  if (!res) {
    res = await fetch(req);
    res = new Response(res.body, res);
    res.headers.set("Cache-Control", "public, max-age=300, s-maxage=3600");
    event.waitUntil(cache.put(key, res.clone()));
  }
  return res;
}

3. Server-Side Caching with Redis and Memcached

When the CDN misses and the request reaches your origin, an in-memory store like Redis stands between your application and the database. Database queries — especially joins, aggregations, and full-text search — are often 10 to 100 times slower than a Redis lookup, so caching rendered fragments, query results, and session data here removes the most expensive work from the hot path.

The cache-aside pattern is the workhorse: the application checks the cache first, falls through to the database on a miss, then writes the result back with a TTL. It keeps the cache lazy and self-healing — stale or evicted entries simply get recomputed on demand. Write-through, where every database write also updates the cache, guarantees freshness but adds latency to writes and complexity to failure paths, so reserve it for data where staleness is genuinely unacceptable.

Choose TTLs from the data's natural rhythm: product catalogs can live for minutes or hours, user sessions for the session lifetime, and rate-limit counters for seconds. Pair TTLs with an eviction policy like allkeys-lru so Redis sheds the least-recently-used keys under memory pressure instead of failing writes, and monitor your hit ratio as the primary health metric.

// Cache-aside pattern with Redis (Node.js)
import { createClient } from "redis";
const redis = createClient();
await redis.connect();

async function getProduct(id) {
  const key = `product:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);          // cache hit

  const product = await db.products.findById(id); // cache miss
  await redis.setEx(key, 600, JSON.stringify(product)); // 10-minute TTL
  return product;
}

4. Cache Invalidation: Strategies That Actually Work

Cache invalidation keeps its reputation as one of the hard problems in computer science because purging the wrong thing — or nothing at all — ships stale content to users. The reliable strategies all share one idea: make invalidation deterministic instead of hopeful, so a deploy or a data change maps to an exact, verifiable cache operation.

For static assets, never invalidate — version instead. Content hashing in the filename (main.9d2c1a.js) turns every deploy into a brand-new URL, so old cached copies are harmless and the HTML file that references them can stay on a short TTL. For dynamic content, purge by surrogate key: tag every cached object with the entities it depends on (product:42, category:shoes) and issue one purge call per changed entity.

Time-based expiry remains the safety net underneath every other strategy. Even with perfect purge logic, a modest TTL bounds how long a missed invalidation can hurt you. The practical rule of thumb: TTLs get shorter as you move from fingerprinted assets (one year) to edge HTML (minutes) to personalized API responses (seconds, or no caching at all).

// Purge all CDN objects tagged with a product id (provider API)
async function purgeProduct(productId) {
  const res = await fetch("https://api.cdn-provider.com/v1/purge", {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${process.env.CDN_API_TOKEN}`,
      "Content-Type": "application/json"
    },
    body: JSON.stringify({ surrogate_keys: [`product:${productId}`] })
  });
  if (!res.ok) throw new Error(`Purge failed: ${res.status}`);
  return res.json();
}

5. Advanced Patterns: Stale-While-Revalidate and Beyond

stale-while-revalidate decouples freshness from latency: the cache serves the stored response immediately — even past its TTL — while a background request refreshes it for next time. Users never wait on a revalidation round-trip, which makes it ideal for personalized feeds, dashboards, and API responses where slightly stale data is perfectly acceptable.

stale-if-error extends the same idea to failure: if the origin is down, keep serving the last good response instead of an error page. Combined, the two directives turn your cache layers into a resilience mechanism, not just a speed mechanism — your site stays up and fast even during origin incidents.

Two more patterns round out a production setup. Request coalescing (the thundering-herd guard) ensures that when a popular key expires, only one request hits the origin while the rest wait for the fresh value. Cache warming preloads critical keys after a deploy or on a schedule, so real users never experience a cold cache.

// Stale-while-revalidate fetch wrapper (client-side)
const swrCache = new Map();

async function swrFetch(url, ttlMs = 60000) {
  const entry = swrCache.get(url);
  if (entry) {
    if (Date.now() - entry.ts < ttlMs) return entry.data; // fresh: serve
    // stale: serve now, refresh in the background
    fetch(url).then(r => r.json())
      .then(d => swrCache.set(url, { data: d, ts: Date.now() }));
    return entry.data;
  }
  const data = await (await fetch(url)).json();
  swrCache.set(url, { data, ts: Date.now() });
  return data;
}

6. Frequently Asked Questions (FAQs)

How long should I cache static assets?

Fingerprint them with a content hash in the filename and cache for one year with the immutable directive. Because the URL changes whenever the content changes, long TTLs are safe and eliminate revalidation traffic entirely.

What is the difference between no-cache and no-store?

no-cache still stores the response but revalidates with the server before every reuse, giving you freshness with 304 savings. no-store forbids storing the response anywhere and is meant for sensitive data such as banking or checkout pages.

When should I use Redis instead of a CDN?

Use a CDN for cacheable HTTP responses served to many users, and Redis for origin-side work: database query results, session data, rate limits, and rendered fragments that are expensive to recompute but not HTTP-cacheable.

How do I invalidate CDN cache after a deploy?

Version static assets with content hashes so they need no invalidation, keep HTML on short TTLs, and purge dynamic content by surrogate key through your provider's purge API, which typically propagates globally within seconds.

Does caching improve SEO?

Yes. Google uses page speed signals such as LCP and INP in ranking, and effective caching directly improves both. Faster repeat visits also reduce bounce rates, which compounds the benefit over time.

Keep leveling up

Caching is a compounding skill — every layer you master shaves milliseconds off every future visit. Keep experimenting with TTLs, keys, and invalidation until your hit ratios stay above 95 percent.
