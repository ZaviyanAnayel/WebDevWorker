1. Three Flavors: Callbacks, Sync, and Promises

The fs module ships three API styles, and choosing correctly is the first skill. The promise API (import { readFile } from "node:fs/promises") is the modern default — clean async/await, proper error propagation, no nesting. The callback API (node:fs) is the legacy original; you'll still meet it in old tutorials and libraries. The sync API (readFileSync) blocks the event loop until the operation completes.

Blocking the event loop is the cardinal sin of Node.js servers: while a sync call runs, no other request is processed. So the rule is simple — never use sync fs methods in request handlers or hot paths. Sync is fine in CLI scripts, build tools, and one-time startup code (loading config before listen()), where nothing else is waiting.

Prefer the node: import prefix (node:fs/promises) over the bare fs — it makes core modules unambiguous and is the documented modern style. For new code, default to fs/promises with async/await and try/catch; reach for streams (section 4) when files get large.

API styleImportWhen to use
Promises ✅node:fs/promisesDefault for all new code — async/await, clean errors
Callbacksnode:fsLegacy code and old libraries; avoid in new code
Sync ⚠️readFileSync etc.CLI scripts, build tools, server startup only — never in request handlers
import { readFile } from "node:fs/promises";

// ✅ Modern style: promises + async/await
async function loadConfig(path) {
  try {
    const text = await readFile(path, "utf8");  // utf8 → string, omit → Buffer
    return JSON.parse(text);
  } catch (err) {
    if (err.code === "ENOENT") return {};       // file missing → defaults
    throw err;                                  // real errors propagate
  }
}

// ⚠️ Sync: acceptable at startup, forbidden in request handlers
import { readFileSync } from "node:fs";
const config = JSON.parse(readFileSync("./config.json", "utf8")); // runs once, before listen()

2. Reading and Writing Files

readFile loads an entire file into memory — perfect for configs, templates, and JSON payloads. Pass "utf8" to get a string; omit it to get a Buffer for binary data like images. writeFile creates or fully replaces a file; appendFile adds to the end without erasing — the right choice for logs. All three are atomic enough for typical use but not transactional: for critical writes, write to a temp file then rename it over the target.

JSON is the most common file format in Node.js work. The pattern is always readFile → JSON.parse on the way in and JSON.stringify → writeFile on the way out, with JSON.stringify(data, null, 2) for human-readable output. Wrap parsing in try/catch — a corrupt file throws SyntaxError, and crashing on a bad config is worse than falling back to defaults with a loud warning.

Check existence without racing: rather than existsSync-then-read (a TOCTOU race), just attempt the read and handle ENOENT. For metadata — size, modification time, file vs. directory — use stat(), which returns a Stats object with .isFile(), .isDirectory(), .size, and .mtime.

import { readFile, writeFile, appendFile, stat } from "node:fs/promises";

// Read → parse → use, with a graceful fallback
async function readJson(path, fallback) {
  try {
    return JSON.parse(await readFile(path, "utf8"));
  } catch (err) {
    if (err.code === "ENOENT" || err instanceof SyntaxError) {
      console.warn(`Using fallback: ${path} unreadable (${err.code ?? "bad JSON"})`);
      return fallback;
    }
    throw err;
  }
}

// Write pretty JSON; append to logs without erasing
await writeFile("./data/users.json", JSON.stringify(users, null, 2), "utf8");
await appendFile("./logs/app.log", `[${new Date().toISOString()}] server started\n`);

// Inspect before you act
const info = await stat("./data/users.json");
console.log(info.isFile(), info.size, info.mtime);  // true 1842 2026-10-14T…

3. Paths and Directories

Never concatenate paths with string addition — "./data" + "/" + file breaks on Windows and invites traversal bugs. The node:path module is the correct tool: path.join() concatenates segments with the right separator and normalizes ..; path.resolve() turns a relative path into an absolute one from the current working directory; path.basename/extname/dirname dissect the pieces.

The classic gotcha is __dirname, which doesn't exist in ES modules. The ESM equivalent derives it from import.meta.url via fileURLToPath — two lines you'll write in every ESM project that reads files relative to its own location. Remember that relative fs paths resolve against process.cwd() (where the command was run), not the script's directory — anchoring with __dirname removes that fragility.

Directory operations round out the toolkit: mkdir(path, { recursive: true }) creates nested directories without complaining if they exist; readdir(path, { withFileTypes: true }) lists entries as Dirent objects (so you can filter files vs. directories without extra stat calls); rename moves files; and rm(path, { recursive: true, force: true }) is the modern recursive delete.

import path from "node:path";
import { fileURLToPath } from "node:url";
import { mkdir, readdir, rename, rm } from "node:fs/promises";

// __dirname equivalent for ES modules (memorize these two lines)
const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

// Build paths safely — never string-concatenate
const dataDir = path.join(__dirname, "data");
const outFile = path.join(dataDir, "report.json");
console.log(path.extname(outFile)); // ".json"
console.log(path.basename(outFile, ".json")); // "report"

// Directories: create nested, list with types, move, remove
await mkdir(dataDir, { recursive: true });

for (const entry of await readdir(dataDir, { withFileTypes: true })) {
  if (entry.isFile() && entry.name.endsWith(".tmp")) {
    await rm(path.join(dataDir, entry.name));   // clean temp files
  }
}

await rename(outFile, path.join(dataDir, "report-final.json"));

4. Streams: Handling Big Files

readFile loads the whole file into RAM — fine for kilobytes, fatal for gigabytes. Streams process data in chunks, keeping memory flat regardless of file size. createReadStream emits data events as chunks arrive; createWriteStream accepts .write() calls; and stream.pipeline wires them together with proper error propagation and cleanup — always prefer pipeline over manual .pipe() chains.

The killer use case is serving or transforming large files: copying a 4GB video, gzipping logs, or parsing a massive CSV line by line with readline. With streams, a 100MB file and a 100GB file use the same memory. The for await...of syntax makes consuming a readable stream feel like a simple loop, and it's the most readable pattern for line-oriented processing.

One concept worth knowing: backpressure — when the writer is slower than the reader, .write() returns false and you should pause until the drain event. pipeline handles this automatically, which is another reason to use it. If you find yourself manually juggling drain, you're probably reimplementing pipeline badly.

import { createReadStream, createWriteStream } from "node:fs";
import { pipeline } from "node:stream/promises";
import { createGzip } from "node:zlib";
import readline from "node:readline";

// Copy + gzip a huge file with constant memory — pipeline handles
// backpressure, errors, and cleanup automatically
await pipeline(
  createReadStream("./logs/huge.log"),
  createGzip(),
  createWriteStream("./logs/huge.log.gz")
);
console.log("compressed without loading it all into RAM");

// Process a massive CSV line by line
const rl = readline.createInterface({
  input: createReadStream("./data/events.csv"),
  crlfDelay: Infinity,
});
let count = 0;
for await (const line of rl) {
  if (line.includes("purchase")) count++;
}
console.log(`purchase events: ${count}`);

5. Watching Files and Best Practices

fs.watch notifies you when files change — the basis of dev-server auto-reload. It's efficient (OS-level notifications, no polling) but raw: events can fire twice for one save, filenames may be missing on some platforms, and recursive watching only works on macOS/Windows. For anything beyond a quick script, use chokidar, which normalizes all of this plus debouncing and glob ignores.

Debouncing matters because editors often save in bursts. A 100–300ms debounce that waits for writes to settle prevents processing half-written files — the classic bug where your watcher reads a file mid-save and chokes on truncated JSON. For config reloads, debounce then re-read with the safe readJson pattern from section 2.

Closing best practices: always specify encoding explicitly ("utf8") rather than converting Buffers later; set restrictive file permissions (0o600) for secrets via the mode option; handle ENOENT/EACCES/ENOSPC with useful messages instead of stack traces; and remember the golden rule — async fs in servers, sync fs only in scripts and startup. Follow that and the fs module will never be the thing that pages you.

import { watch } from "node:fs";

// Debounced watcher: wait for the editor to finish saving
let timer;
watch("./config.json", (eventType) => {
  if (eventType !== "change") return;
  clearTimeout(timer);
  timer = setTimeout(async () => {
    try {
      const config = await readJson("./config.json", {});
      console.log("config reloaded:", config);
    } catch (err) {
      console.error("reload failed, keeping old config:", err.message);
    }
  }, 250); // settle time for bursty editor saves
});

// Write secrets with restrictive permissions
import { writeFile } from "node:fs/promises";
await writeFile("./.secrets/token", token, { mode: 0o600 });  // owner read/write only

6. Frequently Asked Questions (FAQs)

Should I use readFile or readFileSync?

Use the async readFile (from fs/promises) in servers and anything handling concurrent work — sync methods block the event loop and stall every other request. readFileSync is fine in CLI scripts, build tools, and one-time startup code where nothing else is waiting.

How do I read and parse a JSON file in Node.js?

const data = JSON.parse(await readFile(path, 'utf8')). Always wrap it in try/catch: a missing file throws ENOENT and malformed JSON throws SyntaxError. In ES modules you can also use import with an import attribute, but readFile + JSON.parse works everywhere.

How do I handle very large files without running out of memory?

Use streams: createReadStream with pipeline() processes data in chunks so memory stays flat regardless of file size. readFile loads everything into RAM — fine for configs, dangerous for gigabyte-scale files.

Why doesn't __dirname work in ES modules?

__dirname is a CommonJS-only variable. In ES modules, derive it with two lines: const __filename = fileURLToPath(import.meta.url); const __dirname = path.dirname(__filename). This matters because relative fs paths resolve against process.cwd(), not your script's location.

Is fs.watch reliable for production file watching?

It's efficient but raw — duplicate events, missing filenames on some platforms, and no recursive watching on Linux. For robust watching (dev servers, build tools), use the chokidar library, which normalizes platform quirks and adds debouncing and glob support.
