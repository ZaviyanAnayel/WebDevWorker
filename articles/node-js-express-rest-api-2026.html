1. Project Setup: Node, npm, and Express

Express remains the most-used Node.js web framework because it does one thing well: it stays out of your way. It gives you routing, middleware, and request/response helpers, and leaves architecture decisions to you — which is liberating for small services and demands discipline as they grow. This guide builds a products API that demonstrates the patterns production Express apps actually use.

Start with a fresh directory, npm init -y, and npm install express. Add nodemon as a dev dependency for auto-restart during development. Use ES modules ("type": "module" in package.json) — the ecosystem has standardized on them, and all code here uses import syntax.

Even for a tutorial, separate concerns from the start: src/app.js builds the Express app (no listening — this makes testing trivial), src/server.js starts it, and src/routes/ holds route modules. Keep configuration in environment variables via dotenv, never hardcoded — ports, database URLs, and secrets all come from process.env.

# Scaffold the project
mkdir products-api && cd products-api
npm init -y
npm install express dotenv
npm install -D nodemon

# package.json (ES modules + handy scripts)
{
  "name": "products-api",
  "type": "module",
  "scripts": {
    "dev": "nodemon src/server.js",
    "start": "node src/server.js"
  }
}
// src/app.js — builds the app; server.js only listens (testable!)
import express from "express";

export function createApp() {
  const app = express();
  app.use(express.json());              // parse JSON request bodies
  app.get("/health", (req, res) => res.json({ ok: true }));
  return app;
}

// src/server.js — the only file that touches the network
import "dotenv/config";
import { createApp } from "./app.js";

const PORT = process.env.PORT || 3000;
createApp().listen(PORT, () => console.log(`API listening on :${PORT}`));

2. Routes and CRUD Endpoints

Express routing maps HTTP methods + URL patterns to handler functions. For a REST API, use an express.Router() per resource and mount it at a path prefix — app.use("/api/products", productRouter) keeps app.js clean while each router owns its resource's full CRUD surface. Route parameters (/products/:id) arrive in req.params; query strings in req.query; JSON bodies in req.body (after express.json()).

Follow REST conventions in your route table: GET /api/products lists, POST /api/products creates (respond 201 with the new resource), GET /api/products/:id reads one (404 when missing), PUT /api/products/:id replaces, PATCH /api/products/:id partially updates, and DELETE /api/products/:id removes (204 with no body). Consistent verbs and plural nouns make your API predictable before anyone reads the docs.

Keep route handlers thin: validate input, call a service function, send the response. Business logic living directly in handlers becomes untestable spaghetti the moment you add a second caller (a CLI importer, a webhook, a queue worker). Even in this guide's in-memory example, note how the handler delegates to small functions rather than embedding logic.

// src/routes/products.js
import { Router } from "express";

const products = new Map();   // in-memory store (swap for a DB later)
let nextId = 1;
const router = Router();

// GET /api/products — list all
router.get("/", (req, res) => {
  res.json([...products.values()]);
});

// POST /api/products — create (201 + the new resource)
router.post("/", (req, res) => {
  const { title, price } = req.body ?? {};
  const product = { id: String(nextId++), title, price };
  products.set(product.id, product);
  res.status(201).json(product);
});

// GET /api/products/:id — read one (404 when missing)
router.get("/:id", (req, res) => {
  const product = products.get(req.params.id);
  if (!product) return res.status(404).json({ error: "Product not found" });
  res.json(product);
});

// PUT /api/products/:id — full replace
router.put("/:id", (req, res) => {
  if (!products.has(req.params.id)) {
    return res.status(404).json({ error: "Product not found" });
  }
  const product = { id: req.params.id, ...req.body };
  products.set(product.id, product);
  res.json(product);
});

// DELETE /api/products/:id — remove (204, no body)
router.delete("/:id", (req, res) => {
  if (!products.delete(req.params.id)) {
    return res.status(404).json({ error: "Product not found" });
  }
  res.status(204).end();
});

export default router;

3. Middleware: The Heart of Express

Middleware is Express's core abstraction: functions with the signature (req, res, next) that run in registration order, each deciding whether to pass control onward with next(), end the response, or hand an error to next(err). Everything — body parsing, logging, authentication, CORS, error handling — is middleware. Understanding the pipeline is understanding Express.

Write custom middleware for cross-cutting concerns. A request logger records method, URL, and duration. An auth middleware verifies a token and attaches the user to req so handlers stay clean. Apply middleware globally with app.use(), per-router, or per-route — router.post("/", requireAuth, handler) protects just the write endpoints while reads stay public, a pattern nearly every API needs.

Order matters enormously. express.json() must run before any handler reading req.body; auth must run before protected routes; and the error-handling middleware — recognizable by its four arguments (err, req, res, next) — must be registered last, after all routes, so it catches everything. A 404 'not found' catcher also belongs near the end, before the error handler.

MiddlewarePurposeWhere it runs
express.json()Parse JSON request bodies into req.bodyFirst — before any route
Request loggerLog method, URL, status, durationEarly — observe everything
CORS / helmetCross-origin policy, security headersEarly — before routes
Auth (requireAuth)Verify token, attach req.userBefore protected routes only
404 catcherJSON error for unmatched routesAfter all routes
Error handler (err, req, res, next)Centralized error → response mappingAbsolute last
// src/middleware/logger.js — custom middleware
export function logger(req, res, next) {
  const start = Date.now();
  res.on("finish", () => {
    console.log(`${req.method} ${req.originalUrl} → ${res.statusCode} (${Date.now() - start}ms)`);
  });
  next();   // pass control to the next middleware/handler
}

// src/middleware/auth.js — route protection
export function requireAuth(req, res, next) {
  const token = req.headers.authorization?.replace("Bearer ", "");
  if (token !== process.env.API_TOKEN) {
    return res.status(401).json({ error: "Unauthorized" });
  }
  req.user = { id: "demo-user" };   // handlers read req.user, not tokens
  next();
}

// src/middleware/errors.js — centralized error handler (4 args = error middleware)
export function notFound(req, res) {
  res.status(404).json({ error: `Route ${req.method} ${req.path} not found` });
}

// eslint-disable-next-line no-unused-vars
export function errorHandler(err, req, res, next) {
  console.error(err);
  const status = err.status || 500;
  res.status(status).json({
    error: status === 500 ? "Internal server error" : err.message,
  });
}

4. Validation, Status Codes, and Error Handling

Never trust request bodies. Validate req.body before touching it: check required fields, types, and ranges, and respond 400 with a clear message listing what's wrong. For real projects use a schema validator like zod — one schema gives you validation, TypeScript types, and descriptive errors — but even hand-rolled checks beat nothing. Validate route params too: a malformed :id should be a 400, not a database error.

Async handlers need care: Express 4 does not catch rejected promises, so an await that throws becomes an unhandled rejection instead of a 500 response. Wrap async handlers in a tiny helper that forwards rejections to next() — or upgrade to Express 5, which handles async errors natively. Either way, never let a promise rejection escape silently; that's how servers hang.

Map errors to status codes deliberately in your centralized handler: validation failures → 400, missing auth → 401, forbidden → 403, missing resources → 404, conflicts → 409, server bugs → 500. Keep the error response envelope consistent ({ error: message } or { errors: [...] }) across every endpoint — clients should parse errors once, not per route.

// Async wrapper: forwards promise rejections to Express error handling (Express 4)
export const asyncHandler = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

// Validation middleware — reusable per route
export function validateProduct(req, res, next) {
  const { title, price } = req.body ?? {};
  const problems = [];
  if (typeof title !== "string" || !title.trim()) problems.push("title must be a non-empty string");
  if (typeof price !== "number" || price < 0) problems.push("price must be a non-negative number");
  if (problems.length) return res.status(400).json({ errors: problems });
  next();
}

5. Structuring for Growth and Next Steps

When the API outgrows one router file, split into three layers: routes (HTTP only — parse input, call services, send responses), services (business logic, reusable outside HTTP), and data access (database queries, one module per table/collection). Handlers stay under ~15 lines, logic becomes unit-testable without HTTP, and adding a second interface (a worker, a CLI) reuses services directly.

From here, the natural next steps are persistence (PostgreSQL with Prisma or Drizzle — both have excellent Express guides), authentication (JWT access tokens + rotating refresh tokens), and API documentation (OpenAPI via swagger-jsdoc, generated from JSDoc comments on your routes). Each is a well-trodden path; the architecture above accommodates all of them without restructuring.

6. Frequently Asked Questions (FAQs)

Should I choose Express, Fastify, or NestJS for a new API?

Express is the safe default: the largest ecosystem, the most tutorials, and enough flexibility for most services. Choose Fastify for higher throughput with a similar feel, or NestJS when you want an opinionated, Angular-style architecture with dependency injection out of the box.

How do I handle errors in async Express route handlers?

In Express 4, wrap async handlers so rejected promises reach next(err) — a tiny asyncHandler wrapper does this. Express 5 handles async rejections natively, so upgrading removes the need for the wrapper. Either way, finish with a centralized 4-argument error-handling middleware.

Where should business logic live in an Express app?

In service modules, not route handlers. Routes should only parse HTTP input, call a service function, and send the response. This keeps handlers thin, makes logic unit-testable without spinning up HTTP, and lets workers or CLIs reuse the same services.

How do I secure an Express REST API?

Use helmet for security headers, configure CORS explicitly, validate all input (zod is the modern default), add rate limiting with express-rate-limit, authenticate with tokens (never trust client input), and keep secrets in environment variables — never in code or git.

What changed in Express 5, and should I upgrade?

Express 5 is now stable: it handles async errors natively, updates path matching (wildcards need named syntax like /*splat), and drops some deprecated APIs. New projects should start on v5; existing v4 apps should plan the migration since v4 is in maintenance mode.
