1. Event Bubbling and Capturing Explained

When a user clicks a button nested inside a card inside a page, the browser does not fire one lonely event — it dispatches a journey. In the capture phase the event travels down from window to the target; at the target phase it arrives; then in the bubble phase it travels back up through every ancestor. By default, addEventListener handlers run during the bubble phase, which is why a click on a button also “trigger” listeners on its parent divs.

This travel itinerary is the entire basis of event delegation. Two properties of the event object tell you where you are in the journey: event.target is the element where the event originated (the actual button clicked), while event.currentTarget is the element the listener is attached to. Confusing the two is the number-one delegation bug — inside a delegated handler, target is the child, currentTarget is the parent you listened on.

You can observe the capture phase with { capture: true }, and stopPropagation() halts the journey entirely — useful, but dangerous near delegated parents, as section four explains. For now, the takeaway is simple: because events bubble, a parent can hear everything its children do.

// Watch an event bubble up through three levels
document.querySelector('#page').addEventListener('click', e => {
  console.log('page heard it. target =', e.target.id,
              '| currentTarget =', e.currentTarget.id);
});
document.querySelector('#card').addEventListener('click', e => {
  console.log('card heard it. target =', e.target.id);
});
document.querySelector('#btn').addEventListener('click', e => {
  console.log('button heard it first. target =', e.target.id);
});
// Clicking #btn logs: button -> card -> page (bubble order)
// e.target is 'btn' in ALL THREE handlers; currentTarget differs

2. The Delegation Pattern: One Listener to Rule Them All

Event delegation inverts the usual approach: instead of attaching a listener to every item, you attach one listener to their common parent and let bubbling deliver each child's events to it. Inside the handler you inspect event.target — usually via target.closest(selector) — to find which child (or which kind of child) triggered the event, then act accordingly.

closest() is the hero method here: it climbs from the event target up through ancestors until it finds an element matching your selector, or returns null. This handles clicks on nested markup gracefully — a click on the <svg> icon inside a <button> inside a list item still resolves to the list item. Always null-check the result: clicks on empty parent padding match nothing, and your handler must ignore those.

The wins are threefold. Memory: one listener instead of hundreds. Setup cost: no loop attaching handlers on render. And — the killer feature covered next — dynamic elements work with zero extra code, because the listener lives on the parent that was there all along.

// Delegation: ONE listener handles every row, present and future
const list = document.querySelector('#todo-list');

list.addEventListener('click', (e) => {
  const deleteBtn = e.target.closest('.delete-btn');
  if (deleteBtn) {
    deleteBtn.closest('li').remove(); // remove that row
    return;
  }

  const row = e.target.closest('li');
  if (row) {
    row.classList.toggle('done'); // toggle completion
  }
  // clicks on empty list padding: both null -> ignored. Correct!
});

// vs. the naive approach: a listener PER row, re-attached on every render
// document.querySelectorAll('#todo-list li').forEach(li => { ... }); // don't

3. Delegation with Dynamic Content

Dynamic content is where delegation stops being an optimization and becomes the only sane approach. Chat messages arriving over a websocket, infinite-scroll cards, rows added by a form — with per-element listeners you must remember to attach handlers to every new node (and detach them on removal to avoid leaks). With delegation, new children are covered the moment they are inserted, because the parent listener was already listening.

This also simplifies framework-free components. A tabs widget, an accordion, a dropdown menu: each becomes a container with one delegated click handler that switches on data-action attributes. The markup stays declarative (<button data-action="open">), the JavaScript stays in one place, and adding a new tab means adding HTML, not wiring code.

One subtlety: delegated handlers see events from all descendants, including nested interactive elements. A delete button inside a clickable card needs its branch checked first (as in the todo example) so the card-toggle logic does not also fire. Order your closest() checks from most-specific to least-specific, and return early after handling.

// Dynamic chat: messages arrive later, clicks still work
const chat = document.querySelector('#chat');

chat.addEventListener('click', (e) => {
  const msg = e.target.closest('.message');
  if (!msg) return;

  if (e.target.closest('.react-btn')) {
    msg.querySelector('.reactions').textContent += '\u2764\uFE0F';
  } else if (e.target.closest('.reply-btn')) {
    startReply(msg.dataset.id);
  }
});

// Simulate incoming messages — no listener wiring needed
setInterval(() => {
  const div = document.createElement('div');
  div.className = 'message';
  div.dataset.id = crypto.randomUUID();
  div.innerHTML = '<p>Hello!</p>' +
    '<button class="react-btn">\u2764\uFE0F</button>' +
    '<button class="reply-btn">Reply</button><span class="reactions"></span>';
  chat.append(div); // clicks work immediately via delegation
}, 5000);

4. When NOT to Delegate (and Performance Notes)

Delegation is a pattern, not a religion. Some events do not bubble at all — focus, blur, mouseenter, mouseleave, and load among them — so a delegated focus listener on a parent silently never fires. (Their bubbling cousins focusin/focusout do bubble and are the correct delegated substitutes.) Scroll and resize do not bubble usefully either; attach those where they belong.

stopPropagation() is delegation's enemy: if any child handler stops propagation, the event never reaches your delegated parent and the feature silently breaks. In codebases mixing both styles, this produces maddening “works until that component renders” bugs. Prefer checking conditions and returning early over stopping propagation, and treat stopPropagation as a code smell in delegated trees.

Performance-wise, delegation wins on listener count and setup time but adds a tiny per-event cost: every click anywhere in the container runs your handler's closest() checks. For containers with thousands of interactive children this is still far cheaper than thousands of listeners — but do not delegate mousemove at the document level with expensive logic inside; throttle it or scope the listener tightly.

// focus/blur DON'T bubble — use focusin/focusout for delegation
document.querySelector('#form').addEventListener('focusin', (e) => {
  e.target.closest('.field')?.classList.add('focused');
});
document.querySelector('#form').addEventListener('focusout', (e) => {
  e.target.closest('.field')?.classList.remove('focused');
});

// DANGER: this breaks every delegated parent above it
// someWidget.addEventListener('click', e => e.stopPropagation()); // avoid!
// PREFER: handle locally and let the event continue bubbling
someWidget.addEventListener('click', (e) => {
  if (e.target.closest('.internal')) { /* handle */ }
  // no stopPropagation: delegated parents still hear the event
});

5. Event Flow Quick Reference

Keep this table nearby until the event flow becomes instinct. The left column is the journey every event takes; the right columns are the tools you use at each stage.

If you remember one sentence from this guide, make it this: attach one listener high, identify the origin with target.closest(), and let bubbling do the delivery work. That sentence replaces hundreds of lines of listener-wiring code in a typical application.

6. Frequently Asked Questions (FAQs)

What is the difference between event.target and event.currentTarget?

event.target is the element where the event originated (e.g. the button actually clicked), while event.currentTarget is the element the listener is attached to. In a delegated handler on a list, target is the clicked row or button and currentTarget is the list itself.

Which events do not bubble?

focus, blur, mouseenter, mouseleave, load, scroll, and resize do not bubble (or not usefully). For delegated focus handling use their bubbling counterparts focusin and focusout; attach scroll/resize listeners directly to the relevant element or window.

Is event delegation always faster than individual listeners?

It uses far less memory and setup time — one listener instead of hundreds — which is a clear win for lists and dynamic content. The per-event cost is slightly higher (closest() checks on every event), so avoid document-level delegation for high-frequency events like mousemove without throttling.

How do I get data from the clicked child element?

Use event.target.closest('[data-id]') to find the relevant ancestor, then read its dataset: const id = row.dataset.id. Data attributes keep the markup declarative and the handler generic — no closures over loop variables needed.

Can I delegate focus and blur events?

Not directly — neither bubbles. Use focusin and focusout instead, which are the bubbling equivalents and work perfectly with delegation. This is the standard pattern for highlighting the active field wrapper in a form.
