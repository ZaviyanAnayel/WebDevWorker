1. The Four Principles: POUR

WCAG — the Web Content Accessibility Guidelines — organizes every requirement under four principles remembered by the acronym POUR: Perceivable, Operable, Understandable, and Robust. Perceivable means users can sense the content: text alternatives for images, captions for video, sufficient contrast. Operable means users can use the interface: full keyboard access, no time limits that lock people out, no seizure-triggering flashes.

Understandable means users can comprehend it: readable text, predictable navigation, and clear error messages that say how to fix a problem rather than just announcing failure. Robust means the code works with current and future assistive technology: valid HTML, proper semantics, and ARIA used correctly. When a design decision feels debatable, running it through POUR usually resolves the argument.

Conformance comes in three levels: A (the bare minimum — missing it means serious barriers), AA (the legal and practical standard most organizations target), and AAA (the strictest, aspirational for most sites). In 2026, WCAG 2.2 Level AA is the target referenced by the European Accessibility Act and most corporate policies — aim there.

AMinimum — removes the worst barriersEveryone (baseline)
AAStandard — usable by most people with disabilitiesLegal requirement in EU/US contexts

2. Color Contrast & Text Legibility

Color contrast is the most failed — and most fixable — accessibility criterion on the web. WCAG 2.2 AA requires a contrast ratio of at least 4.5:1 for normal text and 3:1 for large text (18pt+ or 14pt bold) and UI components. That trendy light-gray body text on a white background almost certainly fails; so do many brand-color buttons. Check every text/background pairing with a contrast analyzer, not your eyes — designers' monitors lie.

Contrast is necessary but not sufficient for legibility. Keep body text at 16px minimum, line height around 1.5, and line length under 80 characters. Never convey meaning by color alone — a red "error" field needs an icon and text explanation too, because color-blind users cannot distinguish your red from your green. Underlines should be reserved for links; removing them from links while relying on color alone fails the "use of color" criterion.

Dark mode and theming multiply the work: every theme needs its own contrast audit. Build the check into your design tokens — define text colors as pairs with their backgrounds and lint the ratios in CI, so no future "quick brand refresh" silently ships unreadable text.

/* Accessible focus + link styles: never rely on color alone */
a {
  color: #1d4ed8;
  text-decoration: underline;      /* shape, not just color */
  text-underline-offset: 3px;
}
a:hover, a:focus-visible {
  text-decoration-thickness: 2px;
}

/* Minimum legible body text */
body {
  font-size: 1rem;      /* 16px minimum */
  line-height: 1.6;
  max-width: 70ch;      /* comfortable line length */
}

3. Keyboard Navigation Essentials

Every interactive element must be reachable and operable by keyboard alone — Tab to move, Enter/Space to activate, Escape to dismiss. This is non-negotiable: screen reader users, people with motor impairments, and power users all depend on it. Start every audit by unplugging your mouse and completing your core user journey with the keyboard. You will find the traps within minutes.

The two technical pillars are logical focus order and visible focus. Focus order follows the DOM, so keep your source order sane — CSS that visually reorders content without changing the DOM creates a focus sequence that jumps confusingly around the page. Visible focus means never removing the outline without replacing it: :focus-visible lets you style a beautiful custom indicator that appears for keyboard users but not mouse clicks.

Complex widgets need keyboard contracts: modals must trap focus while open and return it to the trigger on close; dropdowns and menus should support arrow keys; skip links let keyboard users jump past repetitive navigation. Test the contract, not just the presence of tabindex.

<!-- Skip link: first thing in the body -->
<a href="#main-content" class="skip-link">Skip to main content</a>

<style>
.skip-link {
  position: absolute; left: -9999px; top: 0;
  background: #eab308; color: #0f172a;
  padding: 10px 16px; font-weight: 700; z-index: 100;
}
.skip-link:focus { left: 8px; top: 8px; }

/* Visible, attractive focus for keyboard users */
:focus-visible {
  outline: 3px solid #eab308;
  outline-offset: 2px;
  border-radius: 4px;
}
</style>
<main id="main-content">...</main>

4. Forms, Labels & Error Handling

Forms are where accessibility failures hurt most — a user who cannot complete checkout or signup is a lost customer, not just a failed audit. Every input needs a programmatically associated <label>: placeholders are not labels (they vanish on input, have poor contrast, and many screen readers skip them). Group related controls with <fieldset> and <legend>, and mark required fields with both text and aria-required or the required attribute.

Error handling separates adequate forms from good ones. Announce errors in text next to the field, link each message to its input with aria-describedby, move focus to the first error on submit, and summarize all errors at the top of the form. Never rely on color alone, and never clear the user's valid entries when one field fails — forcing re-entry punishes everyone and devastates users with cognitive or motor impairments.

Autocomplete attributes (autocomplete="email", tel, cc-number) are a WCAG 2.2 AA requirement for personal data fields and a genuine usability win: they let browsers and password managers fill forms correctly, reducing errors for every user.

<!-- Accessible form field: label, hint, error, autocomplete -->
<div class="field">
  <label for="email">Email address <span aria-hidden="true">*</span></label>
  <p id="email-hint" class="hint">We will only use this for order updates.</p>
  <input type="email" id="email" name="email" required
         autocomplete="email"
         aria-describedby="email-hint email-error" />
  <p id="email-error" class="error" role="alert" hidden>
    Enter a valid email address, like name@example.com.
  </p>
</div>

5. Images, Media & Motion

Every meaningful image needs alt text that conveys its content and function — not its appearance. A chart's alt should state the trend ("Bar chart: revenue doubled from 2024 to 2026"), not "bar chart image." Decorative images get empty alt (alt="") so screen readers skip them; a missing alt attribute is worse, because the reader then announces the filename.

Video and audio need text equivalents: captions for dialogue and meaningful sound (synchronized, not auto-generated gibberish), transcripts for podcasts and interviews, and audio description for important visual information in video. These are WCAG A/AA requirements, and they also serve users watching on mute — the majority on social feeds.

Finally, respect motion sensitivity. Vestibular disorders make parallax, autoplay video, and smooth-scroll animations physically nauseating for some users. Honor prefers-reduced-motion by disabling non-essential animation, and never auto-play anything with sound.

/* Respect users who need reduced motion */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

<!-- Informative image: alt conveys the content -->
<img src="/img/revenue-chart.png"
     alt="Bar chart showing revenue doubling from $1.2M in 2024 to $2.4M in 2026" />

<!-- Decorative image: hidden from assistive tech -->
<img src="/img/decorative-wave.svg" alt="" aria-hidden="true" />

6. Frequently Asked Questions (FAQs)

What does WCAG stand for and which version should I follow?

WCAG stands for Web Content Accessibility Guidelines. In 2026, target WCAG 2.2 Level AA — it is the version referenced by most current regulations including the European Accessibility Act. WCAG 3.0 is still a draft and not yet a compliance target.

Is web accessibility legally required?

In many jurisdictions, yes. The ADA in the US is increasingly applied to websites through lawsuits, the European Accessibility Act enforces requirements from June 2025, and many countries have equivalent laws. Beyond compliance, accessible sites reach more customers and rank better.

What is the fastest accessibility win for an existing site?

Fix color contrast and add missing form labels and alt text. These three issues account for the majority of automated accessibility failures, take hours rather than weeks to fix, and immediately help real users.

Do accessibility overlays work?

No — accessibility experts and disability advocates overwhelmingly oppose overlay widgets. They cannot fix underlying code problems, often interfere with the assistive technology users already rely on, and have been cited in lawsuits as evidence of awareness without remediation. Fix the source code instead.

How do I test accessibility beyond automated tools?

Automated tools catch roughly 30-40% of issues. Complement them with keyboard-only navigation testing, a screen reader pass (NVDA or VoiceOver), zooming to 200%, and — most valuably — usability testing with disabled users.
