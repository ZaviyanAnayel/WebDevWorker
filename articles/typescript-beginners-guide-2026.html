1. Why TypeScript? Static Types for JavaScript

TypeScript is JavaScript with a static type system layered on top: you annotate values with types, and the compiler checks them before your code runs. The classic payoff is catching the typo'd property or wrong argument type at write-time instead of discovering it in production via a Cannot read properties of undefined crash at 2 AM.

The second payoff is tooling. Because the compiler understands your types, editors offer precise autocompletion, safe rename-refactoring across files, and inline documentation. On a large codebase this is transformative — you can explore an unfamiliar module by hovering rather than reading every file, and refactors that would be terrifying in plain JavaScript become routine.

Crucially, TypeScript is a superset: every valid JavaScript program is a valid TypeScript program. You can rename .js files to .ts and adopt types incrementally, which is why teams migrate million-line codebases without a rewrite. Types are erased at compile time, so there is zero runtime overhead — TypeScript changes how you write code, never how it runs.

// Plain JavaScript: the bug hides until runtime
function getDiscount(price, rate) {
  return price - price * rate;
}
getDiscount("100", 0.1); // "100" - "100" * 0.1 → NaN, silently

// TypeScript: the bug is caught while you type
function getDiscount(price: number, rate: number): number {
  return price - price * rate;
}
getDiscount("100", 0.1);
// ❌ Argument of type 'string' is not assignable to parameter of type 'number'

2. Setting Up TypeScript: tsc and tsconfig.json

Install TypeScript as a dev dependency in your project: npm install -D typescript. This gives you the tsc compiler CLI. Running npx tsc --init generates a tsconfig.json with every option documented in comments — it looks intimidating, but you only need to understand a handful of settings to start.

The essential options: target (which JS version to emit — ES2020 or newer is a sane default), module (ESNext or NodeNext for bundlers/Node), strict: true (enables the full family of strict checks — turn this on from day one), outDir (where compiled JS goes), and include/exclude (which files to compile). noEmitOnError prevents emitting JS when type errors exist, which keeps broken builds from shipping.

For Node.js projects, set moduleResolution to Bundler (with Vite/webpack) or NodeNext (for pure Node ESM). If you are starting a frontend app, you rarely configure any of this by hand — Vite's npm create vite@latest -- --template react-ts and Next.js's built-in support generate a correct tsconfig.json for you.

# 1. Install the compiler (per project — never global, so versions stay pinned)
npm install -D typescript

# 2. Generate tsconfig.json with documented defaults
npx tsc --init

# 3. Type-check without emitting, or compile to ./dist
npx tsc --noEmit        # check only — great in CI
npx tsc                 # emits JS per tsconfig
npx tsc --watch         # recompile on every save
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,            // ← the single most important option
    "noEmitOnError": true,     // don't emit JS when type errors exist
    "outDir": "./dist",
    "rootDir": "./src",
    "skipLibCheck": true,      // skip type-checking node_modules .d.ts files
    "esModuleInterop": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}

3. Basic Types: Primitives, Arrays, and Unions

The core primitives mirror JavaScript: string, number, boolean, plus null, undefined, bigint, and symbol. TypeScript's number covers both integers and floats — there is no separate int type. Annotate with a colon: const name: string = "Ava". You will often omit annotations because of type inference: const age = 30 is already known to be number, and redundant annotations just add noise.

Arrays use string[] or Array<string> syntax; tuples fix the length and per-position types with [string, number] — handy for key-value pairs or coordinate pairs. Union types (string | number) express 'either/or' and are the foundation of flexible APIs; literal types ("success" | "error") restrict a value to an exact set of strings.

Two types deserve a warning label. any disables checking entirely and spreads like a virus through inference — treat it as technical debt. unknown is the safe alternative: it accepts anything but forces you to narrow the type before using it. New code should reach for unknown whenever the type is genuinely unknowable, such as parsed JSON or caught errors.

// Inference: no annotation needed, still fully typed
const greeting = "hello";       // string
const scores = [10, 20, 30];    // number[]

// Unions + literal types: precise, self-documenting APIs
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";
type ApiResult = { status: "ok"; data: string } | { status: "error"; message: string };

function handle(res: ApiResult) {
  if (res.status === "ok") {
    console.log(res.data);      // ✅ narrowed: data exists here
  } else {
    console.log(res.message);   // ✅ narrowed: message exists here
  }
}

// unknown forces you to check before use — any would not
function parse(input: string): unknown {
  return JSON.parse(input);
}

4. Functions, Objects, and Type Narrowing

Function annotations cover parameters and the return type: function add(a: number, b: number): number. Parameters are required by default; append ? for optional ones (name?: string) or provide defaults (retries = 3). Arrow functions annotate identically. A useful habit: annotate return types on exported functions — it documents the contract and catches accidental return-type drift during refactors.

Object shapes are described with interfaces (or type aliases — see our dedicated guide): interface User { id: number; name: string; email?: string }. The ? marks optional properties, and readonly prevents reassignment. Interfaces compose with extends, so shared fields live in one place.

Narrowing is how TypeScript refines a broad type to a specific one inside a branch. typeof checks narrow primitives, instanceof narrows class instances, truthiness checks eliminate null/undefined, and discriminated unions (a shared literal field like status) narrow object variants — as the ApiResult example above showed. Well-designed unions make narrowing feel automatic rather than ceremonial.

// Functions: annotated params + return type
function createUser(name: string, age?: number): { id: number; name: string } {
  return { id: Math.floor(Math.random() * 1e6), name };
}
const greet = (user: { name: string }): string => `Hello, ${user.name}!`;

// Interfaces: named object shapes
interface Product {
  readonly id: number;
  title: string;
  price: number;
  tags?: string[];
}

function formatPrice(p: Product): string {
  return `$${p.price.toFixed(2)}`;  // autocomplete knows every field
}

// Narrowing with typeof and truthiness
function printId(id: string | number | null): void {
  if (id == null) return;                 // null/undefined eliminated
  if (typeof id === "string") {
    console.log(id.toUpperCase());        // ✅ string here
  } else {
    console.log(id.toFixed(0));           // ✅ number here
  }
}

5. Compiling Your Code: From .ts to .js

Running npx tsc reads tsconfig.json and emits JavaScript into outDir, mirroring your source tree. Browsers and Node run only the emitted JS — TypeScript never executes directly. During development, npx tsc --watch recompiles on save, and most editors surface errors inline without any manual compile step at all.

strict: true deserves emphasis because it is the difference between TypeScript that helps and TypeScript that merely decorates. Strict mode enables strictNullChecks (no more silent undefined), noImplicitAny (every parameter needs a knowable type), and several other checks. Code written under strict mode has measurably fewer null-reference bugs; code written without it often just moves the same bugs around.

Two final workflow tips. First, add "typecheck": "tsc --noEmit" to your npm scripts and run it in CI — it catches type errors without producing build artifacts. Second, when adopting TypeScript in an existing JavaScript project, enable allowJs and rename files to .ts one at a time, starting with the modules that cause the most bugs. Incremental adoption beats big-bang rewrites every time.

{
  "scripts": {
    "typecheck": "tsc --noEmit",   // CI-friendly: checks types, emits nothing
    "build": "tsc",                // emits ./dist per tsconfig
    "dev": "tsc --watch"           // recompile on save during development
  }
}

// Gradual migration: allowJs lets .js and .ts coexist
// tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "allowJs": true,
    "checkJs": false,      // flip to true later to type-check the old JS too
    "outDir": "./dist"
  },
  "include": ["src/**/*"]
}

6. Frequently Asked Questions (FAQs)

Do browsers run TypeScript directly?

No. Browsers only execute JavaScript, so TypeScript must be compiled to JavaScript with tsc (or a bundler like Vite/esbuild) before it runs. All type annotations are erased during compilation, which is why TypeScript adds zero runtime overhead.

Will TypeScript make my app run faster?

No — and it isn't meant to. TypeScript is a development-time tool: it catches bugs, improves autocompletion, and makes refactoring safer. The emitted JavaScript runs exactly as fast as hand-written JavaScript.

Should I enable strict mode as a beginner?

Yes, absolutely — and especially as a beginner. strict: true turns on the checks (like strictNullChecks and noImplicitAny) that catch the most bugs. Learning with strict mode on teaches you habits that scale; learning without it teaches workarounds you'll have to unlearn.

What is the difference between .ts and .tsx files?

Use .ts for pure TypeScript and .tsx for files containing JSX (React components). The .tsx extension tells the compiler to parse angle brackets as JSX rather than as type assertions, which avoids ambiguity.

Can I convert an existing JavaScript project to TypeScript gradually?

Yes — that's one of TypeScript's strengths. Enable allowJs in tsconfig.json, rename files to .ts one module at a time (starting with the buggiest ones), and fix the errors the compiler surfaces. Your project keeps working at every step.
