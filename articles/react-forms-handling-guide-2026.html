1. Controlled Components: React Owns the Input

In a controlled component, React state is the single source of truth: the input's value comes from state, and every keystroke updates state via onChange. This gives you live access to every value — for instant validation, conditional UI, character counts, and formatted display — at the cost of a re-render per keystroke:

import { useState } from 'react';

function SignupForm() {
  const [values, setValues] = useState({ email: '', password: '' });
  const [touched, setTouched] = useState({});

  const set = (name) => (e) =>
    setValues((v) => ({ ...v, [name]: e.target.value }));

  const emailError =
    touched.email && !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(values.email)
      ? 'Enter a valid email address'
      : '';

  return (
    <form onSubmit={(e) => { e.preventDefault(); submit(values); }}>
      <label>
        Email
        <input
          type="email"
          value={values.email}          {/* React owns the value */}
          onChange={set('email')}        {/* every keystroke updates state */}
          onBlur={() => setTouched((t) => ({ ...t, email: true }))}
          aria-invalid={!!emailError}
          aria-describedby="email-error"
        />
      </label>
      {emailError && <p id="email-error" role="alert">{emailError}</p>}
      <button type="submit" disabled={!!emailError}>Sign up</button>
    </form>
  );
}

Controlled inputs shine when the UI must react to input as it happens: live validation messages, password-strength meters, "confirm password matches" checks, and inputs that format themselves (credit-card spacing, phone masks). The re-render cost is negligible for typical forms — React handles per-keystroke renders of small trees effortlessly.

The classic beginner bug is the read-only input: setting value without onChange locks the field (React warns you). If you truly want an uneditable display value, that's what readOnly or plain text is for — don't fake it with a controlled input missing its handler.

2. Uncontrolled Components and Refs

Uncontrolled components let the DOM own the value. You set an initial value with defaultValue and read the current value from a ref only when you need it — typically on submit. No state, no re-renders per keystroke:

import { useRef } from 'react';

function QuickSearch() {
  const inputRef = useRef(null);

  const onSubmit = (e) => {
    e.preventDefault();
    // Read the DOM value once, at submit time — zero renders while typing
    const query = inputRef.current.value.trim();
    if (query) runSearch(query);
  };

  return (
    <form onSubmit={onSubmit}>
      <input ref={inputRef} defaultValue="" placeholder="Search docs…" />
      <button type="submit">Search</button>
      {/* Reset without state: the DOM API still works */}
      <button type="button" onClick={() => inputRef.current.form.reset()}>
        Clear
      </button>
    </form>
  );
}

Uncontrolled inputs fit simple cases: search boxes, one-off dialogs, and forms where you only care about values at submit time. They're also the pragmatic choice for integrating non-React widgets (rich text editors, date pickers) that manage their own DOM — fight the widget and you lose.

The trade-off is visibility: with no state, you can't do live validation, can't conditionally disable the submit button, and can't easily transform input as it's typed. The rule of thumb — controlled when the UI reacts to input, uncontrolled when only the submit handler needs it — resolves nearly every case. And you can mix both styles in the same form without guilt.

3. Validation Strategies in React

React doesn't change validation fundamentals — the Constraint Validation API from plain HTML works identically — but state gives you finer control over when and how errors appear. The professional rhythm: track touched per field, validate on blur and submit, and show errors only for touched fields or after a submit attempt:

const validators = {
  email: (v) =>
    !v ? 'Email is required'
    : !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(v) ? 'Enter a valid email address' : '',
  password: (v) =>
    !v ? 'Password is required'
    : v.length < 12 ? 'Use at least 12 characters' : '',
  confirm: (v, all) =>
    v !== all.password ? 'Passwords do not match' : '',
};

function useFormValidation(initial) {
  const [values, setValues] = useState(initial);
  const [touched, setTouched] = useState({});
  const [submitted, setSubmitted] = useState(false);

  const errors = Object.fromEntries(
    Object.entries(validators).map(([k, fn]) => [k, fn(values[k], values)])
  );
  const showError = (k) => (touched[k] || submitted) ? errors[k] : '';
  const isValid = Object.values(errors).every((e) => !e);

  return { values, setValues, setTouched, setSubmitted, showError, isValid };
}

Keep validators as pure functions ((value, allValues) => errorMessage | '') — they're trivially unit-testable without rendering anything, and cross-field rules (password confirmation) fall out naturally via the allValues argument. Async validators (username availability) need debounce plus a stale-response guard, exactly like the vanilla pattern.

For accessibility, wire the same attributes as plain HTML: aria-invalid, aria-describedby pointing at the error element, and role="alert" on messages. On failed submit, move focus to the first invalid field — React's declarative rendering makes it easy to forget this imperative nicety, and keyboard users will notice.

4. Form Libraries: React Hook Form and Friends

Hand-rolled form state works until forms get complex — dynamic field arrays, nested objects, async validation, and dirty tracking reinvent the same wheels. React Hook Form (RHF) is the dominant library because of one architectural choice: it keeps inputs uncontrolled by default and subscribes surgically, so typing doesn't re-render your form:

import { useForm } from 'react-hook-form';

function CheckoutForm() {
  const {
    register, handleSubmit, formState: { errors, isSubmitting },
  } = useForm({ defaultValues: { email: '', zip: '' } });

  const onSubmit = async (data) => {
    await api.checkout(data); // isSubmitting disables the button meanwhile
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input
        {...register('email', {
          required: 'Email is required',
          pattern: { value: /^[^@\s]+@[^@\s]+\.[^@\s]+$/, message: 'Invalid email' },
        })}
        aria-invalid={!!errors.email}
      />
      {errors.email && <p role="alert">{errors.email.message}</p>}

      <input
        {...register('zip', {
          required: 'ZIP is required',
          validate: (v) => /^\d{5}(-\d{4})?$/.test(v) || 'Enter a valid ZIP code',
        })}
      />
      {errors.zip && <p role="alert">{errors.zip.message}</p>}

      <button disabled={isSubmitting}>
        {isSubmitting ? 'Placing order…' : 'Place order'}
      </button>
    </form>
  );
}

For schema-driven validation, pair it with Zod via @hookform/resolvers — one schema validates both client and server, which is the real endgame for form correctness.

5. Real-World Patterns: Multi-Step Forms and Submission States

Multi-step forms share one state object across steps, with each step validating only its own fields. Keep the data in the wizard parent (or RHF's useFormContext), validate per-step on "Next," and run full validation only on final submit. Persist drafts to localStorage so a refresh doesn't nuke twenty minutes of work — users forgive many things, but not that.

Submission states deserve explicit design: idle → submitting → success | error. Disable the submit button while submitting (double-submit is a classic duplicate-charge bug), show inline progress, and on error keep every value intact while focusing the error summary. On success, decide deliberately: reset the form, redirect, or show confirmation — never leave the user staring at a filled form wondering if it worked.

File uploads need uncontrolled inputs (input type="file" is read-only by design) — read e.target.files, validate size and type client-side, and upload with FormData plus progress events. And the standing rule from plain HTML still applies in React: server-side validation is mandatory. Client checks are UX; the server is the security boundary. Share the Zod schema between both and the two layers can never drift apart.

6. Frequently Asked Questions (FAQs)

Should I use controlled or uncontrolled components?

Use controlled components when the UI must react to input as it happens — live validation, formatting, conditional buttons. Use uncontrolled components with refs when only the submit handler needs the values, like simple search boxes. Mixing both styles in one form is perfectly fine.

Do I need a form library like React Hook Form?

For simple forms under about five fields, hand-rolled controlled state is fine. Reach for React Hook Form when you need dynamic field arrays, complex validation, dirty tracking, or performance with many fields — it avoids re-renders by keeping inputs uncontrolled under the hood.

How do I handle file inputs in React?

File inputs must stay uncontrolled — their value is read-only. Read selected files from e.target.files or a ref, validate size and type in JavaScript, and upload via FormData. Never try to set a file input's value programmatically; browsers block it for security.

How do I validate forms without re-rendering on every keystroke?

Track touched state and validate on blur and submit, showing errors only for touched fields. Or use React Hook Form, which subscribes to individual fields instead of re-rendering the whole form. Debouncing async validators like username checks also cuts noise.

Why does React Hook Form re-render less than hand-rolled forms?

It registers inputs as uncontrolled and reads values from refs, subscribing components only to the specific form state they use. A hand-rolled controlled form stores every keystroke in React state, re-rendering the component tree on each change.
