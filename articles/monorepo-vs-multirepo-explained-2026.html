1. Monorepo vs Multirepo: The Core Definitions

A monorepo stores many projects — apps, libraries, configs, infrastructure — in a single version-controlled repository. A multirepo (sometimes called polyrepo) gives each project its own repository. The distinction sounds trivial, but it ripples through every workflow: how you share code, run CI, version releases, and onboard engineers.

Monorepos shine at atomic changes: one commit can update a shared UI library and all three apps consuming it, with CI verifying everything together. Google, Meta, and Microsoft run some of the world's largest monorepos for exactly this reason. Multirepos shine at independence: each team owns its release cadence, access control, and CI pipeline without coordinating with anyone else — the model behind most microservice organizations.

The honest trade-off: monorepos centralize complexity in tooling (you need smart builds so a docs typo does not rebuild the world), while multirepos distribute complexity across teams (you need versioning discipline so library updates actually propagate). Neither is free — you are choosing which complexity you would rather manage.

2. Turborepo: Speed Through Smart Caching

Turborepo, now part of Vercel, is the minimalist's monorepo orchestrator. It does not impose project structure or generators; it layers fast task running on top of standard npm/pnpm/yarn workspaces. Its killer feature is caching: Turborepo hashes task inputs (source files, dependencies, env vars) and skips work whose outputs are already cached — locally or shared across the team via Remote Caching.

// turbo.json — define the task graph once
{
  "$schema": "https://turborepo.dev/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "package.json", "tsconfig.json"],
      "outputs": ["dist/**", ".next/**"]
    },
    "test": { "dependsOn": ["build"], "outputs": [] },
    "lint": { "outputs": [] },
    "dev": { "cache": false, "persistent": true }
  }
}

The dependsOn: ["^build"] line is the magic: the ^ means “build my dependencies first,” so Turborepo topologically sorts packages and parallelizes everything else. A typical JavaScript monorepo layout pairs this with workspaces:

// package.json at the repo root
{
  "name": "acme-monorepo",
  "private": true,
  "workspaces": ["apps/*", "packages/*"],
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "test": "turbo run test"
  }
}

// apps/web/package.json consumes the shared UI package
{
  "name": "@acme/web",
  "dependencies": { "@acme/ui": "workspace:*", "@acme/config": "workspace:*" }
}

With Remote Caching enabled, a developer pulling main can skip rebuilding packages a teammate already built — CI uploads artifacts, everyone else downloads them. Teams routinely report 70–90% reductions in CI minutes after adopting it. Turborepo is the right pick when you want monorepo speed with minimal new concepts: if you know workspaces, you are nearly done.

3. Nx: The Enterprise Monorepo Toolkit

Nx takes the opposite philosophy: a full toolkit with opinions about everything. Beyond task running and caching, Nx provides a project graph (a visual map of every dependency between your apps and libraries), code generators (nx g @nx/react:component), automated migrations when dependencies update, and affected commands that run tasks only on projects touched by your change.

// project.json — per-project targets with inputs/outputs
{
  "name": "web",
  "sourceRoot": "apps/web/src",
  "targets": {
    "build": {
      "executor": "@nx/vite:build",
      "outputs": ["{options.outputPath}"],
      "dependsOn": [{ "target": "build", "projects": "dependencies" }]
    },
    "test": {
      "executor": "@nx/vite:test",
      "dependsOn": [{ "target": "build", "projects": "dependencies" }]
    }
  }
}

The affected workflow is where Nx earns its keep on large repos. Instead of testing everything on every PR, CI runs nx affected -t test --base=origin/main and only touches projects downstream of changed files — a docs edit triggers nothing, a core library change triggers its consumers. Combined with Nx Cloud's distributed task execution, thousand-project repos stay fast.

# CI: only build/test what the PR actually affected
- run: npx nx affected -t lint,test,build --base=origin/main --head=HEAD

# Visualize the dependency graph before a refactor
- run: npx nx graph --affected --base=origin/main

Nx also enforces architectural boundaries: you can declare that the billing domain may not import from marketing, and lint fails the PR that violates it. Choose Nx when you need governance, generators, and polyglot support (it handles Go, Rust, and Python alongside JS) — at the cost of learning Nx's concepts and configuration surface.

4. Sharing Code, Versioning and CI Strategies

The daily reality of a monorepo is shared packages. Keep them small and single-purpose (@acme/ui, @acme/auth, @acme/eslint-config) with clear public APIs, and resist the gravity well of a @acme/utils junk drawer. Internal packages are consumed via workspace:* protocol so versions stay in lockstep during development, then published with real versions when external consumers exist.

CapabilityTurborepoNx
Task orchestrationTask graph from turbo.jsonProject graph + per-project targets
CachingLocal + Remote Caching, content-hashedLocal + Nx Cloud, plus distributed execution
Affected commandsVia --filter=[HEAD^1]First-class nx affected
Code generatorsNo (bring your own)Built-in generators for apps, libs, components
Enforced boundariesNoYes, via lint rules on the project graph
Learning curveLow — workspaces plus one configMedium — new concepts and config surface

For versioning published packages, Changesets is the community standard: each PR includes a markdown file declaring patch/minor/major bumps, and a release workflow consumes them into version bumps and changelogs. In CI, always pair affected-analysis with remote caching — affected narrows what runs, caching skips re-running what already ran. Together they keep monorepo CI times flat as the repo grows.

5. Which Should You Choose?

Choose a monorepo when your projects share significant code, you want atomic cross-project changes, and you can invest in build tooling. It fits product companies where the web app, mobile app, and admin panel evolve together. Choose a multirepo when teams need true independence — separate deploy cadences, strict access boundaries, or wildly different tech stacks — and you accept versioning overhead as the price.

Between Turborepo and Nx, the heuristic is simple: pick Turborepo if your team is JavaScript-focused and wants the smallest possible layer over workspaces; pick Nx if you need generators, enforced module boundaries, affected analysis out of the box, or polyglot projects. Both support remote caching, both scale past hundreds of packages, and both let you start small — you can adopt either incrementally inside an existing repo.

A practical migration path: start by extracting one shared package (UI components or config) into workspaces, add Turborepo or Nx for task running, enable remote caching in CI, then split further as duplication appears. Do not begin with a big-bang repo merge — earn the monorepo by proving the tooling on a slice first.

6. Frequently Asked Questions (FAQs)

What is the main difference between a monorepo and a multirepo?

A monorepo keeps multiple projects in one repository so changes across projects happen atomically in a single commit. A multirepo gives each project its own repository, maximizing team independence at the cost of cross-project coordination.

Is Turborepo only for JavaScript projects?

Primarily, yes. Turborepo is designed around JS package managers and workspaces. If your monorepo spans Go, Rust, or Python services, Nx or Bazel-style tools with polyglot support are a better fit.

How does Turborepo remote caching actually save CI time?

Turborepo hashes each task's inputs and reuses previously computed outputs from a shared cache. If CI already built a package with identical inputs, your run downloads the artifacts instead of rebuilding — cutting CI minutes by 70 to 90 percent on typical repos.

What does nx affected do?

It compares your branch against a base (usually main), determines which projects are affected by the changed files using the project dependency graph, and runs tasks only on those projects — so a docs edit triggers no builds.

Can I migrate from multirepo to monorepo gradually?

Yes. Extract one shared package into workspaces first, add Turborepo or Nx for task orchestration, enable remote caching, and merge repositories incrementally. A gradual migration de-risks the tooling before you commit fully.
