1. Why Pagination Is a Design Decision

Pagination exists because returning "everything" does not scale: a 2-million-row table serialized as JSON will exhaust memory, time out, and crush the client trying to parse it. But pagination is more than a performance hack — it is a contract about how clients traverse your data, and a bad contract produces missing records, duplicates, and integrations that silently corrupt themselves.

The core tension is between stability and simplicity. Data changes while clients paginate: rows are inserted, deleted, and reordered. A pagination strategy must define what happens then — does the client see the new row, miss a row, or see one twice? Different strategies answer differently, and the right answer depends on whether your clients are building infinite-scroll feeds, exporting datasets, or syncing state.

Whatever you choose, be consistent across your API, document the exact semantics, and never change pagination behavior in a minor version. Clients encode assumptions about page traversal deep in their sync logic, and a silent change breaks them in ways that surface weeks later as "missing data" bugs.

2. Offset Pagination: Simple and Fragile

Offset pagination (?page=3&per_page=50, or LIMIT 50 OFFSET 100) is the most familiar approach and the right default for admin panels and search results where users jump to arbitrary pages. It is simple to implement and easy to reason about:

-- Offset pagination: page 3 of 50-per-page (page is 1-indexed)
SELECT id, name, created_at
FROM products
ORDER BY created_at DESC, id DESC
LIMIT 50 OFFSET 100;

-- API: GET /api/v1/products?page=3&per_page=50

Its weaknesses are real and worth understanding. First, performance: the database still scans and discards the offset rows, so page 10,000 is dramatically slower than page 1 — deep pagination is effectively a denial-of-service vector on large tables. Second, instability: if a row is inserted or deleted ahead of the client's position, every subsequent page shifts, causing skipped or duplicated records. Offset pagination assumes a frozen dataset, and production datasets are never frozen.

Mitigate where you can: cap the maximum page depth (few legitimate use cases need page 500), enforce a stable sort order (always include a unique tiebreaker like the primary key, or rows with equal sort values shuffle randomly between pages), and set a sane maximum per_page. For user-facing page navigation these trade-offs are fine; for data export and sync, they are not — which is where cursors take over.

3. Cursor and Keyset Pagination

Cursor-based (keyset) pagination replaces page numbers with an opaque pointer to a position in a stable ordering — typically "everything after this ID" or "everything after this timestamp+ID pair". The client passes the cursor from the previous response, and the query seeks directly to that position:

-- Keyset pagination: rows after the last seen (created_at, id) pair
SELECT id, name, created_at
FROM products
WHERE (created_at, id) < ('2026-10-10 14:22:01', 88412)
ORDER BY created_at DESC, id DESC
LIMIT 50;

-- API: GET /api/v1/products?limit=50&cursor=eyJjcmVhdGVkX2F0IjoiMjAyNi0xMC0xMFQxNDoyMjowMSIsImlkIjo4ODQxMn0
-- (cursor is the base64-encoded position; clients treat it as opaque)

This is O(1) regardless of depth — the database seeks via the index instead of scanning discarded rows — and it is stable against inserts and deletes elsewhere in the dataset, because position is defined by values, not by row counts. New rows inserted "ahead" of the cursor simply appear on the next fetch or not at all, depending on direction, but existing pages never shift.

The trade-offs: clients cannot jump to page 47 (cursors are sequential), and the sort order must be immutable and unique — a composite of timestamp plus primary key is the standard choice. Make the cursor opaque (base64-encoded JSON) even if it is technically decodable; opacity lets you change the internal format later without breaking clients that learned to construct cursors themselves.

4. Designing the Response: Metadata and Links

A pagination response should be self-describing. Include the data, the cursor or page info for the next fetch, and enough metadata for clients to build UI and detect the end of the dataset. Here is a clean envelope that works for both strategies:

{
  "data": [ { "id": 88413, "name": "Widget", "...": "..." } ],
  "pagination": {
    "limit": 50,
    "next_cursor": "eyJjcmVhdGVkX2F0Ijoi...",
    "prev_cursor": "eyJjcmVhdGVkX2F0Ijoi...",
    "has_more": true
  }
}

// Offset-style alternative for page-navigation UIs:
{
  "data": [ "..." ],
  "pagination": { "page": 3, "per_page": 50, "total": 12480, "total_pages": 250 }
}

Design notes that prevent future pain: has_more is more robust than comparing returned count to the limit (they diverge when filters apply); total counts are expensive on large tables — provide them only where the UI genuinely needs "page 3 of 250", and consider omitting them on cursor endpoints; and support the standard Link response header (rel="next") as a complement for hypermedia-friendly clients. Whatever envelope you choose, document it once and reuse it identically on every paginated endpoint.

5. Choosing the Right Strategy for Your API

Choose by how clients consume the data, not by what is easiest to write:

StrategyJump to Page NDeep-Pagination PerformanceStable Under WritesBest For
Offset (page/per_page)YesDegrades (OFFSET scans)No — rows shiftAdmin tables, search UIs
Cursor / keysetNo (sequential only)Constant time via indexYesFeeds, sync, exports, infinite scroll
Seek by ID rangeNoConstant timeMostlySimple append-only logs

Practical guidance: use offset for anything with a "go to page" UI and bounded result sets; use cursor pagination for feeds, mobile infinite scroll, data export, and any endpoint where clients sync state over time; and consider offering both on different endpoints rather than forcing one strategy where it fits poorly. Stripe-style APIs famously use cursor pagination everywhere, while admin dashboards everywhere use offset — both are correct in context.

Two final rules. First, always enforce a maximum page size (50–100 is typical) and a default when the client omits it — an unbounded ?per_page=1000000 is a self-inflicted outage. Second, log and alert on deep-offset queries in production; they are the canary for scrapers and runaway integrations, and a cursor-based alternative usually exists for the legitimate use case behind them.

6. Frequently Asked Questions (FAQs)

What is the difference between offset and cursor pagination?

Offset pagination skips N rows (LIMIT 50 OFFSET 100) and supports jumping to any page, but slows down on deep pages and shifts when data changes. Cursor pagination seeks from the last-seen position using an opaque token, stays fast at any depth, and is stable under inserts and deletes — but only supports sequential traversal.

Why is deep offset pagination slow?

Because the database must scan and discard every row before the offset, even though it returns only the page. Page 10,000 of a large table can be thousands of times slower than page 1. Cursor pagination avoids this entirely by seeking directly to the indexed position instead of counting rows.

Should pagination cursors be opaque?

Yes. Base64-encode the cursor payload and document that clients must treat it as an opaque string. Opacity prevents clients from constructing or parsing cursors themselves, which lets you change the internal format — adding fields, switching encodings — without breaking every integration.

How do I paginate consistently when rows are being inserted?

Use cursor (keyset) pagination over a stable, unique ordering such as (created_at, id). Position is defined by values rather than row counts, so inserts and deletes elsewhere in the dataset do not shift the client's pages. Offset pagination cannot guarantee this on a changing dataset.

Should my API return total counts with paginated responses?

Only where the UI genuinely needs them, like page-number navigation showing 'page 3 of 250'. COUNT queries are expensive on large tables, so omit totals on cursor-based endpoints and high-traffic feeds. A has_more flag is cheaper and sufficient for infinite scroll and sync use cases.
