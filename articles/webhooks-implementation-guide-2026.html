1. Webhooks vs Polling vs WebSockets

A webhook is an HTTP callback: instead of clients repeatedly asking "anything new?" (polling), your server pushes an HTTP POST to a URL the client registered when an event occurs. A payment succeeds, a build finishes, a row changes — your system fires a signed JSON payload at the subscriber's endpoint within seconds. It is the standard pattern for event notifications between services precisely because it is simple, decoupled, and near-real-time.

Polling still wins when events are rare and latency does not matter, or when the subscriber cannot receive inbound connections (behind strict firewalls, or a mobile app). WebSockets win for bidirectional, high-frequency streams like live dashboards or chat. Webhooks win for discrete business events between servers: payment status changes, CI results, CRM updates. Choose by the shape of the data, not by fashion.

PatternDirectionLatencyBest For
WebhooksServer pushes to client URLSecondsDiscrete business events (payments, deploys, alerts)
PollingClient asks repeatedlyMinutes (typical)Rare events; clients behind firewalls
WebSocketsBidirectional streamMillisecondsLive dashboards, chat, gaming
Server-Sent EventsServer streams to browserSecondsOne-way live updates to web UIs

One more consideration: webhooks invert the trust direction. With polling, your server only answers; with webhooks, your server makes outbound requests to third-party URLs — which means you must validate those URLs (no internal addresses, to prevent SSRF) and sign every payload so receivers can verify it really came from you.

2. Sending Webhooks from Your Application

Sending webhooks well is mostly about the envelope: a stable event schema, a unique event ID, a timestamp, and an HMAC signature. Here is a sender implementation in Node.js:

const crypto = require('crypto');

async function sendWebhook(url, eventType, data, secret) {
  const payload = JSON.stringify({
    id: crypto.randomUUID(),          // unique per delivery attempt batch
    type: eventType,                   // e.g. "payment.succeeded"
    created_at: new Date().toISOString(),
    data,
  });
  const signature = crypto
    .createHmac('sha256', secret)
    .update(payload)
    .digest('hex');

  const res = await fetch(url, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-Webhook-Signature': `sha256=${signature}`,
      'X-Webhook-Event': eventType,
      'X-Webhook-Delivery': crypto.randomUUID(), // unique per attempt
    },
    body: payload,
    signal: AbortSignal.timeout(10000), // never hang forever on a dead URL
  });
  if (!res.ok) throw new Error(`Webhook failed: ${res.status}`);
  return res;
}

Design decisions that pay off: version your event types (payment.succeeded.v2) so schema changes do not break subscribers; never delete or rename fields without a version bump; include the event ID so receivers can deduplicate; and store every delivery attempt with its response so you have an audit trail when a subscriber says "we never got it". Send from a job queue, never inline in the request that triggered the event — a slow subscriber must never slow down your checkout.

3. Building a Receiver Endpoint

The receiver's job is to accept fast, verify, and process asynchronously. Acknowledge receipt immediately (HTTP 200) and do the real work in a background job — webhook senders retry aggressively on timeouts, and slow endpoints cause duplicate deliveries:

// Express receiver: verify, acknowledge fast, process async
app.post('/webhooks/payments', express.raw({ type: 'application/json' }),
  async (req, res) => {
    const signature = req.headers['x-webhook-signature'];
    if (!verifySignature(req.body, signature, process.env.WEBHOOK_SECRET)) {
      return res.status(401).send('bad signature');
    }
    const event = JSON.parse(req.body.toString());
    await jobQueue.add('process-webhook', event); // async processing
    res.status(200).send('ok'); // acknowledge BEFORE heavy work
  }
);

Note express.raw(): signature verification must run against the exact raw bytes the sender signed, so parse the body yourself after verifying — middleware that parses JSON first will normalize whitespace and break the signature. Also enforce a timestamp tolerance (reject events older than five minutes) to narrow the replay window, and always use HTTPS for receiver endpoints so signatures and payloads are not exposed in transit.

4. Verifying Signatures with HMAC

HMAC signature verification is what stops attackers from forging events to your endpoint. The sender and receiver share a secret; the sender signs the raw payload bytes; the receiver recomputes the signature and compares. Anyone without the secret cannot produce a valid signature, so forged "payment succeeded" events get rejected:

const crypto = require('crypto');

function verifySignature(rawBody, header, secret) {
  if (!header || !header.startsWith('sha256=')) return false;
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(rawBody) // raw bytes, exactly as received
    .digest('hex');
  // timingSafeEqual prevents timing attacks on the comparison
  const a = Buffer.from(header), b = Buffer.from(expected);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

Operational rules for secrets: generate a unique secret per subscriber (so rotating one does not affect others), allow each subscriber to rotate theirs from your dashboard, and support a grace period where two secrets are valid during rotation. Log verification failures without logging the secret itself, and alert on sudden spikes — they often indicate a misconfigured subscriber rather than an attack, but either way you want to know.

5. Retries, Idempotency, and Operational Reliability

Networks fail, so webhooks must be delivered with at-least-once semantics: retry failed deliveries with exponential backoff (e.g. after 1 minute, 5 minutes, 30 minutes, a few hours), cap the retry window (24–72 hours is typical), and then dead-letter the event for manual inspection. Tell subscribers your retry policy up front so they can design for duplicates — because retries plus at-least-once delivery means duplicates are guaranteed, not hypothetical.

Idempotency is the receiver-side answer to duplicates. Key your processing on the event ID: record processed event IDs (with a TTL) and skip any event you have already handled. For state-changing effects like "credit the account", also make the effect itself idempotent — a database upsert keyed on the event ID, or a check-then-act inside a transaction:

// Idempotent receiver: the event ID is the dedupe key
async function handleEvent(event) {
  const seen = await db.processedEvents.findUnique({ where: { id: event.id } });
  if (seen) return; // duplicate delivery — already handled, ack quietly

  await db.$transaction(async (tx) => {
    await tx.orders.update({ where: { id: event.data.orderId },
                             data: { status: 'paid' } });
    await tx.processedEvents.create({ data: { id: event.id } });
  });
}

Finally, give subscribers observability: a dashboard showing recent deliveries, response codes, and retry state, plus a "replay event" button. When something goes wrong at 2 AM, the difference between a five-minute self-service fix and a support ticket is whether the subscriber can see and redrive their own events.

6. Frequently Asked Questions (FAQs)

What is the difference between a webhook and an API?

An API is request-response: the client asks, the server answers. A webhook reverses this — your server sends an HTTP POST to the client's URL when an event happens, so the client learns about it immediately without polling. Webhooks are for event notifications; APIs are for on-demand data access. Most integrations use both.

How do I secure my webhook receiver endpoint?

Verify the HMAC signature of every payload against the raw request body using a per-subscriber secret, enforce HTTPS, reject events with stale timestamps to limit replay, and return 401 for bad signatures. Never trust a webhook payload that fails signature verification — treat it as hostile input.

Why am I receiving duplicate webhook events?

Because webhook delivery is at-least-once: senders retry on timeouts and network errors, and a slow receiver can trigger a retry even though the first attempt succeeded. Design receivers to be idempotent by deduplicating on the event ID, and acknowledge (HTTP 200) before doing slow work.

Should webhooks be sent synchronously in the request handler?

No. Enqueue webhook deliveries in a background job queue and send them asynchronously with retries. Sending inline couples your response time to every subscriber's endpoint speed — one slow or dead subscriber would delay your own requests and eventually exhaust your workers.

How should I version webhook event payloads?

Version the event type (payment.succeeded.v2), never remove or rename fields without a version bump, and keep old versions working for a documented deprecation period. Include the event ID and timestamp in every version so receivers can build version-agnostic deduplication and ordering logic.
