1. Why Print Stylesheets Still Matter in 2026

Nobody prints homepages anymore, but the web still runs on printed and PDF output: invoices, boarding passes, medical forms, shipping labels, restaurant receipts, and financial reports. Most of these are generated from HTML and turned into PDFs via the browser's print pipeline, which means @media print is quietly one of the most business-critical CSS features in existence.

A print stylesheet is simply a set of rules that apply only when the page is printed or saved as PDF. Its job is translation: strip the app chrome (navigation, sidebars, ads, footers, cookie banners), flatten the layout into a single readable column, force dark-on-light colors, and control exactly where pages break. Without it, users get a shrunk screenshot of your app — with it, they get a professional document.

The good news is that print CSS is small. A solid print stylesheet is usually 40–80 lines, lives in the same CSS file as everything else, and needs no build tooling. The patterns below cover nearly every real-world case, from a one-page receipt to a fifty-page generated report.

/* The skeleton every print stylesheet starts from */
@media print {
  /* Hide everything that is not the document itself */
  header, nav, aside, footer,
  .ads, .cookie-banner, .no-print {
    display: none !important;
  }

  /* Force readable, ink-friendly colors */
  body {
    background: #fff !important;
    color: #000;
    font-size: 12pt;
  }
}

2. @media print Fundamentals

The first rule of print CSS: hide ruthlessly. Navigation menus, hero images, social buttons, comment sections, and sticky headers all waste paper and confuse the reader. Give printable regions a class like .print-area and hide everything else, or invert the approach with .no-print on chrome elements. Using !important is acceptable here — print overrides must beat screen styles reliably.

Second, reset the visual language for paper. Screens are backlit; paper is not. Force black text on white, remove text-shadows and translucent overlays, and expand shortened links so the URL is visible: a[href]::after { content: " (" attr(href) ")"; } turns “Read more” into “Read more (https://…)”. Skip this for anchor links and javascript: URLs with a :not() filter so internal page jumps do not print garbage.

Third, think in physical units. Pixels are meaningless on paper; points (pt) and millimeters (mm) are the native units of print. Set body type around 11–12pt, keep line-height generous (1.5+), and constrain the content width — a 1200px app layout squeezed onto A4 becomes unreadably small, so let the print layout flow at 100% width in a single column.

@media print {
  /* Make link destinations visible on paper */
  a[href^="http"]::after {
    content: " (" attr(href) ")";
    font-size: 0.85em;
    word-break: break-all;
  }
  /* ...but not for in-page anchors */
  a[href^="#"]::after { content: ""; }

  main, .print-area {
    width: 100% !important;
    max-width: none !important;
    margin: 0 !important;
    padding: 0 !important;
  }
}

3. Controlling Page Breaks

Bad page breaks are what separate amateur print output from professional documents: a table split mid-row, a heading stranded at the bottom of a page with its paragraph on the next, a chart orphaned from its caption. CSS gives you precise control with the break-* properties (and their legacy page-break-* aliases, which older engines still need).

The workhorse is break-inside: avoid, applied to cards, table rows, figures, and any component that must stay together. Use break-before: page on major sections (each invoice, each chapter) to force a fresh page, and break-after: avoid on headings so a heading never sits alone at the bottom of a page. The orphans and widows properties set the minimum lines that must stay together at the start and end of a paragraph — orphans: 3; widows: 3; is a sane default for body text.

One caution: break-inside: avoid is a request, not a command. If a component is taller than the page itself, the browser must break it somewhere. Design printable components (especially tables) to fragment gracefully: repeat table headers on each page and avoid fixed heights that fight the page box.

@media print {
  /* Never split these across pages */
  .invoice-card, figure, pre, blockquote {
    break-inside: avoid;
  }

  /* Each major section starts on a fresh page */
  .report-chapter {
    break-before: page;
  }

  /* Keep headings glued to the content that follows */
  h1, h2, h3 {
    break-after: avoid;
  }

  p, li {
    orphans: 3;
    widows: 3;
  }

  /* Repeat table headers on every printed page */
  thead { display: table-header-group; }
  tfoot { display: table-footer-group; }
}

4. @page Rules and Print Layout

The @page rule controls the page box itself: its size and margins. @page { size: A4; margin: 20mm; } is the most common declaration, and size: landscape is handy for wide tables and dashboards. Margins set here combine with the browser's own print dialog margins, so keep them modest and let users fine-tune in the dialog.

Complex screen layouts rarely survive printing. Multi-column grids, sticky sidebars, and flex rows designed for 1440px collapse badly on an A4 page. The pragmatic move is to flatten: inside @media print, switch grids and flex containers to display: block, stack sections vertically, and let content flow naturally. A print layout should be boring — boring prints perfectly.

Running headers and footers (page numbers, document titles on every page) are theoretically possible with @page margin boxes like @top-center, but browser support remains spotty — Chrome only recently improved it. For reliable page numbers today, most teams generate PDFs server-side or accept the browser's built-in header/footer options in the print dialog instead of fighting CSS.

/* Page box: size and margins */
@page {
  size: A4;
  margin: 18mm 15mm;
}

@page landscape-sheet {
  size: A4 landscape;
}

@media print {
  /* Flatten fancy screen layouts into a printable column */
  .dashboard-grid, .flex-row {
    display: block !important;
  }

  /* Wide tables get their own landscape page */
  .wide-report {
    page: landscape-sheet;
    break-before: page;
  }
}

5. Testing and Debugging Print CSS

Never test print CSS by actually printing. Every Chromium-based browser lets you emulate print media: open DevTools, press Ctrl+Shift+P, type “rendering”, and set “Emulate CSS media type” to print. The page instantly renders with your @media print rules applied, and you can inspect elements, tweak values live, and iterate in seconds. Firefox offers the same under its document print preview with media emulation.

The browser print preview dialog (Ctrl+P) is the second tool: it shows real pagination, page counts, and margin behavior. Toggle “Background graphics” on and off to see what users with default settings will get — most users leave it off, which is why you must never rely on background colors or images to convey meaning in print.

Common gotchas to sweep for: flex and grid containers that refuse to fragment (flatten them), absolutely positioned elements overlapping content across pages, and web fonts that fail when offline (print output should fall back to system serif/sans gracefully). A final checklist pass through the table below catches 90% of print bugs before your users do.

6. Frequently Asked Questions (FAQs)

Do background colors and images print by default?

No. Browsers strip backgrounds unless the user enables “Background graphics” in the print dialog. Design print output to work without them, and only use print-color-adjust: exact for small critical elements like a logo — never for large areas, which waste ink.

How do I repeat table headers on every printed page?

Add thead { display: table-header-group; } inside your @media print block. This works with real <table> markup and is supported across browsers. Pair it with break-inside: avoid on rows so a single row never splits across the page boundary.

Can I force a page break before a specific element?

Yes: break-before: page (with the legacy alias page-break-before: page for older engines). Apply it to the element that should start on a fresh page, such as each chapter of a report or each invoice in a batch print.

How do I test print styles without wasting paper?

Use DevTools media emulation (Rendering panel → Emulate CSS media type → print) for fast iteration, then check real pagination in the browser's print preview dialog (Ctrl+P). Never ship print CSS tested only by looking at the screen styles.

Why do my flexbox and grid layouts break when printing?

Fragmentation (splitting content across pages) is unreliable for flex and grid containers in several browsers. The standard fix is to flatten them to display: block inside @media print and let the content flow as a simple vertical column.
