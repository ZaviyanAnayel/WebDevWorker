1. Local State First: Lifting State Up

The best state management is the least state management. Before reaching for any library, ask where the state is actually used: if only one component needs it, useState in that component is the complete solution. If two siblings need it, lift it to their closest common parent and pass it down as props. Most "state management problems" are really component-structure problems.

function CheckoutPage() {
  // State lives at the closest common ancestor of everyone who needs it
  const [cart, setCart] = useState([]);
  const addItem = (item) => setCart((c) => [...c, item]);
  const removeItem = (id) => setCart((c) => c.filter((i) => i.id !== id));

  return (
    <div className="checkout">
      <ProductList onAdd={addItem} />      {/* deep, but props are fine */}
      <CartSidebar cart={cart} onRemove={removeItem} />
      <OrderSummary cart={cart} />
    </div>
  );
}

Lifting state works beautifully until the distance grows: when state must travel through five layers of components that don't care about it — prop drilling — every intermediate component re-renders and the code becomes brittle to refactor. That's the signal to introduce a wider mechanism, not a reason to start with one.

A useful discipline: keep state as low as it can possibly live, and colocate state with the UI that uses it. Globalizing everything "just in case" creates invisible coupling where any component can mutate anything. Local-first keeps the data flow legible and makes bugs local too.

2. Context API: The Built-in Prop-Drilling Fix

React's Context API broadcasts a value to an entire subtree without prop drilling. You create a context, provide a value high in the tree, and any descendant consumes it with useContext. It's built in, zero-dependency, and perfect for low-frequency, app-wide values like theme, locale, or the current user:

import { createContext, useContext, useState, useMemo } from 'react';

const ThemeContext = createContext(null);

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('dark');
  // Memoize the value: otherwise EVERY consumer re-renders on EVERY provider render
  const value = useMemo(() => ({ theme, toggle: () =>
    setTheme((t) => (t === 'dark' ? 'light' : 'dark')) }), [theme]);
  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used inside ThemeProvider');
  return ctx;
}

// Any descendant, at any depth, with no prop drilling:
function ThemeButton() {
  const { theme, toggle } = useTheme();
  return <button onClick={toggle}>Switch to {theme === 'dark' ? 'light' : 'dark'}</button>;
}

The critical performance rule: memoize the provider value. Context compares by reference, so an inline object literal is "new" every render and re-renders every consumer — even ones using unrelated parts of the value. Worse, there's no selector: any change to the context value re-renders all consumers. That's why Context is ideal for values that change rarely (theme, auth) and a poor fit for high-frequency state (text inputs, animations, rapidly updating feeds).

Split contexts by update frequency when needed — a UserContext for identity plus a separate CartContext for the cart — so a cart update doesn't re-render everything consuming the user. And always export a custom hook (like useTheme) that throws a helpful error outside the provider; it turns a cryptic null crash into a one-line fix.

3. When Context Isn't Enough

Context hits its limits in three situations. High-frequency updates: a context value changing 60 times a second re-renders the whole consumer subtree every frame — fine for theme toggles, fatal for a live cursor position. Selective subscriptions: Context gives you the whole value or nothing; you can't subscribe to one slice without re-rendering on changes to the rest. Logic outside React: contexts live inside the component tree, so non-component code (API layers, websockets, utility modules) can't read or update them.

External stores solve all three by keeping state outside React and letting components subscribe to exactly the slices they need. Updates propagate through subscriptions, not through the component tree, so a change to one slice re-renders only the components reading that slice. The store is also importable anywhere — thunks, event handlers, and plain modules can all dispatch updates.

Symptoms you need one: you're memoizing aggressively to fight Context re-renders, you're splitting one context into six micro-contexts, state updates need to happen outside components, or you want time-travel debugging and a single serializable snapshot of app state. If none of these apply, Context plus local state remains the simplest correct answer — and simplicity is a feature your future maintainers will thank you for.

4. Redux Toolkit vs Zustand: A Practical Comparison

Redux Toolkit (RTK) is the batteries-included official Redux: slices, Immer-powered "mutative" reducers, and RTK Query for data fetching. Zustand is a minimal external store — create a hook-based store in a few lines with no providers, no boilerplate. Both are excellent; they optimize for different teams:

// Zustand: a complete store in ~10 lines, no provider needed
import { create } from 'zustand';

export const useCartStore = create((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
  remove: (id) => set((s) => ({ items: s.items.filter((i) => i.id !== id) })),
  clear: () => set({ items: [] }),
}));

// Components subscribe to exactly the slice they need:
function CartCount() {
  const count = useCartStore((s) => s.items.length); // re-renders ONLY when length changes
  return <span>{count}</span>;
}
// Redux Toolkit: structured slices + DevTools + RTK Query
import { createSlice, configureStore } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    // Immer lets you write "mutating" code that stays immutable
    add: (state, action) => { state.items.push(action.payload); },
    remove: (state, action) => {
      state.items = state.items.filter((i) => i.id !== action.payload);
    },
  },
});

export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
export const { add, remove } = cartSlice.actions;

Zustand's selector model (useCartStore(s => s.items.length)) is its superpower: components re-render only when their selected slice changes, with zero provider setup. RTK's superpower is structure at scale — standardized async flows with createAsyncThunk, normalized caching with RTK Query, and DevTools time-travel that large teams depend on during incidents. For server state (fetched data), consider React Query/TanStack Query regardless of your client-state choice — it solves caching, deduping, and background refetching better than any client store.

5. Choosing the Right Tool: A Decision Framework

Run through this ladder from simplest to heaviest, and stop at the first rung that fits: 1) Local useState — one component uses it. 2) Lifted state — a few nearby components share it. 3) Context — many components at various depths need a rarely-changing value (theme, user, locale). 4) Zustand — frequently-updating shared state, selective subscriptions, or updates from outside React. 5) Redux Toolkit — large team, complex async workflows, need for standardized patterns and top-tier DevTools.

Separate client state from server state in your thinking. Server state — data fetched from an API — has its own concerns: caching, staleness, deduping, background refetching. A dedicated data-fetching library (React Query, RTK Query, or Next.js server components) handles those; stuffing API responses into a client store and hand-rolling cache invalidation is the most common state-management regret.

Finally, you can mix: Context for theme and auth, Zustand for the cart and UI prefs, React Query for server data. There's no purity requirement — only the requirement that each piece of state lives in the simplest mechanism that serves its update frequency, scope, and consumers. Revisit the choice when the app's shape changes; the ladder works in both directions, and simplifying is also progress.

6. Frequently Asked Questions (FAQs)

Is Redux dead in 2026?

No. Redux Toolkit remains the standard for large teams and complex apps, with RTK Query handling data fetching and DevTools offering unmatched debugging. For smaller apps, lighter options like Zustand or Context are often simpler — Redux was never meant to be the default for every app.

Does Context API cause performance problems?

It can. Every consumer re-renders whenever the provider value changes by reference, with no way to subscribe to part of the value. Memoize the provider value with useMemo, split contexts by update frequency, and avoid Context for rapidly-changing state like form inputs or animations.

What is Zustand and when should I use it?

Zustand is a tiny external state library: you create a store with a hook in a few lines, no provider required, and components subscribe to only the slices they need via selectors. It is ideal when Context re-renders too much, state updates from outside React, or you want minimal boilerplate.

When do I actually need a state management library?

When lifted state and Context start hurting: prop drilling through many layers, Context re-render storms on frequent updates, state that must update from outside components, or a need for time-travel debugging. Until those symptoms appear, local state plus Context is simpler and faster to maintain.

Can I mix Context, Zustand, and Redux in one app?

Yes, and it is common. A typical mix: Context for theme and auth, Zustand for interactive client state like carts or UI preferences, and React Query or RTK Query for server data. Match each piece of state to the simplest tool that fits its scope and update frequency.
