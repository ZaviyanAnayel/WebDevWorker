1. Why Docker Matters for Web Developers

“It works on my machine” is the most expensive sentence in software. Your laptop runs Node 22 on macOS, the staging server runs Node 20 on Ubuntu, and production has a slightly different OpenSSL — and somewhere in those gaps, bugs breed. Docker eliminates the gaps by packaging your app with everything it needs to run: runtime, dependencies, system libraries, and configuration.

A Dockerized app behaves identically on your laptop, your teammate's Windows machine, CI runners, and production servers. Onboarding drops from a day of setup to a single docker compose up. Rollbacks become trivial — just run the previous image tag. And because containers are isolated, you can run five projects with five conflicting Node versions without a single nvm headache.

Docker is not a virtual machine. VMs virtualize hardware and carry a full guest OS; containers share the host kernel and start in milliseconds. That lightness is what makes containers practical for everyday development, not just ops teams.

It also changes how you think about dependencies. Instead of installing Postgres, Redis, and Elasticsearch directly on your laptop — and debugging version conflicts between projects — you run each as a disposable container. Need Postgres 16 for one project and 14 for another? Two containers, zero conflicts, no system-wide installs to clean up later.

2. Images vs Containers: The Core Mental Model

An image is an immutable blueprint — a stacked set of filesystem layers built from a Dockerfile. A container is a running instance of an image, like a class versus an object. You can run dozens of containers from one image, and deleting a container never affects the image.

# Pull an image, run a container, list and stop it
docker pull node:20-alpine
docker run -d --name my-app -p 3000:3000 node:20-alpine
docker ps
docker stop my-app
docker rm my-app

Images are built in layers, and Docker caches each layer. Reorder your Dockerfile so slow-changing steps (installing dependencies) come before fast-changing ones (copying source code), and rebuilds take seconds instead of minutes.

Pull public images from Docker Hub or your registry of choice, and always pin a specific tag like node:20-alpine rather than latest. Floating tags make builds non-reproducible — the image you tested today may silently become a different one tomorrow.

3. Writing Your First Dockerfile

A Dockerfile is the recipe for your image. Here is a production-ready, multi-stage build for a Node.js app — the first stage compiles, the second ships only what is needed to run:

# ---- Build stage ----
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# ---- Production stage ----
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
EXPOSE 3000
CMD ["node", "dist/index.js"]
InstructionPurpose
FROMBase image to start from
WORKDIRWorking directory inside the image
COPYCopy files from build context
RUNExecute commands at build time
EXPOSEDocument which port the app uses
CMDDefault command when container starts

Multi-stage builds matter: the final image contains no source code, no dev dependencies, and no build tools — smaller, faster to deploy, and with a much smaller attack surface. Add a .dockerignore (node_modules, .git, .env) so secrets and junk never enter the build context.

4. Volumes and Networking

Containers are ephemeral by design: delete one and its filesystem goes with it. Volumes are how data survives. A named volume is managed by Docker and ideal for databases; a bind mount maps a host directory into the container and is perfect for live-reloading source code during development.

# Named volume for Postgres data (survives container restarts)
docker run -d --name db \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

# Bind mount for live development
docker run -d --name web -p 3000:3000 \
  -v $(pwd):/app -v /app/node_modules \
  node:20-alpine npm run dev

The -p 3000:3000 flag maps ports as host:container. Containers on the same Docker network reach each other by name — your app connects to postgres://db:5432, no IP addresses needed. That service-name networking is exactly what Docker Compose sets up for you automatically.

5. Docker Compose for Multi-Container Apps

Real apps are rarely one container. Docker Compose defines your whole stack — app, database, cache — in one YAML file and starts it with a single command:

services:
  web:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://user:secret@db:5432/app
    depends_on: [db, redis]
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
    environment:
      POSTGRES_PASSWORD: secret
  redis:
    image: redis:7-alpine
volumes:
  pgdata:

Run docker compose up -d to start everything, docker compose logs -f to watch output, and docker compose down to stop. Commit this file and every developer, CI runner, and server spins up the identical stack. That is the “works on my machine” problem, solved permanently.

When you are done for the day, docker compose down -v removes containers and named volumes together — handy for resetting a dev database to a clean slate. Your compose file remains, so tomorrow's up rebuilds the whole world exactly as before.

6. Frequently Asked Questions (FAQs)

What is the difference between a Docker image and a container?

An image is an immutable template built from a Dockerfile, like a class. A container is a running instance of an image, like an object. You build images once and run many containers from them.

Do I still need a virtual machine if I use Docker?

Usually not for development. Containers share the host kernel, so they start in milliseconds and use far less memory than VMs. VMs are still useful when you need a different kernel, such as running Linux containers on older Windows setups.

How do I keep my Docker images small?

Use slim base images like alpine, leverage multi-stage builds to exclude build tools, combine RUN commands to reduce layers, and add a .dockerignore file. A Node app image can shrink from over 1 GB to under 150 MB.

What is the difference between a volume and a bind mount?

A named volume is managed by Docker and best for persistent data like databases. A bind mount maps a specific host directory into the container and is best for development, such as live-reloading your source code.

Is Docker free to use?

Docker Engine and the Docker CLI are free and open source. Docker Desktop is free for personal use, education, and small businesses, with paid subscriptions for larger companies. Alternatives like Podman and Rancher Desktop are fully free.
