1. Measure First: Finding the Real Bottleneck

Performance work without measurement is superstition. React apps feel slow for specific, diagnosable reasons — a component re-rendering hundreds of times, a 2 MB bundle, a list rendering 10,000 DOM nodes — and each demands a different fix. Guessing leads to memoizing everything, which adds overhead while the real problem (say, a synchronous 800 ms computation on every keystroke) goes untouched.

Start with the React DevTools Profiler: record an interaction, then inspect which components rendered and for how long. Components highlighted in yellow/red are your suspects; the "why did this render" hints reveal whether props, state, or context changed. Pair it with the browser's Performance panel for the full picture — scripting, layout, and paint — since a "React is slow" complaint is often a layout-thrashing or oversized-image problem in disguise.

For production reality, measure Core Web Vitals: Largest Contentful Paint (loading), Interaction to Next Paint (responsiveness), and Cumulative Layout Shift (visual stability). Lab tools like Lighthouse estimate them; field data from real users (via the web-vitals library) tells you what actually happens on mid-range phones. Optimize the metric your users feel, not the one that's easiest to demo.

2. Memoization: React.memo, useMemo, and useCallback

Memoization trades memory and comparison cost for skipped work. React.memo skips re-rendering a component when its props are shallowly equal; useMemo caches an expensive value; useCallback stabilizes a function reference. The chain matters: memoizing a child is useless if the parent passes a new inline object or arrow function every render:

import { memo, useMemo, useCallback, useState } from 'react';

// Memoized child: re-renders ONLY when user or onFollow actually change
const UserCard = memo(function UserCard({ user, onFollow }) {
  return (
    <div className="card">
      <Avatar src={user.avatar} />
      <span>{user.name}</span>
      <button onClick={() => onFollow(user.id)}>Follow</button>
    </div>
  );
});

function UserList({ users }) {
  const [filter, setFilter] = useState('');

  // Stable function: same reference across renders unless deps change
  const handleFollow = useCallback((id) => {
    api.follow(id);
  }, []);

  // Expensive filter runs only when users or filter change
  const visible = useMemo(() =>
    users.filter((u) => u.name.toLowerCase().includes(filter.toLowerCase())),
    [users, filter]
  );

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      {visible.map((u) => (
        <UserCard key={u.id} user={u} onFollow={handleFollow} />
      ))}
    </>
  );
}

Notice what makes this work: handleFollow is stable via useCallback, so UserCard's props stay referentially equal while typing in the filter box — only the list membership changes. Without useCallback, every keystroke would create a new function, defeat memo, and re-render every card.

But memoization has a cost — prop comparisons and cache bookkeeping on every render. Don't wrap everything: profile first, then memoize components that render often with unchanged props (list rows, heavy charts, complex cards) and computations that are genuinely expensive (sorting/filtering large arrays, parsing). React Compiler (in modern setups) now auto-memoizes much of this, making manual memoization a targeted tool rather than a default.

3. Code Splitting and Lazy Loading

Most apps ship their entire bundle on first load — including the admin panel 99% of users never open. Code splitting breaks the bundle into chunks loaded on demand, and React.lazy + Suspense make route-level splitting nearly free:

import { lazy, Suspense } from 'react';
import { createBrowserRouter, RouterProvider } from 'react-router-dom';

// Each lazy() call becomes a separate chunk, fetched on first navigation
const AdminPanel = lazy(() => import('./pages/AdminPanel'));
const Reports = lazy(() => import('./pages/Reports'));
const ChartEditor = lazy(() => import('./components/ChartEditor'));

function LoadingFallback() {
  return <div className="skeleton">Loading…</div>;
}

const router = createBrowserRouter([
  { path: '/', element: <Home /> }, // in the main bundle: fast first paint
  {
    path: '/admin',
    element: (
      <Suspense fallback={<LoadingFallback />}>
        <AdminPanel />
      </Suspense>
    ),
  },
  { path: '/reports', element: (
      <Suspense fallback={<LoadingFallback />}><Reports /></Suspense>
  )},
]);

Split at route boundaries first — it's the biggest win for the least effort — then at heavy components behind user interaction (rich text editors, chart builders, modals). Design the fallback as a skeleton matching the incoming layout to avoid layout shift, and consider prefetching the chunk on link hover or during idle time so navigation feels instant.

Watch chunk granularity: hundreds of tiny chunks mean hundreds of requests (HTTP/2 helps, but each still has overhead), while a few giant chunks defeat the purpose. Bundlers handle the balance well by default — override only with evidence. And always verify with a bundle analyzer; the most common surprise is a "lazy" chunk that secretly imports the whole app through a barrel file.

4. Virtualizing Long Lists

Rendering 10,000 rows creates 10,000 DOM nodes — slow to create, slow to diff, slow to paint. Virtualization renders only the visible window (plus a small overscan buffer) and recycles rows as you scroll, keeping the DOM at a few dozen nodes regardless of dataset size. Libraries like TanStack Virtual or react-window implement it; the concept is straightforward:

import { useVirtualizer } from '@tanstack/react-virtual';
import { useRef } from 'react';

function VirtualList({ items }) {
  const parentRef = useRef(null);
  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 56,   // estimated row height in px
    overscan: 5,              // extra rows rendered above/below viewport
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: 'auto' }}>
      {/* Spacer div fakes the full scroll height */}
      <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
        {virtualizer.getVirtualItems().map((v) => (
          <div key={v.key}
               style={{ position: 'absolute', top: 0, left: 0, width: '100%',
                        transform: `translateY(${v.start}px)` }}>
            <Row item={items[v.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}

Virtualization needs measurable row heights (fixed or estimated-then-measured) — dynamic content requires the measurer variant. Combine it with memoized rows so scrolling doesn't re-render visible items, and keep row components light: a virtualized list of heavy cards still janks if each card does expensive work.

Virtualize when lists exceed a few hundred rows or rows are complex. Below that, plain rendering with good keys is simpler and faster to build. Also consider pagination or "load more" as a UX alternative — sometimes the best virtualization is not rendering the data at all until asked.

5. Rendering Less: Keys, Colocation, and Update Discipline

Beyond the big techniques, daily habits compound. Keys: use stable IDs, never array indices for dynamic lists — index keys make React reuse the wrong DOM nodes on reorder, corrupting input state and focus while doing extra work. State colocation: keep state in the lowest component that needs it; a search input's keystroke state in the page root re-renders the whole page per keystroke, while the same state inside the search box re-renders only the box.

React.memo + stable propsWasted re-rendersHeavy child re-renders with same props

Debounce expensive reactions to rapid input — search queries, resize handlers — so work happens once per pause, not once per keystroke. And for updates that can lag slightly behind interaction, useTransition marks them non-urgent: the input stays responsive while the heavy list update yields, eliminating the classic "typing freezes while filtering" complaint.

The meta-rule: make the common path cheap. Fewer nodes, smaller bundles, narrower re-renders, deferred non-urgent work. Profile, fix the biggest bar in the flame chart, and repeat — performance is a loop, not a checklist.

6. Frequently Asked Questions (FAQs)

Is premature optimization bad in React?

Yes, when it means memoizing everything before measuring. Unused memoization adds comparison overhead and dependency-array maintenance. Profile with React DevTools first, fix the actual bottleneck — often state placement or bundle size — and memoize only where the profiler proves it helps.

Does useMemo always make my app faster?

No. useMemo trades the cost of recomputation for the cost of caching and dependency comparison. It pays off for genuinely expensive computations or values feeding memoized children and effect dependencies. For cheap values, it is pure overhead.

How do I decide where to split my code?

Split at route boundaries first — admin panels, settings, and dashboards most users never visit. Then split heavy components behind user interaction, like editors and chart builders. Verify chunk contents with a bundle analyzer to catch barrel files pulling everything back in.

What is list virtualization?

Rendering only the rows visible in the viewport plus a small buffer, instead of all rows. A spacer element fakes the full scroll height while a few dozen DOM nodes get recycled during scrolling. Libraries like TanStack Virtual implement it; use it for lists beyond a few hundred rows.

Why are React keys important for performance?

Keys tell React which items correspond across renders. Stable ID keys let React reuse DOM nodes on reorder; index keys make it reuse the wrong nodes, causing extra work plus corrupted input state and focus. Always key dynamic lists by stable unique IDs.
