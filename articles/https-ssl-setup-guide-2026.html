1. Why HTTPS Is Non-Negotiable in 2026

HTTPS is no longer a premium feature — it is the baseline expectation of the modern web. Browsers now mark plain HTTP pages as "Not Secure", search engines rank HTTPS sites higher, and features like geolocation, service workers, and credential management APIs are restricted to secure contexts entirely. If your site still serves traffic over HTTP, you are losing trust, traffic, and functionality at once.

The security case is straightforward: without TLS, everything between your server and the user — passwords, session cookies, form submissions — travels in plaintext, readable by anyone on the network path. Coffee-shop Wi-Fi sniffing, ISP injection of ads or scripts, and corporate middleboxes all become trivially effective against HTTP. TLS encrypts the channel, authenticates the server via its certificate, and guarantees the data has not been tampered with in transit.

The cost objection died years ago. Certificates are free through Let's Encrypt, issuance is automated, and the performance overhead of modern TLS (especially with TLS 1.3's faster handshakes and HTTP/2 multiplexing) is negligible. There is simply no reason left to ship HTTP in 2026.

2. Free Certificates with Let's Encrypt and Certbot

Let's Encrypt is a free, automated certificate authority trusted by all major browsers, and Certbot is its official client. On a typical Ubuntu server running Nginx, going from HTTP to HTTPS takes two commands:

# Install certbot with the Nginx plugin
sudo apt update && sudo apt install -y certbot python3-certbot-nginx

# Obtain a certificate and auto-configure Nginx for HTTPS
sudo certbot --nginx -d example.com -d www.example.com

# Test automatic renewal (certificates last 90 days; renewals are automatic)
sudo certbot renew --dry-run

Certbot validates that you control the domain (usually via an HTTP challenge), issues the certificate, rewrites your Nginx configuration to serve HTTPS, and sets up a redirect from HTTP to HTTPS. The 90-day certificate lifetime is deliberate — it limits the damage of a compromised key and forces automation, which is why the renewal timer matters more than the certificate itself.

For servers where you prefer manual control, use certbot certonly --webroot or DNS-based validation for wildcard certificates (-d "*.example.com"), then point your web server at the certificate files in /etc/letsencrypt/live/. Never copy private keys across servers over insecure channels, and restrict key file permissions to root.

3. Configuring TLS on Nginx and Apache

If Certbot's automatic configuration is not an option, the manual Nginx setup is only a few lines. The key decisions: listen on 443 with ssl, point to your certificate and key, enable only TLS 1.2 and 1.3, and redirect all HTTP traffic to HTTPS:

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name example.com www.example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;          # disable TLS 1.0/1.1 entirely
    ssl_prefer_server_ciphers on;
    ssl_session_cache shared:SSL:10m;

    # ... your normal location blocks ...
}

server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;   # permanent redirect to HTTPS
}

For Apache, the equivalent uses SSLEngine on with SSLCertificateFile and SSLCertificateKeyFile inside a <VirtualHost *:443> block, plus a mod_rewrite rule for the HTTP-to-HTTPS redirect. After configuring either server, verify with SSL Labs' test (ssllabs.com/ssltest) and aim for an A rating: it checks protocol versions, cipher suites, certificate chains, and common misconfigurations in one pass.

4. Enabling HSTS the Safe Way

HTTP Strict Transport Security (HSTS) is a response header that tells browsers to only ever contact your domain over HTTPS — even if the user types http:// or clicks an old HTTP link. This closes the gap where an attacker strips the initial HTTP-to-HTTPS redirect (SSL stripping) before the user ever reaches your secure page. Without HSTS, that first insecure request is a permanent weak point.

Enable it cautiously, because HSTS is cached by browsers for the duration you specify and is difficult to undo quickly. Roll it out in stages:

# Stage 1: short max-age to verify nothing breaks (1 day)
add_header Strict-Transport-Security "max-age=86400" always;

# Stage 2: after a week of no issues, extend to 6-12 months with subdomains
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

# Stage 3 (optional, irreversible-ish): submit to the HSTS preload list
# add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;

The preload directive is for submission to the browser preload list, which ships inside browsers themselves — powerful, but removal takes months, so only do it when you are certain every subdomain supports HTTPS. Always serve the HSTS header on HTTPS responses only, and test with curl -I https://example.com to confirm it is present.

5. Renewals, Monitoring, and Mixed-Content Fixes

Certificates expire — Let's Encrypt's every 90 days — so automation is the whole game. Certbot installs a systemd timer or cron job that runs certbot renew twice daily; verify it exists and that your web server reloads after renewal (Certbot's Nginx and Apache plugins handle this, but manual setups need a --deploy-hook "systemctl reload nginx"). Set up external monitoring too: a free uptime monitor that alerts on certificate expiry catches the failure modes automation misses.

The most common post-migration issue is mixed content: your page loads over HTTPS but pulls images, scripts, or fonts over HTTP, which browsers block or warn about. Find offenders fast in the browser console (look for "Mixed Content" warnings), then fix them at the source — update hardcoded http:// URLs in templates and the database, and consider adding upgrade-insecure-requests to your Content Security Policy as a safety net during cleanup:

# Find hardcoded http:// asset URLs in your project
grep -rn "http://" templates/ static/ --include="*.html" --include="*.js"

# CSP directive that auto-upgrades insecure subresource requests
add_header Content-Security-Policy "upgrade-insecure-requests;" always;

HTTPS done right is a chain: valid certificate, strong TLS configuration, permanent redirects, HSTS, automated renewals, and clean subresources. Each link is simple; together they are what "secure" actually means in the browser.

6. Frequently Asked Questions (FAQs)

Is a free Let's Encrypt certificate as secure as a paid one?

Yes. Browsers trust Let's Encrypt certificates exactly like paid domain-validated certificates, and the encryption strength is identical. Paid certificates mainly add extended validation branding or longer lifetimes; for transport security, Let's Encrypt is the standard choice for the vast majority of sites.

How often do Let's Encrypt certificates need renewal?

Every 90 days. The short lifetime is intentional — it limits exposure if a key is compromised. Certbot automates renewal with a twice-daily check, so in practice you set it up once and never think about it again, as long as you verify the renewal timer is running.

What is the difference between TLS 1.2 and TLS 1.3?

TLS 1.3 is faster (one fewer round trip in the handshake), simpler (obsolete cipher suites removed), and more secure by design. Enable both 1.2 and 1.3 for compatibility, but disable TLS 1.0 and 1.1 entirely — they have known weaknesses and no modern client needs them.

What is mixed content and how do I fix it?

Mixed content happens when an HTTPS page loads subresources (images, scripts, stylesheets) over HTTP, which browsers block or flag. Fix it by updating hardcoded http:// URLs in your templates, database, and CMS content to https://, and add the upgrade-insecure-requests CSP directive as a transitional safety net.

Should I enable HSTS preload?

Only when you are certain every subdomain — including future ones — will serve HTTPS permanently. Preload bakes your domain into browsers themselves and takes months to remove. Start with a short max-age, extend to a year with includeSubDomains, and add preload only after months of stable HTTPS everywhere.
