1. Custom Elements: Defining Your Own HTML Tags

Custom elements let you define new HTML tags with encapsulated behavior — <user-card>, <star-rating>, <data-table> — that work in any page and any framework. The browser treats them as first-class elements: they parse in HTML, appear in the DOM, and upgrade automatically when their definition loads.

There are two flavors. Autonomous custom elements extend HTMLElement directly and are the common case. Customized built-in elements extend existing tags like HTMLButtonElement via the is attribute, but Safari has never supported them, so autonomous elements are the portable choice for real projects.

Every custom element name must contain a hyphen — user-card, not usercard — which guarantees the browser will never collide with a future standard tag. Register with customElements.define(), and elements already in the document upgrade in place, keeping their attributes, children, and position.

Timing matters for perceived performance: define elements as early as possible so the browser upgrades them before first paint, avoiding a flash of unstyled custom tags. For larger apps, use customElements.whenDefined() to coordinate code that depends on an element being ready, and consider declarative shadow DOM — <template shadowrootmode="open"> — to get server-rendered encapsulated markup with zero JavaScript on the critical path.

// Define an autonomous custom element
class UserCard extends HTMLElement {
  constructor() {
    super(); // always call super() first
  }

  connectedCallback() {
    const name = this.getAttribute("name") || "Anonymous";
    this.innerHTML = `<div class="card">Hello, ${name}!</div>`;
  }
}

customElements.define("user-card", UserCard);

2. Shadow DOM: True Style and Markup Encapsulation

Shadow DOM gives an element its own sealed-off DOM subtree. Styles defined inside a shadow root do not leak out, and page styles do not leak in — which finally solves the oldest problem in component UI: a global stylesheet accidentally restyling your widget, or your widget's CSS breaking the host page.

Attach a shadow root with attachShadow({ mode: "open" }) and everything you append to it is encapsulated. Use open mode in practice: it keeps the shadow root inspectable in DevTools and accessible to testing tools, while closed mode hides it at the cost of debuggability for almost no real security benefit.

Events crossing the shadow boundary are retargeted: a click inside the shadow tree appears to come from the host element itself. This is usually what you want for encapsulation, but when a parent genuinely needs details, dispatch a CustomEvent with composed: true so it propagates through the boundary.

// Shadow DOM: styles stay inside the component
class FancyButton extends HTMLElement {
  constructor() {
    super();
    const shadow = this.attachShadow({ mode: "open" });
    shadow.innerHTML = `
      <style>
        button {
          background: #eab308; color: #0f172a; border: 0;
          padding: 10px 22px; border-radius: 8px;
          font-weight: 700; cursor: pointer;
        }
        button:hover { filter: brightness(1.1); }
      </style>
      <button><slot>Click me</slot></button>`;
  }
}
customElements.define("fancy-button", FancyButton);

3. Templates and Slots: Composable Components

The <template> element holds inert markup: its contents are parsed but not rendered and scripts inside do not run until you clone it. This makes templates the ideal blueprint for component internals — define the structure once, then stamp out a fresh copy per instance without re-parsing HTML strings every time.

Slots are the composition mechanism. A <slot> in your shadow tree acts as a placeholder where the user's light-DOM children get projected, so <user-card><img ...></user-card> renders the image at the slot's position. Named slots (<slot name="avatar">) let consumers target specific regions, and fallback content inside the slot renders when nothing is assigned.

Listen for slotchange when your component needs to react to projected content — counting items, measuring, or toggling empty states. Combined with templates, slots give you the same composition ergonomics as framework slots or React children, built directly into the platform.

<template id="user-card-template">
  <style>
    :host { display: block; border: 1px solid #334155; border-radius: 12px; padding: 16px; }
    .header { display: flex; gap: 12px; align-items: center; }
  </style>
  <div class="header">
    <slot name="avatar"><span>👤</span></slot>
    <div><slot name="name">Anonymous</slot></div>
  </div>
  <slot></slot> <!-- default slot for everything else -->
</template>

<script>
class UserCard extends HTMLElement {
  constructor() {
    super();
    const tpl = document.getElementById("user-card-template");
    this.attachShadow({ mode: "open" }).appendChild(tpl.content.cloneNode(true));
  }
}
customElements.define("user-card", UserCard);
</script>

<!-- Named slots route light-DOM children into place -->
<user-card>
  <img slot="avatar" src="/ada.png" alt="Ada">
  <strong slot="name">Ada Lovelace</strong>
  <p>First programmer. Wrote notes on the Analytical Engine.</p>
</user-card>

4. Lifecycle Callbacks and Observed Attributes

Custom elements expose four lifecycle callbacks. connectedCallback fires when the element joins the document — this is where you render, fetch data, and attach listeners. disconnectedCallback fires on removal and is where you clean up timers, observers, and subscriptions to avoid memory leaks.

attributeChangedCallback fires whenever a listed attribute changes, making attributes the reactive input channel of your component. Declare which attributes to watch in the static observedAttributes getter, then re-render or update state inside the callback. adoptedCallback covers the rare case of moving nodes between documents.

A clean pattern is to mirror attributes to properties: the attribute is the declarative HTML API, the property is the ergonomic JavaScript API, and each setter updates the other. Guard against infinite loops by checking whether the value actually changed before reflecting it back.

// Reactive counter driven by an observed attribute
class ClickCounter extends HTMLElement {
  static get observedAttributes() { return ["count"]; }

  constructor() {
    super();
    this.attachShadow({ mode: "open" });
  }

  get count() { return Number(this.getAttribute("count") || 0); }
  set count(v) { this.setAttribute("count", String(v)); }

  connectedCallback() { this.render(); }

  attributeChangedCallback(name, oldVal, newVal) {
    if (oldVal !== newVal) this.render();
  }

  render() {
    this.shadowRoot.innerHTML =
      `<button id="btn">Clicked ${this.count} times</button>`;
    this.shadowRoot.getElementById("btn")
      .addEventListener("click", () => { this.count = this.count + 1; });
  }
}
customElements.define("click-counter", ClickCounter);

5. Styling, Theming, and Framework Interop

Shadow DOM gives you three styling hooks. :host targets the element itself from inside, ::slotted() styles projected light-DOM children (one level deep), and CSS custom properties pierce the boundary by design — making them the official theming API. Expose --button-bg style variables and consumers theme your component without breaking encapsulation.

Web components work inside every major framework because frameworks ultimately render HTML. React 19 handles custom elements natively; in Vue and Angular you may need to tell the compiler which tags are custom so it does not try to resolve them as components. Pass complex data as properties (not attributes) and listen for CustomEvents with composed: true for seamless interop.

Know when not to reach for them: highly stateful application screens with complex routing are still more productive in a framework. Web components shine for design systems, embeddable widgets, and cross-framework UI libraries — the leaf nodes of your UI that must survive framework migrations. And always keep accessibility in mind: use semantic elements inside your shadow tree and manage focus explicitly.

6. Frequently Asked Questions (FAQs)

Do web components work in all modern browsers?

Yes. Custom elements, shadow DOM, and HTML templates are natively supported in Chrome, Edge, Firefox, and Safari with no polyfills needed. Only customized built-in elements lack Safari support, which is why autonomous elements are the recommended pattern.

Should I use web components instead of React or Vue?

Not as a wholesale replacement. Frameworks remain more productive for stateful application screens. Web components excel at design systems, embeddable widgets, and UI libraries that must work across frameworks and survive framework migrations.

What is the difference between shadow DOM and an iframe?

Both provide encapsulation, but shadow DOM is lightweight: it shares the document's stylesheets scope rules, JavaScript context, and accessibility tree, with no separate document or heavy process boundary. Iframes are far heavier and break seamless integration.

How do I style content projected into slots?

Use the ::slotted() pseudo-element inside your shadow styles, which targets top-level slotted nodes. For deeper theming, expose CSS custom properties — they pierce the shadow boundary by design and are the standard theming API.

Are web components a good fit for design systems?

They are one of the best fits. Framework-agnostic components mean one design system can serve React, Vue, Angular, and plain HTML consumers simultaneously, and the components keep working even as teams migrate between frameworks.
