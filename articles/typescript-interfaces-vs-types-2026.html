1. What Is a TypeScript Interface?

An interface declares the shape of an object: which properties exist, their types, and which are optional or readonly. It is the idiomatic way to describe object contracts in TypeScript — function parameters, class instances, API payloads, and component props. Interfaces are nominal in declaration but structural in checking: TypeScript cares that a value has the required shape, not that it was explicitly declared with the interface.

Interfaces compose through extends, letting you build specialized shapes from shared bases without repeating fields. A class can implement an interface, which makes the compiler verify the class provides every member. This is the classic object-oriented modeling toolkit, and it reads naturally to developers from any typed language.

Interfaces have one unique superpower: declaration merging. Declaring two interfaces with the same name merges their members into one. Libraries exploit this for extensibility — you can augment a third-party interface (say, adding a field to Express's Request) without touching its source. No other TypeScript construct does this.

// Interfaces describe object shapes
interface User {
  readonly id: number;
  name: string;
  email: string;
  role?: "admin" | "member";   // optional property
}

interface Admin extends User {
  permissions: string[];       // adds to the base shape
}

// Classes can implement interfaces — the compiler enforces it
class ApiUser implements User {
  constructor(
    public readonly id: number,
    public name: string,
    public email: string,
  ) {}
}

// Declaration merging: two declarations become one interface
interface Config { apiUrl: string }
interface Config { timeout: number }
// Config now has BOTH apiUrl and timeout — unique to interfaces

2. What Is a Type Alias?

A type alias gives a name to any type — not just objects. Primitives, unions, tuples, function signatures, mapped types, template literal types: if TypeScript can express it, a type alias can name it. Where interfaces are specialized for object shapes, type aliases are the general-purpose naming tool.

This generality is why type aliases own several territories interfaces cannot enter. A union like string | number or a tuple like [number, number] has no interface equivalent. Function types (type Handler = (e: Event) => void) and mapped types (type Partial<T>) are alias territory too. When you need to name anything that isn't a plain object shape, reach for type.

Type aliases also compose differently: instead of extends, you combine them with intersection (&) and union (|) operators. type Admin = User & { permissions: string[] } achieves what interface extension does, with the added ability to intersect unions and primitives — something extends cannot express.

// Type aliases can name ANY type — not just objects
type ID = string | number;                    // union of primitives
type Point = [number, number];                // tuple
type Status = "idle" | "loading" | "done";    // literal union
type Handler = (event: string) => void;       // function signature

// Combining with & (intersection) and | (union)
type Named = { name: string };
type Aged = { age: number };
type Person = Named & Aged;                   // has name AND age
type Input = string | string[] | null;        // flexible input

// Mapped types: derive new types from old ones
type ReadonlyPoint = { readonly [K in keyof Point]: Point[K] };
type ApiResponse<T> = { data: T; error: string | null };

3. Head-to-Head: The Real Differences

For plain object shapes the two are nearly interchangeable — interface User { name: string } and type User = { name: string } check identically. The differences appear at the edges, and they are decisive once you know them.

Declaration merging belongs to interfaces only: redeclaring a type alias is a compile error, while redeclaring an interface merges. Conversely, only type aliases can express unions, tuples, primitives, and mapped types, and only aliases support computed property names in the general case. Interfaces are restricted to object shapes (plus function/call signatures via a rarer syntax).

Error messages differ subtly: interfaces keep their name in hover tooltips and errors (User), while complex type aliases sometimes expand into their full structure, which can make deeply composed aliases harder to read in diagnostics. Performance-wise, interfaces are marginally cheaper for the compiler because their named structure caches well — measurable only in enormous codebases with thousands of recursive types, so it should never drive the decision alone.

The practical upshot: neither is 'better' in general. They overlap heavily for object shapes and diverge everywhere else. Teams that argue about this usually haven't hit the actual decision points — which are specific, learnable, and covered next.

4. When to Use Each: Practical Rules

Four rules cover nearly every case. One: use interface for public API shapes — library interfaces, component props, and anything consumers might want to extend via declaration merging. The TypeScript team itself recommends interfaces for object-oriented-style public contracts.

Two: use type for unions, tuples, function signatures, mapped types, and any non-object type — interfaces simply cannot do these jobs. Three: for internal object shapes, pick one and be consistent; the codebase-wide convention matters more than the choice. Many teams default to interface for objects and type for everything else, which is an excellent default.

Four: when extending third-party types you don't own, prefer interface merging or module augmentation over copying their shape into your own alias — merging keeps you in sync with library updates automatically. And a style note: name interfaces without the Hungarian I prefix (User, not IUser) — the prefix is a C# habit that TypeScript's structural typing makes unnecessary.

// ✅ Public API shape → interface (extensible via merging)
export interface PaginatedResult<T> {
  items: T[];
  total: number;
  page: number;
}

// ✅ Union of variants → type (interfaces can't do this)
export type UploadState =
  | { kind: "idle" }
  | { kind: "uploading"; progress: number }
  | { kind: "done"; url: string }
  | { kind: "failed"; error: string };

// ✅ Function signature → type
export type EventHandler<E> = (event: E) => void;

// ✅ Extending a library type you don't own → interface merging
declare module "express-serve-static-core" {
  interface Request {
    userId?: string;   // now req.userId type-checks everywhere
  }
}

5. Real-World Example: Modeling API Data

Consider a products API. The domain entities — Product, Category — are object shapes, so interfaces fit. The API envelope is generic over the payload type, and the request outcome is a union of success/failure — both type-alias territory. This mixed approach is what professional codebases actually look like: interfaces for the nouns, type aliases for the compositional machinery around them.

Notice how the discriminated union ApiOutcome makes the consumer's job pleasant: checking outcome.ok narrows the type, so outcome.data is available in the success branch and outcome.error in the failure branch, with no type assertions. This pattern — interfaces for shapes, aliases for unions — eliminates an entire class of 'undefined is not an object' bugs at the API boundary, which is exactly where untyped data enters your system.

The same split applies to component props in React or Vue: props are object shapes (interfaces), while the component's variant prop ("primary" | "ghost") is a literal union (type alias). Once the two-rules mental model clicks, the choice stops being a debate and becomes a reflex.

// Domain entities: object shapes → interfaces
interface Category { id: number; slug: string; name: string }
interface Product {
  id: number;
  title: string;
  price: number;
  category: Category;
  inStock: boolean;
}

// API machinery: generics + unions → type aliases
type ApiOutcome<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: string; message: string } };

async function fetchProducts(): Promise<ApiOutcome<Product[]>> {
  const res = await fetch("/api/products");
  if (!res.ok) {
    return { ok: false, error: { code: "HTTP_" + res.status, message: res.statusText } };
  }
  return { ok: true, data: (await res.json()) as Product[] };
}

// Consumer: narrowing makes the unhappy path explicit
const outcome = await fetchProducts();
if (outcome.ok) {
  renderGrid(outcome.data);          // Product[] — fully typed
} else {
  showError(outcome.error.message);  // error object — fully typed
}

6. Frequently Asked Questions (FAQs)

Can an interface describe a union type like string | number?

No — interfaces can only describe object shapes. For unions, tuples, primitives, function signatures, or mapped types, use a type alias. This is the single most common reason code reaches for type over interface.

What is declaration merging and when is it useful?

When you declare two interfaces with the same name, TypeScript merges their members into one interface. It's mainly useful for augmenting third-party library types — for example, adding a userId field to Express's Request interface — without modifying the library's source code.

Do interfaces exist at runtime?

No. Like all type annotations, interfaces are completely erased during compilation and produce zero JavaScript output. They exist purely for the compiler and your editor — which is why they can never affect runtime behavior or be inspected with reflection.

Which is faster for the TypeScript compiler, interface or type?

Interfaces are marginally cheaper because their named declarations cache well during checking, but the difference is negligible except in gigantic codebases with deeply recursive types. Choose based on expressiveness and team convention, never on this micro-difference.

Should our team standardize on interfaces or types?

Standardize the convention, not a single keyword: interfaces for object shapes and public API contracts, type aliases for unions, tuples, functions, and mapped types. Document it once in your contributing guide and enforce it in code review — consistency is what pays off.
