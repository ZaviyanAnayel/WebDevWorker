1. What SSH Keys Are — and Why They Beat Passwords

Every time you type a server password or paste a GitHub token, you are doing security the hard way. SSH keys replace that with public-key cryptography: a private key stays on your computer (never shared), and a public key is placed on every server or service you want to access. When you connect, the server issues a challenge only your private key can answer — no password crosses the network.

This is both safer and more convenient. Keys are immune to brute-force password guessing and phishing, they cannot be intercepted and replayed like typed passwords, and with ssh-agent you unlock the key once per session instead of typing credentials dozens of times a day.

You will use SSH keys for two things constantly: pushing to GitHub without typing a password, and logging into servers without one. Set them up once, and the daily friction of development drops noticeably.

The math behind it is elegant: the public key can verify signatures but cannot create them, so publishing it widely is safe by design. Even if an attacker collects every public key you have ever shared, they learn nothing that helps them impersonate you.

2. Generating Your Key Pair

One command creates your key pair. Modern guidance is clear: use ed25519 — it is faster, smaller, and more secure than RSA at equivalent strength, and universally supported now.

# Generate an ed25519 key pair (accept defaults, set a passphrase)
ssh-keygen -t ed25519 -C "you@example.com"

# Your keys live here:
#   ~/.ssh/id_ed25519      (PRIVATE - never share)
#   ~/.ssh/id_ed25519.pub  (public - safe to upload anywhere)
AlgorithmCommand FlagVerdict for 2026
ed25519-t ed25519Default choice: fast, secure, compact
RSA 4096-t rsa -b 4096Use only for legacy systems lacking ed25519
ECDSA-t ecdsaFine, but no advantage over ed25519
DSA-t dsaDeprecated — do not use

Always set a passphrase. It encrypts the private key on disk, so a stolen laptop does not mean stolen server access. The next section shows how to type it only once per session.

3. Using ssh-agent (Type Your Passphrase Once)

ssh-agent is a background helper that holds your decrypted key in memory. Unlock it once, and every SSH and Git operation for the rest of your session just works.

# Start the agent and add your key
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# Make it permanent: add to ~/.ssh/config
Host *
  AddKeysToAgent yes
  IdentityFile ~/.ssh/id_ed25519

On macOS the passphrase is stored in the Keychain automatically; on Windows, Git Bash and WSL support ssh-agent the same way. Verify everything with ssh-add -l, which lists the loaded keys and their fingerprints.

The ~/.ssh/config file is worth learning beyond this: it lets you define short host aliases (Host prod → full hostname, user, key, and port), turning ssh -i ~/.ssh/prod.pem -p 2222 deploy@203.0.113.10 into ssh prod.

A complete host entry shows the pattern — one block per server, holding everything SSH needs:

Host prod
  HostName 203.0.113.10
  User deploy
  Port 2222
  IdentityFile ~/.ssh/prod_ed25519

Now ssh prod, scp file prod:/tmp/, and even VS Code's Remote-SSH all use the alias. One config file, zero memorized flags.

4. Adding Your Key to GitHub and Your Servers

Your public key (.pub) is meant to be shared — that is the whole design. For servers, ssh-copy-id installs it in one step. For GitHub, paste it into Settings → SSH and GPG keys.

# Copy your key to a server (uses password one final time)
ssh-copy-id user@server.com

# Display your public key to paste into GitHub
cat ~/.ssh/id_ed25519.pub

# Test the GitHub connection
ssh -T git@github.com
# Hi username! You've successfully authenticated.

After this, change your Git remotes from HTTPS to SSH (git@github.com:owner/repo.git) with git remote set-url — or clone with SSH from the start — and pushes will never ask for a password again.

On the server side, your key lands in ~/.ssh/authorized_keys. You can manage that file manually to grant or revoke access per key — each line is one key, and deleting a line instantly revokes that device.

For teams, consider key options in authorized_keys: a prefix like command="/usr/local/bin/deploy.sh" restricts a key to running a single script — perfect for CI deploy keys that should never get an interactive shell.

5. Locking Down and Troubleshooting SSH

SSH is powerful, so harden it. On any server you manage, disable password authentication entirely once keys work — this single change defeats virtually all automated brute-force attacks.

# /etc/ssh/sshd_config hardening (then: sudo systemctl reload ssh)
PasswordAuthentication no
PermitRootLogin no
MaxAuthTries 3

# Key files must have strict permissions
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys ~/.ssh/id_ed25519

When something fails, add -v (verbose, up to -vvv) to see exactly which authentication methods were tried: ssh -v user@server. The classic Permission denied (publickey) is almost always one of three things: the public key is not in authorized_keys, file permissions are too open, or you are offering the wrong private key — all visible in verbose output.

6. Frequently Asked Questions (FAQs)

What is the difference between SSH and HTTPS for Git?

Both are encrypted. SSH uses your key pair, so you never type credentials after setup. HTTPS asks for a username and personal access token on each new device. SSH is more convenient for daily work on your own machines; HTTPS is simpler on shared or temporary computers.

Should I put a passphrase on my SSH key?

Yes. A passphrase encrypts the private key file, so someone who steals your laptop still cannot use the key. Combined with ssh-agent, you type it once per session, so the security costs you almost nothing.

Can I use the same SSH key on multiple computers?

You can, but it is better to generate a separate key pair per device. That way, if one laptop is lost or compromised, you revoke just its key on GitHub and your servers without touching your other machines.

How do I fix Permission denied (publickey)?

Run ssh -v to see the details, then check: is your public key in the server's ~/.ssh/authorized_keys, are permissions set to 700 on ~/.ssh and 600 on key files, and are you connecting as the right user with the right key? Nine times out of ten it is one of these.

Is ed25519 really better than RSA?

For new keys, yes. Ed25519 keys are shorter, faster to generate and use, and provide security comparable to RSA-3072 in just 256 bits. Every modern OpenSSH version, GitHub, and GitLab supports it. Only fall back to RSA-4096 for ancient systems.
