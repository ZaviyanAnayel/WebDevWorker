1. What Makes an App a PWA

A Progressive Web App is a website that adopts three capabilities: it is capable (it can do app-like things with modern web APIs), reliable (it loads fast and works offline), and installable (users can add it to their home screen or desktop and launch it like a native app). There is no single framework or app-store wrapper required — these are platform features of the web itself.

The business case is well documented: installable web apps remove the friction of app-store downloads, which is where most acquisition funnels leak. Companies that ship PWAs routinely report higher engagement, better repeat-visit rates, and meaningful conversion lifts, because an icon on the home screen is a permanent re-engagement channel that costs nothing to maintain.

Just as important is what a PWA is not. It is not a hybrid wrapper, not a separate codebase, and not a replacement for your website — it is your website, progressively enhanced. Every user gets the fast baseline experience; users on supporting browsers additionally get installation, offline support, and push notifications.

2. The Web App Manifest: Your App's Identity

The web app manifest is a JSON file that tells the browser who your app is: its name, icons, colors, and how it should behave when launched. Without a manifest, there is nothing to install — the browser has no icon to show, no theme color for the splash screen, and no display mode to apply. It is the single most overlooked PWA requirement.

Get the icons right and everything else follows. Provide a 192px and a 512px icon at minimum, add maskable variants so Android can apply adaptive-icon shapes without cropping your logo, and include screenshots so install dialogs look rich. Set display to standalone for a native-app feel, and match theme_color with your meta name="theme-color" tag so the splash screen blends into your UI.

Common mistakes: a manifest linked with the wrong MIME-adjacent path, icons that 404, start_url pointing somewhere other than your entry point, and forgetting id, which keeps the installed app's identity stable across manifest edits. Validate with DevTools' Application panel, which flags every missing field explicitly.

3. Service Workers: Reliability and Offline Support

Reliability is the pillar users feel first. The app shell architecture splits your app into the static shell (layout, navigation, styles) and the dynamic content (data). The service worker precaches the shell during installation, so repeat visits paint instantly — even on a flaky train connection — while content loads progressively around it.

Layer runtime caching on top of the precache: cache-first for versioned assets, network-first with an offline fallback for navigations, and stale-while-revalidate for data that can be slightly old. The goal is a simple contract with the user — the app always opens, and content is as fresh as the connection allows.

Design the offline experience deliberately instead of treating it as an error state. Show cached data with a subtle offline badge, queue mutations for background sync, and make the offline page genuinely useful — recent content, key actions, and a clear path back when connectivity returns. Offline is a feature, not a failure.

4. Installability: Criteria and the Install Prompt

For Chrome and Edge to offer installation, your app must clear a checklist: served over HTTPS, a manifest with name plus 192px and 512px icons, a registered service worker with a fetch handler, and a start_url that loads. Miss any one of these and the install prompt silently never appears — which is why installability bugs are so often misdiagnosed as browser issues.

Never wait passively for the browser's mini-infobar. Capture the beforeinstallprompt event, stash it, and surface your own install button at a moment of high intent — right after a user completes a task or enables notifications. Your own UI converts dramatically better than a browser banner, and you control exactly when the ask happens.

On iOS, installation happens through Share and then Add to Home Screen rather than an automatic prompt, so include a short coach-mark for iPhone users. Once installed, respect the display-mode: standalone media query to hide browser-only chrome, and handle the appinstalled event to log conversions and dismiss your install nudges.

// Capture the install prompt and show it at the right moment
let deferredPrompt = null;

window.addEventListener("beforeinstallprompt", (event) => {
  event.preventDefault();          // hold it until the user shows intent
  deferredPrompt = event;
  document.getElementById("installBtn").hidden = false;
});

document.getElementById("installBtn").addEventListener("click", async () => {
  if (!deferredPrompt) return;
  deferredPrompt.prompt();                       // show the browser dialog
  const { outcome } = await deferredPrompt.userChoice;
  console.log("Install choice:", outcome);       // "accepted" or "dismissed"
  deferredPrompt = null;
  document.getElementById("installBtn").hidden = true;
});

window.addEventListener("appinstalled", () => {
  console.log("PWA installed — log the conversion");
});

5. Push Notifications and Re-engagement

An installed PWA with push permission is a re-engagement channel that rivals native apps. But permission is fragile: asking on first load trains users to tap Block forever. Ask only after delivering value — after a completed task, a saved preference, or an explicit settings toggle — and explain exactly what the notifications will contain.

The flow has three parts: the page subscribes through the PushManager and gets an endpoint URL plus encryption keys, your server stores the subscription, and when something happens your server sends an encrypted payload to the push service, which wakes the service worker — even with no tabs open — to display the notification.

Treat push as a privilege, not a megaphone. Send notifications that are timely, personal, and actionable; give users granular controls over notification types; and always deep-link into the relevant screen. One irrelevant blast can cost you the permission permanently, while well-targeted pushes measurably lift 30-day retention.

// Subscribe the user to push notifications
async function subscribeToPush() {
  const reg = await navigator.serviceWorker.ready;
  const permission = await Notification.requestPermission();
  if (permission !== "granted") return null;

  const subscription = await reg.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlBase64ToUint8Array(PUBLIC_VAPID_KEY)
  });

  // Send the subscription to your server for storage
  await fetch("/api/push/subscribe", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(subscription)
  });
  return subscription;
}

// In the service worker: render the notification on push
self.addEventListener("push", (event) => {
  const data = event.data ? event.data.json() : {};
  event.waitUntil(
    self.registration.showNotification(data.title || "TaskBoard", {
      body: data.body || "Something needs your attention.",
      icon: "/icons/icon-192.png",
      data: { url: data.url || "/" }
    })
  );
});

6. Frequently Asked Questions (FAQs)

Do PWAs work on iPhone?

Yes. iOS supports the core PWA features — installable web apps, service workers, and offline caching — through Add to Home Screen. Some capabilities such as push notifications and background sync have historically been limited on iOS, so check current platform support for features you depend on.

Can a PWA access native device features?

Modern PWAs can access cameras, geolocation, Bluetooth, file systems, contacts, and more through web APIs, with the exact set varying by browser and OS. For most business apps the web platform now covers everything needed; only deep OS integration still favors native.

Do I need to publish my PWA in an app store?

No. Users install PWAs directly from the browser with no store involved, and you deploy updates instantly by deploying your website. Stores like Google Play do accept PWAs packaged with tools like Bubblewrap, but it is optional.

How do users install a PWA?

On Android and desktop Chrome or Edge, the browser offers an install prompt when your app meets the installability criteria, and you can also trigger it from your own install button. On iOS, users tap Share and then Add to Home Screen.

Are PWAs good for SEO?

Excellent. A PWA is a website, so it is crawlable, linkable, and indexable like any page — a major advantage over native apps. Fast load times and offline reliability further help the page experience signals Google uses in ranking.

Keep leveling up

PWAs turn your website into an app users keep. Ship the manifest, the worker, and the install prompt — then measure how many visitors choose to install.
