1. What HTTP Request Methods Are

Every HTTP request starts with a request line: a method, a path, and a protocol version. The method (also called the verb) tells the server what kind of operation the client wants — read data, create something, update, or delete.

GET /api/users/42 HTTP/1.1
Host: example.com
Accept: application/json

The method is a contract. When your frontend sends DELETE /api/users/42, every layer — browser, CDN, proxy, framework — understands the intent without reading your documentation. Using methods correctly is what makes an API RESTful; using POST for everything is what makes it a guessing game.

HTTP defines nine standard methods, but five do nearly all the work in web development: GET, POST, PUT, PATCH, and DELETE. Master these five and you have mastered REST semantics.

The remaining four — HEAD, OPTIONS, TRACE, and CONNECT — play supporting roles: HEAD fetches headers without a body (great for checking whether a resource changed), and OPTIONS powers the CORS preflight requests your browser sends automatically. You will encounter them, but rarely define them yourself.

2. GET and POST: Reading vs Creating

GET retrieves a resource and must not change anything on the server. Parameters travel in the URL query string, responses are cacheable, and browsers can safely retry GETs — which is why refreshing a page never creates a duplicate order.

POST submits data to be processed, most commonly creating a new resource. The payload travels in the request body, keeping URLs clean and allowing large or sensitive data that should never appear in logs or browser history.

// GET: read a user (cacheable, no side effects)
const user = await fetch('/api/users/42').then(r => r.json());

// POST: create a user (body carries the data)
const created = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Ada', email: 'ada@example.com' }),
}).then(r => r.json());

The rule of thumb: if the operation only reads, it is a GET. If it creates something new (or triggers a process like sending an email), it is a POST. A successful POST conventionally returns 201 Created with the new resource's URL.

3. PUT, PATCH, and DELETE: Updating and Removing

PUT replaces an entire resource: you send the complete new representation, and the server swaps it in. PATCH applies a partial update: you send only the fields that changed. This distinction matters for APIs — PUT with missing fields typically clears them, while PATCH leaves untouched fields alone.

DELETE removes the resource at the URL. Successful deletes return 204 No Content (nothing to show) or 200 with a confirmation.

import express from 'express';
const app = express();
app.use(express.json());

// PUT: full replacement — client sends the ENTIRE user object
app.put('/api/users/:id', (req, res) => {
  users[req.params.id] = { id: req.params.id, ...req.body };
  res.json(users[req.params.id]);
});

// PATCH: partial update — only the provided fields change
app.patch('/api/users/:id', (req, res) => {
  Object.assign(users[req.params.id], req.body);
  res.json(users[req.params.id]);
});

// DELETE: remove the resource
app.delete('/api/users/:id', (req, res) => {
  delete users[req.params.id];
  res.status(204).end();
});

Notice the URL pattern: the resource (/api/users/42) stays constant while the method expresses the action. That is REST's core elegance — nouns in the URL, verbs in the method.

4. Safe and Idempotent: The Two Properties That Matter

Two formal properties determine how infrastructure treats your requests. A method is safe if it never modifies server state — safe requests can be prefetched, cached, and retried freely. A method is idempotent if making the same request N times has the same effect as making it once — idempotent requests can be safely retried after network failures.

MethodSafeIdempotentHas BodyTypical Use
GETYesYesNoRead a resource
POSTNoNoYesCreate a resource
PUTNoYesYesReplace a resource
PATCHNoUsually*YesPartial update
DELETENoYesNoRemove a resource

Why idempotency matters in practice: if a PUT request times out, the client can retry without fear — setting the price to $19 twice still leaves it at $19. Retrying a POST might charge the customer twice, which is why payment APIs use idempotency keys to make even POSTs safe to retry.

5. Using Methods Correctly in REST APIs

Correct method usage is a checklist, not a philosophy. Name resources with plural nouns (/api/orders, not /api/getOrders), let the method carry the verb, and return the right status codes: 200 for success, 201 for created, 204 for deleted, 400 for bad input, 404 for missing resources.

# Explore any API's method semantics with curl
curl -X GET https://api.example.com/users/42
curl -X POST https://api.example.com/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Ada"}'
curl -X DELETE https://api.example.com/users/42 -i

Common mistakes to avoid: using GET for actions with side effects (a GET /delete-account link can be triggered by a crawler or prefetcher), tunneling everything through POST, and returning 200 for errors instead of proper 4xx codes. Get the methods right and your API becomes self-documenting.

One last habit: document your methods with an OpenAPI spec. When the spec declares that PATCH /api/users/{id} accepts a partial user object, client SDKs, docs, and validation can all be generated from that single source of truth.

6. Frequently Asked Questions (FAQs)

What is the difference between PUT and PATCH?

PUT replaces the entire resource with the representation you send — omitted fields are typically cleared. PATCH applies a partial update, changing only the fields you include. Use PUT when the client manages the full resource state, PATCH for targeted edits.

Is POST idempotent?

No. Repeating a POST generally creates additional resources or triggers the action again — submitting an order form twice may create two orders. If safe retries matter, use PUT or add an idempotency key to your POST requests.

Can GET requests have a body?

Technically the spec does not forbid it, but in practice many servers, proxies, and clients ignore or reject GET bodies. Pass parameters in the query string instead — it is cacheable, bookmarkable, and universally supported.

Which HTTP method should I use to delete a resource?

DELETE. Send it to the resource's URL, like DELETE /api/users/42. Return 204 No Content on success. Avoid GET-based deletion links, since crawlers and prefetchers can trigger them unintentionally.

What does idempotent mean in simple terms?

Doing it twice has the same result as doing it once. Deleting a user twice leaves the user deleted either way, so DELETE is idempotent. Placing the same order twice creates two orders, so that POST is not.
