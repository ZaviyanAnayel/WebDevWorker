1. The Problem: Drowning in Events

Some browser events fire at a furious rate: scroll can emit dozens of events per second, resize fires continuously while dragging a window edge, and input fires on every keystroke. Running expensive work — an API search, a layout measurement, a re-render — on every single event melts CPUs, hammers APIs, and drops frames. Your handler is not too slow; it is simply called too often.

Debounce and throttle are the two canonical answers, and they solve different halves of the problem. Debounce says “wait until the events stop, then run once” — ideal when you only care about the final state. Throttle says “run at most once per interval while events continue” — ideal when you need regular updates during continuous activity. Confusing them produces bugs that feel intermittent: a throttled search input fires mid-typing; a debounced scroll handler never updates while scrolling.

Both are higher-order functions: they take your function and return a wrapped version with timing behavior. The implementations are each under fifteen lines, and writing them once yourself — rather than copying a snippet — is what makes the difference between them stick permanently.

// The problem: this fires on EVERY keystroke
document.querySelector('#search').addEventListener('input', (e) => {
  fetch(`/api/search?q=${e.target.value}`); // 10 keystrokes = 10 requests!
});

// Scroll handlers have the same disease
window.addEventListener('scroll', () => {
  document.querySelectorAll('.reveal').forEach(checkVisibility); // per frame!
});

2. Debounce: Wait Until It Stops

Debounce restarts a timer on every call and only invokes your function when the timer survives uninterrupted for the full wait period. Typing “javasc” then pausing fires one search for the complete term; each keystroke before the pause just resets the clock. The implementation is a closure over a timeout id: clear the pending timer, set a new one.

The classic options are leading and trailing edge. Trailing (the default) runs after the quiet period — right for search inputs and autosave. Leading runs immediately on the first call, then ignores subsequent calls until the wait elapses — right for “submit once” buttons where double-clicks must not double-submit. Some implementations support both; know which edge your use case needs before reaching for options.

Choose the wait to match human rhythm: 200–300ms for search-as-you-type, 500–1000ms for autosave and resize-recalculation. Too short and you barely save any calls; too long and the UI feels dead. And always cancel pending debounced calls on teardown — a debounced save firing after its component unmounted is a real-world bug.

function debounce(fn, wait = 300, { leading = false } = {}) {
  let timeoutId = null;
  return function (...args) {
    const callNow = leading && timeoutId === null;
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => {
      timeoutId = null;
      if (!leading) fn.apply(this, args); // trailing edge
    }, wait);
    if (callNow) fn.apply(this, args);     // leading edge
  };
}

// Search input: one request per pause in typing
const search = debounce((query) => {
  fetch(`/api/search?q=${encodeURIComponent(query)}`)
    .then(r => r.json()).then(renderResults);
}, 250);

document.querySelector('#search')
  .addEventListener('input', (e) => search(e.target.value.trim()));

3. Throttle: At Most Once Per Interval

Throttle guarantees your function runs at most once per interval no matter how many events arrive. The simplest implementation records the last run timestamp and executes only when enough time has passed; a refined version also schedules a trailing call so the final state is never skipped (a scroll handler that never renders the last 200ms of scrolling feels broken).

For visual updates during scroll, requestAnimationFrame is the idiomatic throttle: it naturally caps execution to the display's refresh rate and aligns work with the browser's paint cycle. A tiny rAF-throttle wrapper — “if no frame is scheduled, schedule one” — replaces timestamp math entirely for animation-adjacent handlers.

Throttle intervals follow the same human-rhythm logic: ~100ms for scroll-linked effects (parallax, reveal-on-scroll), 200–500ms for resize recalculation, and rAF for anything that moves pixels. Longer than ~500ms and continuous interactions start feeling steppy rather than smooth.

function throttle(fn, interval = 200) {
  let lastRun = 0;
  let timeoutId = null;
  return function (...args) {
    const now = Date.now();
    const remaining = interval - (now - lastRun);
    clearTimeout(timeoutId);
    if (remaining <= 0) {
      lastRun = now;
      fn.apply(this, args); // leading edge: run now
    } else {
      // trailing edge: guarantee the final state runs
      timeoutId = setTimeout(() => {
        lastRun = Date.now();
        fn.apply(this, args);
      }, remaining);
    }
  };
}

// rAF throttle: perfect cadence for scroll-driven visuals
function rafThrottle(fn) {
  let scheduled = false;
  return function (...args) {
    if (scheduled) return;
    scheduled = true;
    requestAnimationFrame(() => {
      scheduled = false;
      fn.apply(this, args);
    });
  };
}

window.addEventListener('scroll',
  rafThrottle(() => updateParallax(window.scrollY)), { passive: true });

4. Choosing Between Them: Real-World Rules

The decision rule fits in one sentence: if you want the final state after activity stops, debounce; if you want regular updates while activity continues, throttle. Search inputs, autosave, and window-resize recalculation debounce. Scroll effects, mousemove tracking, and live character counters throttle.

Watch for the hybrid cases. Infinite scroll typically throttles the scroll check (regular polling while scrolling) but the actual data fetch is naturally once-per-threshold. A resize handler that re-lays-out a chart usually debounces at ~250ms — but if the layout is cheap and the chart should track the drag live, throttle at ~100ms instead. Let the cost of the work and the need for liveness decide, not habit.

In frameworks, wrap the debounced/throttled function once (useMemo, a module-level definition, or a ref) — recreating it every render resets its internal timer and silently disables the rate limiting. And remember cleanup: cancelAnimationFrame, clearTimeout, and removeEventListener for anything you scheduled, or background tabs will keep doing phantom work.

// Resize: debounce expensive re-layout until dragging pauses
const relayout = debounce(() => {
  chart.resize(window.innerWidth, window.innerHeight);
  repositionOverlays();
}, 250);
window.addEventListener('resize', relayout);

// Mousemove: throttle live coordinate readout
const readout = throttle((x, y) => {
  coordsEl.textContent = `${x}, ${y}`;
}, 100);
canvas.addEventListener('mousemove', (e) => readout(e.clientX, e.clientY));

// Cleanup matters: cancel pending work on teardown
// (framework unmount, SPA navigation, component destroy)
window.removeEventListener('resize', relayout);

5. Debounce vs Throttle Cheat Sheet

This table is the whole guide on one card: the behavior, the canonical use cases, and the failure mode of picking the wrong one. When a teammate asks “should this be debounced or throttled?”, walk down the middle column together and let the use case decide confidently.

Both patterns share the same three engineering duties: create the wrapped function once so its internal timer survives across events, pick an interval that matches human perception rather than an arbitrary round number, and clean up timers and listeners on teardown. Get those three right and event storms become a solved problem rather than a recurring production fire.

6. Frequently Asked Questions (FAQs)

What is the real difference between debounce and throttle?

Debounce waits for a pause in events and then runs once (final state wins); throttle runs at most once per fixed interval while events keep coming (regular updates win). Search inputs debounce; scroll handlers throttle.

How do I write debounce from scratch?

Return a wrapper function that closes over a timeout id: on each call, clearTimeout the pending timer and set a new one for `wait` ms that invokes the original function. Only the last call in a burst survives, because every earlier timer gets cleared.

What are leading and trailing edge?

Leading edge runs the function immediately on the first call of a burst (then ignores the rest); trailing edge — the default — runs after the quiet period ends. Use leading for submit buttons (first click wins) and trailing for search inputs (final text wins).

When should I use throttle instead of debounce?

When you need updates during continuous activity rather than after it stops: scroll-linked animations, parallax, mousemove coordinates, live resize previews. If the user must see feedback while the event stream is still flowing, throttle.

Can I use requestAnimationFrame as a throttle?

Yes, and for visual updates it is the best throttle: it caps execution to the display refresh rate and syncs work with the browser's paint cycle. It only fits animation-adjacent handlers, though — for API calls or autosave, use time-based debounce/throttle instead.
