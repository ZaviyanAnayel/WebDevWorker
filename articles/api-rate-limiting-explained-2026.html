1. Why Every API Needs Rate Limiting

Rate limiting caps how many requests a client can make in a given period. It exists for four reasons that compound on each other: protecting your infrastructure from accidental and malicious overload, keeping one abusive client from degrading service for everyone else, defending expensive endpoints (AI inference, report generation, search) from cost explosions, and making your pricing tiers enforceable. An API without rate limiting is one misconfigured client loop away from an outage — or a surprise cloud bill.

Limits also shape client behavior for the better. When developers know the budget, they batch requests, cache aggressively, and implement backoff — all of which reduce your load. The alternative, silent throttling or IP bans with no communication, produces confused integrators and support tickets. Good rate limiting is as much a developer-experience feature as a protective one.

Decide what you are limiting by: per API key for authenticated traffic, per IP for anonymous traffic, and per user for abuse-sensitive actions like login attempts or password resets. Different endpoints deserve different budgets — a GET /status health check and a POST /generate-report job should never share a limit.

2. Fixed Window and Sliding Window

The fixed window algorithm is the simplest: divide time into windows (say, one minute each) and allow N requests per window per client, resetting the counter when the window rolls over. It is trivial to implement with a single counter in Redis, but it has a well-known flaw — the boundary spike. A client can make N requests at 12:00:59 and N more at 12:01:01, effectively doubling the intended rate across the boundary.

The sliding window fixes this by tracking individual request timestamps (or a rolling weighted count) so the "last 60 seconds" is always a true rolling period. It eliminates boundary spikes and is fairer, at the cost of more memory — you store timestamps instead of one counter. A popular middle ground is the sliding-window counter, which weights the previous window's count by overlap and needs only two counters per client.

For most APIs, the practical choice is: fixed window when simplicity matters and slight burstiness is acceptable (internal tools, low-stakes endpoints), sliding window when fairness at boundaries matters (public APIs, billing-adjacent limits). Both are easy to reason about, which is their real advantage over cleverer schemes.

3. Token Bucket and Leaky Bucket

The token bucket is the most flexible algorithm in common use. Each client has a bucket holding up to capacity tokens; tokens refill at a steady rate; each request consumes one token, and requests with an empty bucket are rejected. The beauty is that it allows controlled bursts — a client that has been idle accumulates tokens and can burst up to capacity — while the long-term average never exceeds the refill rate. That matches real traffic better than rigid windows.

Here is a compact in-memory implementation showing the core logic:

class TokenBucket {
  constructor(capacity, refillPerSecond) {
    this.capacity = capacity;
    this.tokens = capacity;
    this.refillPerSecond = refillPerSecond;
    this.lastRefill = Date.now();
  }
  take() {
    const now = Date.now();
    // Refill based on elapsed time, capped at capacity
    this.tokens = Math.min(
      this.capacity,
      this.tokens + ((now - this.lastRefill) / 1000) * this.refillPerSecond
    );
    this.lastRefill = now;
    if (this.tokens < 1) return false; // rate limited
    this.tokens -= 1;
    return true;
  }
}
// 100-request burst capacity, sustained 10 requests/second afterwards
const bucket = new TokenBucket(100, 10);

The leaky bucket is the token bucket's mirror image: requests enter a queue and leak out at a constant rate, which smooths bursts into perfectly even traffic. It is ideal when downstream systems need a steady flow (a payment processor that penalizes spikes), but it is less forgiving to legitimate bursty clients. In practice, token bucket dominates for APIs because burst tolerance matches how real clients behave.

4. Implementing Limits in Node.js

For production Node.js APIs, do not hand-roll distributed rate limiting — use a proven middleware backed by Redis so limits are shared across all your server instances. The express-rate-limit package with a Redis store is the standard starting point:

const rateLimit = require('express-rate-limit');
const RedisStore = require('rate-limit-redis');

// General API limit: 100 requests per 15 minutes per IP
const apiLimiter = rateLimit({
  store: new RedisStore({ /* redis client options */ }),
  windowMs: 15 * 60 * 1000,
  max: 100,
  standardHeaders: true,  // sends RateLimit-* headers (see section 5)
  legacyHeaders: false,
  message: { error: 'Too many requests, please slow down.' },
});
app.use('/api/', apiLimiter);

// Stricter limit for expensive endpoints
const expensiveLimiter = rateLimit({
  store: new RedisStore({ /* ... */ }),
  windowMs: 60 * 60 * 1000,
  max: 10,
  keyGenerator: (req) => req.user?.apiKey || req.ip, // limit by key, not IP
});
app.use('/api/v1/reports', expensiveLimiter);

Three production details matter enormously. First, key by API key or user ID for authenticated traffic — IP-based limiting punishes everyone behind a shared NAT or corporate proxy. Second, put rate limiting behind your authentication middleware when keys exist, so the key is available to the key generator. Third, treat the limiter as critical path: if Redis goes down, fail open for read endpoints (degraded but alive) and fail closed for expensive or abuse-sensitive ones, and alert immediately.

5. Communicating Limits: Headers and 429s

Clients can only respect limits they can see. The IETF standardized RateLimit-* response headers (RFC 9652), and you should send them on every response, not just rejections:

# Headers on a normal response: client sees budget and reset time
RateLimit-Limit: 100
RateLimit-Remaining: 87
RateLimit-Reset: 42

# On rejection: HTTP 429 with Retry-After (seconds or HTTP date)
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 38
Retry-After: 38
Content-Type: application/json

{ "error": "rate_limit_exceeded",
  "message": "You have exceeded 100 requests per 15 minutes.",
  "retry_after_seconds": 38 }

Document your limits prominently: the default budget per tier, which endpoints have special limits, and the exact backoff behavior you expect. Recommend exponential backoff with jitter in your client SDKs — it prevents the thundering-herd retry storms that turn a brief limit breach into a sustained outage. And never use rate limiting as your only abuse defense for login or signup endpoints; pair it with CAPTCHA or proof-of-work challenges, because distributed credential stuffing rotates IPs faster than any per-IP limit can track.

6. Frequently Asked Questions (FAQs)

What is the difference between throttling and rate limiting?

Rate limiting rejects requests over a defined budget (usually with HTTP 429), while throttling slows them down — queueing or delaying excess requests instead of refusing them. Rate limiting is simpler and standard for APIs; throttling suits cases where every request must eventually be served, like background job intake.

Should I rate limit by IP address or API key?

By API key (or user ID) for authenticated traffic — it identifies the actual client and survives shared NATs, VPNs, and corporate proxies that put many users behind one IP. Use per-IP limits only for anonymous endpoints like signup or login, where no key exists yet.

What HTTP status code should a rate limiter return?

429 Too Many Requests, with a Retry-After header telling the client how long to wait. Include the RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset headers so clients can manage their budget proactively instead of discovering the limit by hitting it.

How do token bucket and fixed window differ in practice?

Fixed window counts requests in rigid time blocks and can allow double the intended rate across a window boundary. Token bucket refills continuously and permits controlled bursts up to its capacity while capping the long-term average. Token bucket matches real bursty client traffic more fairly; fixed window is simpler to implement.

Can rate limiting stop DDoS attacks?

Not alone. Rate limiting protects application logic from abuse and accidental overload, but volumetric DDoS attacks saturate network capacity before your limiter even runs. Pair API rate limiting with a CDN or dedicated DDoS mitigation service at the edge for network-layer floods.
