1. JSON Syntax: The Rules That Matter

JSON (JavaScript Object Notation) looks simple — and mostly is — but its strictness surprises developers coming from JavaScript. JSON is a subset of JavaScript literal syntax with tighter rules: keys must be double-quoted, strings must use double quotes (no single quotes), trailing commas are forbidden, and comments are not allowed. A payload that works fine as a JS object literal can be invalid JSON.

JSON supports exactly six data types: objects, arrays, strings, numbers, booleans, and null. There is no date type, no undefined, no functions, no comments, and no distinction between integers and floats — everything numeric is just a "number". This minimalism is why JSON won: every language can map these six types onto its own, and parsers stay small and fast.

The most common syntax errors are worth memorizing because you will hit them in logs for years: single-quoted strings, trailing commas after the last array element or object property, unquoted keys, and comments pasted from documentation. When a parser rejects your payload, check those four first — they account for the vast majority of "unexpected token" errors.

{
  "name": "Ada Lovelace",
  "born": 1815,
  "active": true,
  "languages": ["Analytical Engine", "Bernoulli numbers"],
  "mentor": null,
  "address": { "city": "London", "postcode": "W1" }
}
// Valid JSON. Now the classic mistakes:
// { 'name': 'Ada' }        -> single quotes are INVALID
// { "name": "Ada", }       -> trailing comma is INVALID
// { name: "Ada" }          -> unquoted key is INVALID

2. Parsing JSON Safely in JavaScript and Python

Parsing turns a JSON string into native data structures. In JavaScript, JSON.parse throws a SyntaxError on invalid input, so any parse of untrusted or external data belongs inside try/catch — a crashed Node process or a broken UI over one malformed webhook payload is an avoidable outage:

// JavaScript: always guard parses of external data
function safeParse(jsonString) {
  try {
    return { ok: true, data: JSON.parse(jsonString) };
  } catch (err) {
    console.error('Invalid JSON payload:', err.message);
    return { ok: false, data: null };
  }
}

// Reviver: transform values during parsing (e.g. ISO dates -> Date objects)
const data = JSON.parse(payload, (key, value) =>
  key === 'createdAt' ? new Date(value) : value
);

Python's json.loads raises json.JSONDecodeError (a subclass of ValueError) on bad input, so the same try/except discipline applies. One Python-specific note: json.loads accepts single-quoted strings only if you pre-process them — do not; fix the producer instead, because silently "fixing" malformed JSON hides data-integrity bugs.

import json

try:
    data = json.loads(payload)
except json.JSONDecodeError as e:
    print(f"Bad payload at line {e.lineno}, column {e.colno}: {e.msg}")
    data = None

# object_hook: customize how JSON objects become Python objects
from collections import namedtuple
User = namedtuple('User', ['name', 'email'])
user = json.loads('{"name": "Ada", "email": "ada@example.com"}',
                  object_hook=lambda d: User(**d))

Never parse JSON with eval() — it executes arbitrary code and is the textbook route to injection. JSON.parse and json.loads are purpose-built, fast, and safe.

3. JSON.stringify: Replacers, Spacing, and Gotchas

JSON.stringify converts values back to a JSON string, and its optional arguments solve real problems. The second argument — the replacer — lets you filter or transform properties, which is how you strip secrets before logging or sending data to the client:

const user = { id: 7, name: 'Ada', passwordHash: '...', token: '...' };

// Replacer as an array: whitelist exactly the fields to include
JSON.stringify(user, ['id', 'name']);
// -> '{"id":7,"name":"Ada"}'  (secrets never leave the server)

// Replacer as a function: full control over transformation
JSON.stringify(user, (key, value) =>
  key === 'createdAt' && value instanceof Date ? value.toISOString() : value
);

// Third argument: pretty-print with 2-space indentation for logs and files
JSON.stringify(user, null, 2);

Know the gotchas: undefined, functions, and symbols are silently dropped from objects (and become null in arrays); Date objects serialize via toISOString(); circular references throw a TypeError (use a cycle-detecting replacer or a library for those); and BigInt values throw unless you convert them to strings first. The silent dropping of undefined is the one that bites hardest — an object missing a key and an object with that key set to undefined serialize identically.

4. Dates, Big Numbers, and Other Edge Cases

JSON's six types leave gaps that every API designer must handle deliberately. Dates are the classic: there is no date type, so the convention is ISO 8601 strings ("2026-10-14T09:00:00Z") — always in UTC, always with an explicit offset or Z. Document the format in your API docs; "a date string" without a specified format is a bug waiting for a timezone.

Large integers are the subtler trap. JSON numbers are IEEE 754 doubles, so integers beyond 2^53 lose precision — a real problem for 64-bit database IDs and snowflake-style identifiers. The safe pattern is to serialize such IDs as strings and document it. Twitter's API famously moved to string IDs for exactly this reason.

Duplicate object keys deserve a callout: the JSON spec says behavior is unpredictable, and most parsers silently keep the last value — a potential vector for smuggling data past validation. Strict parsers and schema validators can flag duplicates; lenient ones will not.

5. Validating Structure with JSON Schema

When JSON crosses a trust boundary — public APIs, webhooks, config files — "it parsed successfully" is not enough. You need to know the shape is right: required fields present, types correct, values in range. JSON Schema is the standard vocabulary for declaring those rules, and validators exist for every major language:

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "User",
  "type": "object",
  "required": ["name", "email"],
  "properties": {
    "name":  { "type": "string", "minLength": 1, "maxLength": 100 },
    "email": { "type": "string", "format": "email" },
    "age":   { "type": "integer", "minimum": 0, "maximum": 150 },
    "tags":  { "type": "array", "items": { "type": "string" }, "maxItems": 20 }
  },
  "additionalProperties": false
}

Validate on the server with a library (Ajv for JavaScript, jsonschema for Python), and fail closed: reject payloads that do not match rather than coercing them. additionalProperties: false is the strictness knob most teams underuse — it turns "typo in a field name silently ignored" into "clear 400 error", which is vastly easier to debug.

JSON Schema also doubles as documentation: publish your schemas alongside your API reference and clients can generate types, mocks, and tests from them. For internal TypeScript projects, tools that derive schemas from types (or types from schemas) keep the contract and the code from drifting apart.

6. Frequently Asked Questions (FAQs)

Why does JSON require double quotes instead of single quotes?

JSON was designed as a strict, minimal interchange format, and its specification only allows double-quoted strings and keys. Single quotes, trailing commas, and comments are all invalid. The strictness is deliberate: it keeps parsers small, fast, and consistent across every programming language.

How should I handle dates in JSON?

Use ISO 8601 strings in UTC, like 2026-10-14T09:00:00Z, and document the format explicitly in your API docs. There is no native JSON date type, so the string convention plus a documented format is the interoperable standard. Parse them into native date objects on receipt with a reviver or object_hook.

Why do large IDs lose precision in JSON?

JSON numbers are IEEE 754 double-precision floats, which cannot exactly represent integers beyond 2^53. Database IDs or snowflake identifiers larger than that get rounded. Serialize such IDs as strings and document the convention — this is why many public APIs return IDs like "id": "1234567890123456789".

What is the difference between JSON.parse and eval?

JSON.parse only understands JSON data and throws on anything else, making it safe for untrusted input. eval() executes arbitrary JavaScript, so parsing attacker-controlled JSON with eval hands them code execution. Never use eval for JSON — there is no case where it is the right tool.

When should I use JSON Schema?

Whenever JSON crosses a trust boundary: public API inputs, webhook payloads, and configuration files. Schema validation checks that required fields exist, types are correct, and values are in range — catching malformed or malicious payloads that merely parsing successfully would let through.
