1. Setting Up Flask and Your First Route

Flask calls itself a microframework, and the name is honest: the core is deliberately tiny. Instead of handing you an ORM, an admin panel, and an authentication system you never asked for, Flask gives you routing, request handling, and templates — then gets out of your way. That minimalism is exactly why it remains one of the best first frameworks in 2026: every moving part is visible, so you learn how the web actually works instead of learning one framework's magic.

Start with a virtual environment so Flask and its dependencies never collide with other projects on your machine. On most systems that means running python -m venv venv, activating it, and then pip install flask. Isolating dependencies is a habit worth building on day one — production servers, Docker images, and CI pipelines all expect your packages to be pinned in a requirements file rather than installed globally.

A minimal Flask app is five meaningful lines: create the app object, attach a view function to a URL with the @app.route decorator, and return a response. Run it with python app.py and the development server starts on http://127.0.0.1:5000, with debug mode giving you automatic reloading and an in-browser debugger when something crashes. Debug mode is a development-only superpower — it must never be enabled on a public server, a point we will return to in the deployment section.

from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello, Flask — your first route works!"

@app.route("/hello/<name>")
def greet(name):
    return f"Hello, {name}!"

if __name__ == "__main__":
    app.run(debug=True)

2. Rendering Templates with Jinja2

Returning HTML strings from view functions works for a demo and becomes miserable the moment a page needs real markup. Flask's answer is Jinja2, a template engine that keeps your Python logic in .py files and your markup in a templates/ folder beside your app. The call render_template("team.html", members=members) loads the template, fills in the variables you pass, and returns finished HTML.

Jinja2's syntax is deliberately small: {{ variable }} prints a value, {% for m in members %} loops, and {% if user %} branches. Everything printed with {{ }} is HTML-escaped by default, which quietly neutralizes the most common cross-site scripting (XSS) mistakes beginners make. You only bypass escaping with the |safe filter when you are certain the HTML is yours — a rule that will save you from genuine vulnerabilities later.

Template inheritance is the feature that keeps larger sites sane. You define base.html once with your doctype, navigation, and footer, mark the changing regions with {% block content %}, and every page extends the base and fills in only its own block. Change the navigation in one file and the whole site updates — the same DRY principle you already apply to Python code.

# app.py
from flask import Flask, render_template

app = Flask(__name__)

@app.route("/team")
def team():
    members = ["Ayesha", "Bilal", "Chen"]
    return render_template("team.html", members=members)

<!-- templates/team.html -->
{% extends "base.html" %}
{% block content %}
  <h1>Our Team</h1>
  <ul>
  {% for m in members %}
    <li>{{ m }}</li>
  {% endfor %}
  </ul>
{% endblock %}

3. Handling Forms and User Input

Forms are where a site stops being a brochure and starts being an application. A Flask view that accepts a form declares methods=["GET", "POST"]: GET renders the empty form, POST receives the submission. Submitted fields arrive in the request.form dictionary, keyed by each input's name attribute — request.form.get("email") is a line you will write a hundred times, so learn its shape early.

After processing a POST, never render a template directly. Redirect instead — return redirect(url_for("contact")) — in what is called the Post/Redirect/Get pattern. Without it, a user who refreshes the confirmation page resubmits the form, creating duplicate orders, duplicate comments, or duplicate database rows. The redirect is a single line and it eliminates an entire class of bugs.

Two habits separate toy forms from production forms. First, validate everything server-side even if JavaScript already validated it in the browser, because browser checks are trivially bypassed; Flask-WTF makes this pleasant and adds CSRF protection tokens automatically. Second, use flash() messages to confirm what happened, so users never wonder whether their click registered.

from flask import Flask, render_template, request, redirect, url_for, flash

app = Flask(__name__)
app.secret_key = "change-this-in-production"

@app.route("/contact", methods=["GET", "POST"])
def contact():
    if request.method == "POST":
        email = request.form.get("email", "").strip()
        if "@" not in email:
            flash("Please enter a valid email address.")
            return render_template("contact.html")
        # save the message to your database here...
        flash("Thanks! We will be in touch.")
        return redirect(url_for("contact"))  # Post/Redirect/Get
    return render_template("contact.html")

4. Structuring a Real Flask Project

A single app.py carries you surprisingly far — then one day it doesn't, and untangling 800 lines is nobody's idea of fun. The conventional layout splits concerns: an app package with __init__.py holding an application factory, route logic grouped into blueprint modules, a templates/ folder, a static/ folder for CSS and images, and a config module. Imports stay clean because nothing reaches across layers it shouldn't.

The application factory — a create_app() function that builds and returns the Flask instance — is the pattern production Flask code is written in. It lets you create multiple app instances with different configurations for development, testing, and production, which is exactly what a real test suite needs. Configuration itself lives in classes or environment variables, never hardcoded in the source you commit.

Blueprints are Flask's answer to a growing route list: group related views such as auth, blog, and admin into separate modules and register each with app.register_blueprint(). A url_prefix like "/auth" keeps URLs organized automatically. Combined with the factory pattern, blueprints turn a weekend project into a codebase a team can actually work in.

# app/auth.py
from flask import Blueprint

auth_bp = Blueprint("auth", __name__, url_prefix="/auth")

@auth_bp.route("/login")
def login():
    return "Login page goes here"

# app/__init__.py
from flask import Flask
from .auth import auth_bp

def create_app():
    app = Flask(__name__)
    app.config["SECRET_KEY"] = "change-this-in-production"
    app.register_blueprint(auth_bp)
    return app

5. Running and Deploying Your Flask App

Flask's built-in server exists for development: it is single-threaded, it reloads your code, and it is not hardened for the open internet. Production means putting a real WSGI server in front — Gunicorn on Linux, typically run as gunicorn -w 4 "app:create_app()", or Waitress if you need something cross-platform — usually behind Nginx, which handles TLS termination, static files, and slow clients.

Configuration is the other half of production readiness. Secrets like SECRET_KEY and database URLs must come from environment variables, never from committed code; the python-dotenv package loads a local .env file during development so the pattern stays identical everywhere. Keep debug mode off in production (it defaults to off), and pin your dependencies in requirements.txt so every deploy installs exactly what you tested.

Where you deploy matters less than how: a small VPS, Render, Railway, or a Docker container all work because a WSGI app is ultimately just a Python process. Whichever you choose, add a process manager or platform health check so the app restarts if it crashes, and put structured logging in place before launch — the first production bug is dramatically cheaper when you can actually see it.

6. Frequently Asked Questions (FAQs)

Is Flask still worth learning in 2026?

Absolutely. Flask powers a huge number of production APIs and internal tools, its small core teaches you how HTTP, routing, and templating actually work, and the extension ecosystem covers databases, authentication, and more. Learning Flask first makes every other web framework easier to understand.

Should I learn Flask or Django first?

Choose Flask if you want to understand each piece of a web app and move fast on smaller projects or APIs. Choose Django if you want batteries included — admin panel, ORM, and authentication out of the box — for larger, convention-driven projects. Many developers learn Flask first and pick up Django quickly afterward.

Can Flask handle real production traffic?

Yes, when deployed correctly. The development server is not for production, but Flask behind Gunicorn or uWSGI with multiple workers, fronted by Nginx, comfortably serves thousands of requests per second. Scaling further is about caching, database tuning, and horizontal replicas — the same as with any framework.

How do I connect a database to Flask?

Use Flask-SQLAlchemy: define Python model classes, point the app at a database URI, and query with an ORM instead of raw SQL. Add Flask-Migrate to version your schema changes over time. This stack scales from a SQLite prototype to production PostgreSQL.

Does Flask support async views?

Flask 2.x lets you write async def view functions, but it remains fundamentally a synchronous WSGI framework. If your app is I/O-heavy with many concurrent connections — streaming, websockets, high-fanout APIs — FastAPI or another ASGI framework is the better tool for the job.
