1. How a CSRF Attack Actually Works

Cross-site request forgery exploits a simple fact: browsers automatically attach cookies to every request, including requests triggered by someone else's page. Imagine you are logged into your bank. You then visit a malicious forum page containing a hidden form that auto-submits a transfer request to the bank's domain. Your browser dutifully includes your session cookie, the bank sees a valid authenticated request, and the transfer goes through. You never clicked anything on the bank's site.

The attack works because the bank cannot distinguish a request your page made from a request a hostile page made — both carry the same cookie. CSRF does not steal your session; it rides it. That is also why it primarily threatens state-changing requests: transfers, password changes, email updates, deletions. Read-only GET requests that merely display data are less useful to an attacker, which is why the first rule of CSRF defense is architectural: never change state on a GET request.

Here is what the attacker's page looks like — a form that needs zero interaction from the victim beyond loading the page:

<!-- Attacker's page: auto-submits a forged request to the victim's bank -->
<body onload="document.forms[0].submit()">
  <form action="https://bank.example/transfer" method="POST">
    <input type="hidden" name="to" value="attacker-account">
    <input type="hidden" name="amount" value="5000">
  </form>
</body>
<!-- The victim's browser attaches their bank session cookie automatically. -->

Notice there is no JavaScript trickery beyond auto-submit and no stolen credentials. The defense must therefore give the server a way to verify that the request genuinely originated from its own pages — which is exactly what CSRF tokens do.

2. Synchronizer Tokens: The Standard Defense

The synchronizer token pattern is the standard CSRF defense and the one frameworks implement for you. The server generates a unique, unpredictable token per user session, embeds it in every form (or exposes it to JavaScript for AJAX), and requires it on every state-changing request. The attacker's page cannot read the token because the same-origin policy prevents cross-origin pages from reading your site's responses — so the forged request arrives without a valid token and is rejected.

The token must be cryptographically random (at least 128 bits), tied to the user's session, and compared in constant time to avoid timing leaks. It should also rotate when privilege levels change, such as at login. Double-submit cookies — where the token is stored in a cookie and echoed back in the request body — are a stateless alternative, but they are weaker when subdomains can be compromised, so prefer server-side token storage.

For AJAX-heavy applications, the common pattern is to render the token into a meta tag and attach it as a custom header on every fetch call:

<!-- Server renders the token where your JS can read it -->
<meta name="csrf-token" content="a3f9c21e7b4d4e8f9a0b1c2d3e4f5061">

<script>
// Attach the token to every state-changing request
const token = document.querySelector('meta[name="csrf-token"]').content;
async function apiPost(url, data) {
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-CSRF-Token': token },
    body: JSON.stringify(data),
    credentials: 'same-origin'
  });
  return res.json();
}
</script>

The server then validates that the X-CSRF-Token header matches the token stored for the session before processing anything else in the request.

3. SameSite Cookies and Additional Layers

The SameSite cookie attribute is the most impactful CSRF mitigation browsers have shipped in years. Setting SameSite=Lax tells the browser not to send the cookie on cross-site POST requests — which kills the classic auto-submit attack outright — while still sending it on top-level navigations so normal links keep working. SameSite=Strict goes further and withholds the cookie on all cross-site requests, at the cost of users appearing logged out when they arrive from an external link.

SameSite is a powerful layer, but it is not a complete defense on its own. Older browsers may ignore it, some legitimate flows (cross-site payment callbacks, certain SSO redirects) need SameSite=None; Secure, and it does nothing against same-site attacks like XSS. Treat it as one layer in a stack: SameSite cookies plus synchronizer tokens plus state-changing-only-on-POST/PUT/DELETE.

# Set-Cookie with modern CSRF-aware attributes
Set-Cookie: sessionid=abc123; Path=/; HttpOnly; Secure; SameSite=Lax

# Strict for highly sensitive apps (note the UX trade-off on external links)
Set-Cookie: sessionid=abc123; Path=/; HttpOnly; Secure; SameSite=Strict

Two more layers worth knowing: verifying the Origin and Referer headers on state-changing requests (cheap, effective, though headers can be suppressed by privacy tools, so use as a complement), and requiring re-authentication or a one-time confirmation for the most sensitive actions like password changes and payouts.

4. Implementing CSRF Protection in Express and Django

In Express, the csurf package was long the default but is now deprecated; modern apps typically use csrf-csrf (double-submit) or a small custom middleware with server-side token storage. Here is a minimal, correct custom implementation:

const crypto = require('crypto');

// Issue a token per session and expose it to views
app.use((req, res, next) => {
  if (!req.session.csrfToken) {
    req.session.csrfToken = crypto.randomBytes(32).toString('hex');
  }
  res.locals.csrfToken = req.session.csrfToken;
  next();
});

// Verify on every state-changing route
function verifyCsrf(req, res, next) {
  const sent = req.body._csrf || req.headers['x-csrf-token'];
  const expected = req.session.csrfToken;
  const ok = sent && expected &&
    crypto.timingSafeEqual(Buffer.from(sent), Buffer.from(expected));
  if (!ok) return res.status(403).json({ error: 'Invalid CSRF token' });
  next();
}
app.post('/transfer', verifyCsrf, (req, res) => { /* ... */ });

Django developers get this out of the box: the CsrfViewMiddleware is enabled by default, templates use {% csrf_token %}, and AJAX requests read the csrftoken cookie. The main Django gotcha is forgetting the token in JavaScript-driven forms or disabling the middleware "temporarily" and shipping it that way. In Rails, protect_from_forgery with: :exception plays the same role. Whatever your stack, prefer the framework's built-in implementation over hand-rolled crypto.

5. CSRF Checklist for SPAs and APIs

Single-page applications and pure APIs need a slightly different checklist than server-rendered apps. If your API uses cookie-based sessions, everything above applies — tokens are still required. If your API uses bearer tokens (Authorization headers) instead of cookies, CSRF is largely a non-issue because the browser does not automatically attach bearer tokens to cross-site requests; the attacker cannot forge the header. Many teams therefore choose token-based auth for SPAs precisely to sidestep CSRF.

ScenarioSession MechanismCSRF RiskRecommended Defense
Server-rendered formsCookiesHighSynchronizer tokens + SameSite=Lax
SPA + cookie sessionCookiesHighToken in header + SameSite=Lax
SPA + bearer/JWTAuthorization headerLowNo CSRF token needed; guard against XSS instead
Cross-site embeds/widgetsCookies with SameSite=NoneMediumTokens required; narrow widget permissions

Final checklist before you ship: state changes never happen on GET; every POST, PUT, PATCH, and DELETE validates a token or is exempt for a documented reason; cookies carry SameSite=Lax (or Strict where UX allows) plus Secure and HttpOnly; and your most sensitive actions demand fresh authentication. Get those right and CSRF drops off your threat list.

6. Frequently Asked Questions (FAQs)

What is the difference between CSRF and XSS?

XSS injects malicious scripts into your pages that run in victims' browsers; CSRF tricks a victim's browser into making an unwanted request to your site using their existing session. XSS steals the session, CSRF rides it. Defenses differ: XSS needs output encoding and CSP, while CSRF needs tokens and SameSite cookies.

Do I need CSRF protection if my API uses JWT bearer tokens?

Generally no. Browsers automatically attach cookies to cross-site requests but never automatically attach Authorization headers, so an attacker cannot forge a bearer-token request from their page. If your SPA stores the JWT in a cookie instead of memory or localStorage, however, CSRF protection is still required.

Is SameSite=Lax enough to prevent CSRF on its own?

It stops the classic cross-site POST attack in modern browsers, but it is not complete: older browsers ignore it, some flows need SameSite=None, and it does nothing against same-site attacks. Use it as a strong layer alongside synchronizer tokens, not as the only defense.

Why should state-changing actions never use GET requests?

GET requests are triggered by links, images, and prefetches without user intent, and browsers attach cookies to all of them — making CSRF trivial. They are also logged in server logs and browser history. Reserve GET for safe, read-only operations and require POST, PUT, PATCH, or DELETE for anything that changes state.

What is the double-submit cookie pattern?

The server sets the CSRF token in a cookie and the client echoes the same value back in a request parameter or header; the server accepts the request when the two match. It is stateless and simple, but weaker than server-side token storage if an attacker can write cookies from a subdomain. Prefer synchronizer tokens for sensitive applications.

Keep leveling up

Combine CSRF tokens with SameSite cookies, strict security headers, and XSS defenses to make forged and injected requests fail before they reach your logic.
