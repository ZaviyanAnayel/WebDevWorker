1. Setting Up Jest and Writing Your First Test

Jest remains the most popular JavaScript test runner because it works with zero configuration for most projects: test runner, assertion library, mocking, and coverage ship in one package. Install it, write a file ending in .test.js, and run npx jest — Jest discovers tests, executes them in parallel workers, and reports results with a readable diff on failure.

npm install --save-dev jest

// sum.js
function sum(a, b) {
  return a + b;
}
module.exports = sum;

// sum.test.js
const sum = require("./sum");

test("adds 1 + 2 to equal 3", () => {
  expect(sum(1, 2)).toBe(3);
});

// package.json
{
  "scripts": { "test": "jest", "test:watch": "jest --watch" }
}

For TypeScript, add ts-jest or @swc/jest as the transform so type-stripping happens before tests run — SWC is the faster choice in 2026. Jest picks up tests matching **/__tests__/**/*.[jt]s?(x) and **/?(*.)+(spec|test).[jt]s?(x) by default; colocating test files next to source keeps imports short and makes ownership obvious.

Run Jest in watch mode during development: it re-runs only tests related to changed files, giving feedback in under a second on most codebases. That tight loop is what turns testing from a chore into a design tool — you write the test, watch it fail, then make it pass.

2. Matchers and Test Structure

Matchers are Jest's assertion vocabulary, and choosing the right one makes failures readable. Use toBe for primitives (it checks Object.is identity), toEqual for deep object equality, and specialized matchers like toContain, toMatch, and toThrow where they fit. Structure suites with describe blocks for grouping and beforeEach/afterEach for setup and teardown.

const { calculateTotal } = require("./cart");

describe("calculateTotal", () => {
  let cart;

  beforeEach(() => {
    cart = [
      { name: "Keyboard", price: 89, qty: 1 },
      { name: "Mouse", price: 39, qty: 2 },
    ];
  });

  test("sums line items", () => {
    expect(calculateTotal(cart)).toBe(167);
  });

  test("applies discount codes", () => {
    expect(calculateTotal(cart, "SAVE10")).toBeCloseTo(150.3, 1);
  });

  test("rejects unknown discount codes", () => {
    expect(() => calculateTotal(cart, "NOPE")).toThrow(/unknown discount/i);
  });

  test("returns items matching a search", () => {
    const names = cart.map((i) => i.name);
    expect(names).toContain("Mouse");
    expect(cart).toEqual(expect.arrayContaining([
      expect.objectContaining({ name: "Keyboard" }),
    ]));
  });
});
MatcherUse it when
toBe(value)Comparing primitives: numbers, strings, booleans
toEqual(obj)Deep-comparing objects and arrays
toStrictEqual(obj)Deep compare including undefined keys and types
toContain(item)Checking arrays and strings for membership
toThrow(error)Asserting a function throws, optionally matching message
toBeCloseTo(n)Comparing floats where precision matters
expect.objectContainingMatching a subset of an object's properties

Keep tests focused on behavior, not implementation: assert what a function returns or what the user sees, not which internal helper it called. Tests coupled to internals break on every refactor and teach teams to fear changing code — the opposite of what a test suite is for.

3. Mocking: Functions, Modules and Timers

Mocking isolates the unit under test from its dependencies — network calls, databases, timers. jest.fn() creates a bare mock function that records calls; jest.mock() replaces an entire module; jest.spyOn() wraps a real method so you can observe it without replacing its behavior. Reach for mocks at boundaries (HTTP, filesystem, time), not for your own pure functions.

// userService.js depends on an HTTP client
const api = require("./api");
async function getUserName(id) {
  const user = await api.fetchUser(id);
  return user.name.toUpperCase();
}

// userService.test.js
jest.mock("./api"); // auto-mock the whole module
const api = require("./api");
const { getUserName } = require("./userService");

test("uppercases the fetched user name", async () => {
  api.fetchUser.mockResolvedValue({ name: "waseem" });
  await expect(getUserName(7)).resolves.toBe("WASEEM");
  expect(api.fetchUser).toHaveBeenCalledWith(7);
  expect(api.fetchUser).toHaveBeenCalledTimes(1);
});

test("spies observe without replacing", () => {
  const logger = { info: (m) => m };
  const spy = jest.spyOn(logger, "info");
  logger.info("hello");
  expect(spy).toHaveBeenCalledWith("hello");
  spy.mockRestore();
});

For time-dependent code, fake timers make tests deterministic: jest.useFakeTimers() replaces setTimeout and Date, then jest.advanceTimersByTime(5000) moves the clock forward instantly. Modern fake timers (@sinonjs/fake-timers under the hood) even fake queueMicrotask and requestAnimationFrame, so debounced UI logic becomes testable without real waits.

One caution: over-mocking produces tests that pass while the app is broken. If you mock every module your code touches, you are testing the mocks. Prefer testing through public interfaces, and reserve full module mocks for I/O boundaries you genuinely cannot hit in a unit test.

4. Testing Async Code and the DOM

Async tests just return a promise — Jest waits for it. Use async/await with resolves/rejects matchers for promise assertions, and always await the assertion itself; a floating promise makes the test pass vacuously. For DOM testing, Jest's default jsdom environment gives you document and window, and Testing Library's @testing-library/dom (or the React/Vue bindings) lets you interact the way users do.

import { getByRole, fireEvent } from "@testing-library/dom";

function renderCounter() {
  document.body.innerHTML = `<button data-testid="inc">Count: 0</button>`;
  const btn = document.querySelector("[data-testid='inc']");
  let n = 0;
  btn.addEventListener("click", () => {
    n += 1;
    btn.textContent = `Count: ${n}`;
  });
  return btn;
}

test("increments the counter on click", () => {
  const btn = renderCounter();
  fireEvent.click(getByRole(document.body, "button"));
  fireEvent.click(getByRole(document.body, "button"));
  expect(btn.textContent).toBe("Count: 2");
});

test("async fetch flow", async () => {
  api.fetchUser.mockResolvedValue({ name: "waseem" });
  await expect(getUserName(7)).resolves.toBe("WASEEM");
});

Query by role, label, or text — the same affordances assistive technology uses — and reserve data-testid for elements with no semantic hook. This keeps tests resilient to markup refactors and nudges you toward accessible markup as a side effect. For API-heavy flows, Mock Service Worker (MSW) intercepts requests at the network layer, so components exercise their real fetch logic against realistic fixtures.

5. Coverage and CI Integration

Coverage tells you which lines never executed during tests — useful as a spotlight, dangerous as a target. Enable it with --coverage and set thresholds in config so CI fails when coverage drops, but treat 100% as information, not a mandate: chasing the last percent usually means testing getters instead of behavior.

// jest.config.js
module.exports = {
  testEnvironment: "jsdom",
  collectCoverageFrom: ["src/**/*.{js,ts}", "!src/**/*.test.{js,ts}"],
  coverageThreshold: {
    global: { branches: 80, functions: 85, lines: 85, statements: 85 },
  },
  coverageReporters: ["text", "lcov", "html"],
};

// .github/workflows/test.yml
- name: Run tests with coverage
  run: npx jest --coverage --ci --maxWorkers=2
- name: Upload coverage
  uses: codecov/codecov-action@v4

In CI, run Jest with --ci (fails instead of watching, treats snapshots strictly) and cap workers with --maxWorkers so parallel jobs do not starve each other. Cache node_modules and Jest's cache directory between runs. A suite that takes under five minutes in CI gets run on every PR; one that takes thirty gets skipped — speed is a feature of your testing strategy.

Finally, review uncovered lines regularly with the HTML report. Untested branches cluster around error handling and edge cases — exactly the code that fails in production. A coverage report read as a map of risk, not a vanity metric, is one of the highest-value artifacts your test suite produces.

6. Frequently Asked Questions (FAQs)

Do I still need Jest in 2026, or should I use Vitest?

Both are excellent. Vitest is faster and Vite-native, ideal for Vite projects. Jest remains the default for Create React App, Next.js, and React Native, with the largest plugin ecosystem. Choose based on your bundler, not hype.

How do I test TypeScript with Jest?

Add @swc/jest (fastest) or ts-jest as the transform in jest.config.js. SWC strips types without type-checking, so keep tsc --noEmit as a separate CI step for full type safety.

What is the difference between jest.fn(), jest.mock(), and jest.spyOn()?

jest.fn() creates a standalone mock function. jest.mock() replaces an entire module's exports. jest.spyOn() wraps an existing method to observe calls while keeping its real implementation.

Why do my async tests pass when they should fail?

You likely forgot to await the assertion or return the promise. A floating promise means Jest finishes the test before the assertion runs. Always await expect(promise).resolves... or return the promise chain.

What coverage percentage should I aim for?

Aim for 80 to 90 percent on statements and branches for application code, enforced via coverageThreshold. Treat coverage as a map of untested risk areas, not a goal — 100 percent coverage with weak assertions proves little.
