1. The Error Object and Why Errors Deserve Design

Most JavaScript developers treat errors as an afterthought: a console.error here, an empty catch {} there. Then production breaks, the logs say [object Object], and nobody can tell whether the failure was a network blip, a programming bug, or bad user input. Errors are a design surface — the taxonomy you choose determines whether your team can diagnose issues in minutes or days.

Every error in JavaScript is an object, usually an instance of Error or one of its built-ins: TypeError, RangeError, SyntaxError, ReferenceError, URIError, AggregateError, and EvalError. Each carries message, name, and a stack trace. The built-in types already communicate a category — a TypeError says "wrong type was used," a RangeError says "value out of bounds" — so throwing the right type is the cheapest documentation you can write.

The golden rule: throw Error objects, never strings. throw "failed" discards the stack trace and breaks every tool that expects .message and .stack. And the cause property (supported in all modern engines) lets you chain errors — wrap a low-level failure in a domain-level error without losing the original: throw new Error('Payment failed', { cause: originalError }). Your future on-call self will thank you.

2. try/catch/finally Done Right

try/catch is for recoverable, expected failures — network calls, JSON parsing, user input — not for papering over bugs. A catch block should either recover, translate the error into something the caller understands, or clean up and rethrow. The worst pattern in the wild is the silent swallow:

// BAD: hides bugs, lies about success
try {
  renderDashboard(user);
} catch (e) {} // nothing here. The dashboard is blank and nobody knows why.

// GOOD: handle what you expect, rethrow what you don't
try {
  const raw = localStorage.getItem('prefs');
  return raw ? JSON.parse(raw) : defaults;
} catch (err) {
  if (err instanceof SyntaxError) {
    reportCorruptPrefs();   // expected: user data can be corrupt
    return defaults;        // recover with a sane fallback
  }
  throw err; // unexpected: let it propagate to the global handler
} finally {
  hideLoadingSpinner(); // always runs: success, error, or early return
}

Use instanceof checks to discriminate: catch the SyntaxError from a JSON parse, rethrow the TypeError that indicates your own bug. The finally block is for unconditional cleanup — closing loaders, releasing locks, aborting controllers — and it runs even if the try block returns early or the catch rethrows.

Keep try blocks small and specific. Wrapping 200 lines in one try makes it impossible to know which statement failed and invites catching errors you never intended to handle. One operation per try, with the catch scoped to that operation's failure modes, is the professional shape.

3. Custom Error Classes for Real Applications

Built-in error types describe language-level failures, not your domain. When a payment fails, a quota is exceeded, or validation rejects input, a custom error class lets callers distinguish cases with instanceof instead of fragile string matching on messages:

class AppError extends Error {
  constructor(message, { code = 'UNKNOWN', status = 500, cause } = {}) {
    super(message, { cause });
    this.name = this.constructor.name;
    this.code = code;     // machine-readable: 'PAYMENT_DECLINED'
    this.status = status; // HTTP mapping for API responses
  }
}

class ValidationError extends AppError {
  constructor(field, message) {
    super(message, { code: 'VALIDATION_FAILED', status: 422 });
    this.field = field;
  }
}

class PaymentError extends AppError {
  constructor(message, cause) {
    super(message, { code: 'PAYMENT_FAILED', status: 502, cause });
  }
}

// Callers can now branch precisely
try {
  await checkout(cart);
} catch (err) {
  if (err instanceof ValidationError) {
    highlightField(err.field, err.message);
  } else if (err instanceof PaymentError) {
    showRetryDialog(err.message);
  } else {
    throw err; // genuinely unknown: escalate
  }
}

Two details matter. Set this.name so stack traces and logs identify the class, and always pass { cause } when wrapping so the original stack survives. A code property gives you a stable, localizable identifier — messages are for humans and change; codes are for logic and don't.

Resist the urge to create dozens of micro-classes. A small hierarchy — one base AppError with code/status, plus a handful of domain subclasses — covers nearly every app. What matters is that catching code can discriminate reliably, not that every failure has its own class name.

4. Async Errors: Promises, async/await, and Rejections

Async code has its own failure plumbing, and mixing the models is where errors silently vanish. Inside an async function, await converts rejections into thrown errors, so try/catch works naturally. Outside one — in .then() chains or fire-and-forget calls — you need .catch(), and an unhandled rejection will crash Node or spam the console in browsers:

// try/catch works with await — rejections become throws
async function loadUser(id) {
  try {
    const res = await fetch('/api/users/' + id);
    if (!res.ok) throw new AppError('User fetch failed', { status: res.status });
    return await res.json(); // can also throw on malformed JSON
  } catch (err) {
    logError(err);
    throw new AppError('Could not load user', { cause: err });
  }
}

// Parallel work: Promise.all fails fast; allSettled never throws
const results = await Promise.allSettled([loadUser(1), loadUser(2)]);
for (const r of results) {
  if (r.status === 'rejected') reportFailure(r.reason);
  else renderUser(r.value);
}

// Fire-and-forget MUST still handle rejection — never float a promise
saveDraft(draft).catch((err) => logError(err));

Remember that fetch only rejects on network failure — a 404 or 500 still resolves, so check res.ok yourself. And Promise.all rejects on the first failure while discarding the rest; when you need every outcome (bulk imports, fan-out requests), reach for Promise.allSettled and inspect each result.

For callback-based APIs, promisify once at the boundary so the rest of your code lives in one error model. And never let a promise float: an un-awaited, un-caught promise is a crash waiting for production traffic. Lint rules like no-floating-promises exist precisely for this.

5. Global Handlers and Production Error Reporting

No matter how careful your local handling is, something will escape — a bug in a rarely-hit branch, a third-party script throwing, a rejection nobody awaited. Global handlers are your last line of defense: they keep the app alive, show the user something sane, and ship the diagnostic to your error tracker.

// Catch synchronous errors and resource load failures
window.addEventListener('error', (event) => {
  // event.error: the Error object (for JS errors)
  // event.message, event.filename, event.lineno: location
  reportToTracker({
    message: event.message,
    stack: event.error?.stack,
    url: location.href,
    userAgent: navigator.userAgent,
  });
  showToast('Something went wrong. Our team has been notified.');
});

// Catch unhandled promise rejections (async escapes)
window.addEventListener('unhandledrejection', (event) => {
  event.preventDefault(); // we handled it: don't spam the console
  reportToTracker({ message: String(event.reason?.message || event.reason) });
});

// In Node.js: never let these pass silently
process.on('unhandledRejection', (reason) => { logger.fatal(reason); process.exit(1); });
process.on('uncaughtException', (err) => { logger.fatal(err); process.exit(1); });

In production, pair global handlers with an error-tracking service and include context: the route, the user action, the app version. In React, add an Error Boundary per major route so one crashing component shows a fallback instead of a blank page. And set up alerts on error-rate spikes — the handler that only writes to a dashboard nobody watches is barely better than catch {}.

6. Frequently Asked Questions (FAQs)

Should I wrap everything in try/catch?

No. Use try/catch for expected, recoverable failures like network requests, JSON parsing, and storage access. Programming bugs should surface loudly through global handlers and error tracking so they get fixed, not get silently swallowed by an over-eager catch block.

Why should I throw Error objects instead of strings?

Throwing a string discards the stack trace and breaks every tool that expects .message and .stack. Always throw new Error() or a custom subclass, and use the cause property to chain the original error when wrapping lower-level failures.

How do I handle fetch errors correctly?

Fetch only rejects on network failure, so a 404 or 500 still resolves. Always check response.ok and throw your own error for bad statuses, then handle JSON parse failures separately. Wrap the whole sequence in try/catch when using await.

What is an unhandled promise rejection?

It happens when a promise rejects but nothing awaits it or attaches .catch(). Browsers log it to the console; Node.js crashes the process. Listen for unhandledrejection globally as a safety net, but fix the source: never let promises float.

Can try/catch recover from syntax errors?

No. Syntax errors are thrown at parse time, before any code runs, so no try/catch in that script can catch them. They must be fixed in the source. Runtime errors — the ones your code can encounter while executing — are what try/catch is for.
