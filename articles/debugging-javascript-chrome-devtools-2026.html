1. Breakpoints That Do the Work

The Sources panel is where debugging happens. A line breakpoint pauses execution exactly where you click, but the real power is in conditional breakpoints: right-click a line number, choose Add conditional breakpoint, and enter an expression like user.id === 42. Execution pauses only when the condition holds — invaluable inside loops that run ten thousand times.

Logpoints are breakpoints that print instead of pausing: right-click, Add logpoint, and enter "cart total:", total. You get console output with zero code changes and zero restarts — perfect for production-adjacent debugging where you cannot edit files. XHR/fetch breakpoints pause when a request URL matches a substring, and event listener breakpoints (in the right-hand pane) pause on clicks, timers, or uncaught exceptions.

// Instead of littering code with console.log...
function applyDiscount(cart, code) {
  const rule = DISCOUNT_RULES[code]; // conditional breakpoint: code === "SAVE10"
  const total = cart.reduce((s, i) => s + i.price * i.qty, 0);
  return total * (1 - rule.rate);    // logpoint: "rate applied:", rule.rate
}

// ...set a conditional breakpoint on the rule lookup and a
// logpoint on the return. No edits, no rebuild, full visibility.

Learn the stepping keys and debugging becomes fluid: Step over (F10) runs the current line, Step into (F11) descends into function calls, Step out (Shift+F11) finishes the current function. Blackbox library scripts (right-click a file → Add script to ignore list) so stepping never descends into minified vendor code.

2. Scope, Call Stack and the Watch Panel

When paused, the right-hand Scope pane shows every variable visible at that point — local, closure, and global — with live values you can expand, and you can double-click any value to edit it mid-debug. Change a variable, resume execution, and watch the program take a different path: this “what-if” editing is the fastest way to test a hypothesis without restarting.

The Call Stack pane answers “ how did I get here?” Click any frame to inspect the variables as they were at that level — DevTools re-evaluates scope per frame. Async stack traces (enabled by default in modern Chrome) link setTimeout callbacks and promise continuations back to the code that scheduled them, which untangles the classic “who called this callback” mystery.

Pin expressions in the Watch pane to track values across steps: cart.items.length, response.status, or any expression re-evaluated on every pause. Combined with the Console drawer (press Esc to open a console alongside Sources), you can run arbitrary code in the paused frame's scope — call functions, inspect objects, even hot-patch a fix and continue.

3. Profiling Performance: Finding the Slow Parts

When the bug is slowness, not incorrectness, switch to the Performance panel. Hit record, interact with the page, stop — and you get a flame chart of exactly what the main thread did. Long tasks (blocking chunks over 50ms) show in red; click one to see its call tree and the precise function burning time. Most performance bugs are one expensive function hiding in an innocent-looking interaction.

// Mark sections of code to find them in the flame chart
function renderProductList(products) {
  performance.mark("render-start");
  const html = products.map(productCard).join("");
  document.getElementById("list").innerHTML = html;
  performance.mark("render-end");
  performance.measure("render-list", "render-start", "render-end");
}

// Long Task API: catch jank programmatically
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 100) {
      console.warn("Long task:", entry.duration.toFixed(0) + "ms");
    }
  }
});
observer.observe({ entryTypes: ["longtask"] });

The Memory panel tackles leaks: take heap snapshots before and after an operation, and compare them to find retained objects. The classic web leak is a forgotten event listener or timer keeping a detached DOM tree alive — the retainers view shows you exactly which reference chain prevents garbage collection.

For rendering issues, the Rendering drawer (DevTools → More tools) can paint flashing rectangles over repaints, highlight layout shift regions, and emulate a slow CPU. If the whole page flashes on every keystroke, you have found a repaint storm worth fixing with containment or virtualization.

4. Console Power Techniques

The Console is far more than console.log. console.table(users) renders arrays of objects as a sortable table; console.group()/groupEnd() nest related output; console.assert(condition, message) logs only when the condition fails. Styled logs with %c help important messages stand out in noisy output.

// Beyond console.log
console.table(cart.items, ["name", "price", "qty"]);

console.group("checkout");
console.log("items:", cart.items.length);
console.log("total:", total);
console.groupEnd();

console.assert(total > 0, "Total should never be zero", cart);

// Command-line superpowers (Console only)
// $0            – currently selected element in Elements panel
// $_            – result of the last evaluated expression
// copy(obj)     – copies object as JSON to clipboard
// monitor(fn)   – logs every call of fn with arguments
// getEventListeners(el) – lists listeners attached to an element
copy(document.querySelector("#app").dataset); // paste config anywhere

Live Expressions (the eye icon in the Console toolbar) pin an expression that re-evaluates continuously — watch document.querySelectorAll(".error").length update as you interact. And monitorEvents(element) logs every DOM event fired on an element, which demystifies components that “should” be emitting events but are not.

One discipline that multiplies all of this: reproduce the bug in the smallest possible case before reaching for tools. A minimal reproduction focuses the flame chart, the breakpoints, and your attention on the actual defect instead of application noise.

5. Debugging Production Issues

Production bugs cannot be reproduced locally — that is usually why they survived. Start with source maps: if your build uploads them (privately, never publicly), DevTools maps minified stack traces back to original files. The Overrides feature (Sources → Overrides) lets you save local copies of remote files and live-edit production code in your browser only, testing fixes against the real backend.

PanelReach for it when
SourcesStepping through logic, breakpoints, editing live code
ConsoleQuick probes, live expressions, command-line utilities
NetworkFailed requests, slow APIs, payload inspection
PerformanceJank, long tasks, scripting bottlenecks
MemoryGrowing heap, detached DOM, suspected leaks
ApplicationStorage, cookies, service workers, cache state

The Network panel's timing breakdown (queueing, DNS, TTFB, content download) tells you whether a slow request is the server or the client, and right-clicking a request lets you Copy as fetch to replay it in the Console. For errors users report but you cannot see, combine DevTools with real-user monitoring — session replay tools show you the user's exact clicks leading to the crash.

Build a personal debugging checklist and follow it in order: reproduce minimally, check the console for errors, verify network payloads, set breakpoints at the boundary, inspect scope, form a hypothesis, test it by editing live. Systematic beats brilliant — the developers who fix bugs fastest are rarely the ones who guess fastest.

6. Frequently Asked Questions (FAQs)

What is the difference between a breakpoint and a logpoint?

A breakpoint pauses execution so you can inspect state. A logpoint prints a message to the console without pausing and without modifying code. Use logpoints for tracing values through hot paths where pausing would be disruptive.

How do I debug minified production JavaScript?

Enable source maps in your build and upload them to a private location or error-tracking service. DevTools will map minified code back to your original sources for readable stack traces and breakpoints.

Why does my breakpoint show as unverified or never hit?

Common causes: the code runs before DevTools attaches, a service worker serves a cached bundle, or source maps point at stale files. Hard-reload with cache disabled, verify the file contents match, and check the file is actually executed.

What is blackboxing in DevTools?

Blackboxing (the ignore list) tells the debugger to skip library and framework scripts when stepping. Your Step Into stays in your code instead of descending into minified vendor bundles, making stepping dramatically faster.

How can I find a memory leak with DevTools?

Open the Memory panel, take a heap snapshot, perform the suspect operation, then take another snapshot and compare. Look for growing object counts and use the retainers view to find what keeps detached DOM nodes or closures alive.
