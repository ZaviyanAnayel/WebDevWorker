1. What Hooks Are and Why They Replaced Classes

Hooks are functions that let function components "hook into" React features — state, lifecycle, context, refs — that previously required class components. Since React 16.8, they have become the standard way to write React: the official docs teach hooks first, and every modern library ships hook-based APIs.

Classes forced awkward patterns: related logic got split across componentDidMount, componentDidUpdate, and componentWillUnmount, while unrelated logic piled into the same lifecycle method. Reusing stateful logic meant render props or higher-order components — wrapper hell. Hooks solve both: effects colocate setup and cleanup by concern, and custom hooks share logic with a plain function call.

Mentally, a hook is a function call that React tracks by call order. On every render, React walks your component's hook calls in the same sequence and matches each to its stored state. That ordering is the entire reason for the Rules of Hooks — call them unconditionally, in the same order, every render — and understanding it makes every hook behavior (stale closures, effect timing, ref persistence) click into place.

2. useState and useEffect: The Core Pair

useState declares component state; useEffect synchronizes with the outside world (network, DOM, subscriptions). Together they cover the vast majority of component logic:

import { useState, useEffect } from 'react';

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [status, setStatus] = useState('idle'); // 'idle' | 'loading' | 'error'

  useEffect(() => {
    let cancelled = false;
    setStatus('loading');
    fetch('/api/users/' + userId)
      .then((r) => { if (!r.ok) throw new Error('fetch failed'); return r.json(); })
      .then((data) => { if (!cancelled) { setUser(data); setStatus('idle'); } })
      .catch(() => { if (!cancelled) setStatus('error'); });
    return () => { cancelled = true; }; // cleanup: ignore late responses
  }, [userId]); // re-run only when userId changes

  // Functional updates: safe when new state depends on old state
  const [count, setCount] = useState(0);
  const incrementTwice = () => {
    setCount((c) => c + 1);
    setCount((c) => c + 1); // each updater sees the latest value
  };
}

Two habits separate beginners from professionals. First, functional updates (setCount(c => c + 1)) whenever the new state derives from the old — plain setCount(count + 1) reads a stale closure in rapid-fire handlers. Second, effect cleanup: every subscription, timer, or fetch started in an effect needs a cleanup function that cancels it, or you'll set state on unmounted components and leak listeners.

Choose state shape deliberately: keep state minimal and derive the rest. Don't store both firstName/lastName and fullName — compute fullName during render. And when several state values always change together, merge them into one object or reach for useReducer, which also shines for complex transitions like form wizards.

3. useRef, useMemo, and useCallback: Beyond the Basics

useRef gives you a mutable box that persists across renders without triggering re-renders when it changes. Its two jobs: holding DOM nodes and holding any mutable value (timers, previous values, counters) that shouldn't participate in rendering:

import { useRef, useMemo, useCallback } from 'react';

function SearchBox({ items, onSelect }) {
  const inputRef = useRef(null);      // 1. DOM access
  const prevQuery = useRef('');       // 2. mutable value, no re-render
  const renderCount = useRef(0);
  renderCount.current += 1;

  useEffect(() => { inputRef.current?.focus(); }, []);

  // useMemo: cache an EXPENSIVE computation, recompute only when items change
  const sorted = useMemo(() => {
    return [...items].sort((a, b) => a.score - b.score);
  }, [items]);

  // useCallback: stable function identity for memoized children
  const handleSelect = useCallback((id) => {
    prevQuery.current = inputRef.current.value;
    onSelect(id);
  }, [onSelect]);

  return (
    <>
      <input ref={inputRef} placeholder="Search..." />
      <ExpensiveList items={sorted} onSelect={handleSelect} />
    </>
  );
}

The key insight: useMemo memoizes a value, useCallback memoizes a function (it's literally useMemo(() => fn, deps)). They only pay off when the memoized thing feeds a memoized child (React.memo) or an effect dependency — memoizing a cheap computation that nothing depends on just adds overhead and dependency-array busywork.

Common useRef traps: reading ref.current during render is unreliable (it's for event handlers and effects), and mutating a ref doesn't re-render — if the UI must reflect the value, it belongs in state. A classic legitimate use is storing the latest callback in a ref to break an effect dependency cycle without stale closures.

4. The Rules of Hooks and the Dependency Array

Rule 1: only call hooks at the top level — never inside loops, conditions, or nested functions. Rule 2: only call hooks from React functions — components or custom hooks. Violating rule 1 scrambles React's call-order bookkeeping: after a conditional hook, every subsequent hook reads the wrong state slot, producing bugs that look like impossible behavior. The eslint-plugin-react-hooks rules catch these statically — keep them enabled and treat warnings as errors.

// BAD: conditional hook breaks call order
function Bad({ enabled }) {
  const [count, setCount] = useState(0);
  if (enabled) {
    useEffect(() => { /* ... */ }, []); // shifts every hook after it!
  }
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

// GOOD: condition goes INSIDE the hook
function Good({ enabled }) {
  const [count, setCount] = useState(0);
  useEffect(() => {
    if (!enabled) return;
    const id = setInterval(() => setCount((c) => c + 1), 1000);
    return () => clearInterval(id);
  }, [enabled]);
  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}

The dependency array answers "when should this effect re-run?" Every reactive value used inside the effect — props, state, and any function defined in the component — belongs in it. Omitting one creates a stale closure: the effect keeps seeing the first render's values. The exhaustive-deps lint rule will nag you; listen to it, and fix the warning by adding the dep, memoizing the function with useCallback, or moving the logic inside the effect.

An empty array [] means "run once after mount" — correct for truly one-time setup like focusing an input, wrong for anything reading props or state. If your effect needs latest values but shouldn't re-run, the ref pattern (store the value/callback in a ref, read it in the effect) is the escape hatch. And in React 18's StrictMode, effects mount-unmount-mount in development to surface missing cleanup — if your effect breaks under double-invocation, the effect (not StrictMode) is the bug.

5. Custom Hooks: Extracting Reusable Logic

A custom hook is just a function starting with use that calls other hooks. It lets you extract stateful logic — data fetching, form handling, media queries — into a tested, reusable unit without components or wrapper hierarchies. Each component that calls it gets independent state; hooks share logic, not data.

import { useState, useEffect } from 'react';

// Reusable: sync state with localStorage
export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const raw = localStorage.getItem(key);
      return raw !== null ? JSON.parse(raw) : initialValue;
    } catch { return initialValue; }
  });
  useEffect(() => {
    try { localStorage.setItem(key, JSON.stringify(value)); }
    catch { /* quota or private mode: fail silently */ }
  }, [key, value]);
  return [value, setValue];
}

// Reusable: fetch with loading/error states
export function useFetch(url) {
  const [data, setData] = useState(null);
  const [error, setError] = useState(null);
  useEffect(() => {
    let cancelled = false;
    setError(null);
    fetch(url)
      .then((r) => { if (!r.ok) throw new Error(r.statusText); return r.json(); })
      .then((d) => { if (!cancelled) setData(d); })
      .catch((e) => { if (!cancelled) setError(e); });
    return () => { cancelled = true; };
  }, [url]);
  return { data, error, loading: !data && !error };
}

// Usage: one line per concern, fully independent per component
function Settings() {
  const [theme, setTheme] = useLocalStorage('theme', 'dark');
  const { data: prefs } = useFetch('/api/prefs');
}

Name custom hooks after what they do (useLocalStorage, useDebounce), keep them focused on one concern, and return conventional shapes — [value, setter] for state-like hooks, objects for multi-value ones. Well-built custom hooks are where React codebases get their leverage: the third time you copy-paste an effect, extract it.

6. Frequently Asked Questions (FAQs)

Can I call hooks inside conditions or loops?

No. Hooks must be called unconditionally at the top level of your component or custom hook, in the same order on every render. React tracks hooks by call order, so a conditional hook shifts every hook after it into the wrong state slot. Put the condition inside the hook or inside an event handler instead.

When exactly does useEffect run?

After the component renders and the browser paints. With a dependency array, React re-runs the effect only when a listed value changed since the last render; with an empty array it runs once after mount; with no array it runs after every render. Cleanup from the previous run executes before the next one.

What is the difference between useMemo and useCallback?

useMemo caches a computed value; useCallback caches a function reference — it is shorthand for useMemo(() => fn, deps). Use them when the memoized value feeds a React.memo child or sits in an effect dependency array. Memoizing cheap values nothing depends on only adds overhead.

How do I share stateful logic between components?

Extract it into a custom hook: a function starting with use that calls built-in hooks. Each component calling it gets fully independent state — custom hooks share logic, not data. For genuinely shared data, combine custom hooks with Context or an external store.

Do hooks work in class components?

No. Hooks are exclusively for function components and custom hooks. Classes keep their lifecycle methods and this.setState. You can freely mix hook-based function components and class components in the same app while migrating incrementally.
