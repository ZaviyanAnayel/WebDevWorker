JavaScript Modules: ES import/export and Dynamic import() Explained

1. Why Modules Changed JavaScript Forever

Before ES modules arrived in 2015, every <script> tag dumped its variables into one shared global scope. Libraries survived by wrapping everything in IIFEs, load order was fragile, and two scripts defining utils would silently clobber each other. Debugging a large app meant untangling an invisible web of globals.

ES modules fixed this at the language level: each file is its own module with its own scope, dependencies are declared explicitly with import, and the public surface is declared with export. There are no globals unless you deliberately create them. This explicitness is what makes tree-shaking possible — bundlers can statically analyze the import graph and drop code nobody references.

In the browser, modules load with <script type="module">, which is deferred by default (it runs after HTML parsing, in order), and supports import statements natively. In Node.js, modules are the default in .mjs files or any package with "type": "module". One syntax, two runtimes — that universality is why every modern framework and bundler is built on top of it.

2. Named vs Default Exports: The Syntax That Matters

A module can expose values two ways. Named exports export multiple bindings by name; default export exports a single main value per module. They can be mixed, but understanding when to use each keeps your APIs predictable:

// math.js — named exports (preferred for utilities)
export const PI = 3.14159;
export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; }

// logger.js — default export (one main thing per module)
export default function log(message, level = 'info') {
  console[level]('[app]', message);
}

// app.js — importing both styles
import { add, multiply, PI } from './math.js';
import log from './logger.js';              // default: any name works
import log2, { add as sum } from './logger.js'; // mixed + aliasing
import * as math from './math.js';          // namespace import
console.log(math.add(2, 3));

Community consensus has settled: prefer named exports for most code because they make imports greppable and renames safe. Reserve default exports for modules that truly have one main export — a React component file, a class, or a configuration object. Re-exporting through barrel files (index.js files that re-export everything) is convenient but can slow down bundlers and hide circular dependencies, so use them sparingly in large codebases.

3. Module Mechanics: Scope, Strict Mode, and Live Bindings

Three mechanics surprise developers coming from scripts. First, modules are always strict mode — no opt-in needed, so accidental globals throw instead of silently appearing. Second, top-level variables stay in the module; nothing leaks to window unless you assign it there deliberately. Third, imports are live bindings, not copies:

// counter.js
export let count = 0;
export function increment() { count += 1; }

// app.js
import { count, increment } from './counter.js';
console.log(count); // 0
increment();
console.log(count); // 1 — the binding updated, not a snapshot
// count = 5;       // TypeError: imports are read-only in the importer

Live bindings mean an importer always sees the exporter's current value, but cannot reassign it — assignment must happen inside the exporting module. This one-way flow prevents spooky action at a distance while still allowing modules to share genuinely mutable state like caches or registries.

Also know that modules execute exactly once, no matter how many files import them. The first import evaluates the module; later imports reuse the cached instance. That singleton behavior is why modules are a natural home for shared configuration, connection pools, and event buses — but it also means top-level side effects (network calls, DOM writes) run at import time, which complicates testing. Keep module top-level code to declarations; put side effects behind exported functions.

4. Dynamic import(): Loading Code on Demand

Static import must sit at the top level and always loads eagerly. import() — a function-like expression — breaks both constraints: it can appear anywhere, takes a computed string, and returns a promise for the module namespace. This is the primitive behind route-based code splitting:

// Load a heavy charting library only when the user opens the dashboard
async function showDashboard() {
  showSpinner();
  try {
    const { renderCharts } = await import('./charts.js');
    renderCharts(document.getElementById('dashboard'));
  } catch (err) {
    showError('Could not load the dashboard. Check your connection.');
    console.error(err);
  } finally {
    hideSpinner();
  }
}

// Conditional polyfill: only load what the browser lacks
if (!('IntersectionObserver' in window)) {
  await import('./polyfills/intersection-observer.js');
}

Bundlers like Vite, webpack, and Rollup detect import() and automatically split the target into a separate chunk that loads on demand. Each dynamic import becomes its own network request, so group related lazy code into one module rather than scattering dozens of tiny dynamic imports. A common production pattern: React.lazy(() => import('./AdminPanel')) for admin routes, heavy editors, and anything behind a user interaction.

One caveat: the specifier in a browser must be a full URL or a relative path including the file extension ('./charts.js', not './charts'), because browsers perform no extension resolution. Bundlers usually forgive the omission during builds, but the native behavior is what runs in production if you ship unbundled modules.

5. Pitfalls: Circular Imports, Extensions, and Bundler Quirks

Circular imports — A imports B, B imports A — are legal but treacherous. Because modules evaluate in dependency order, one side of the cycle will observe the other's exports before they are initialized, reading undefined or hitting the temporal dead zone. The fix is architectural: extract the shared piece into a third module both can import, or defer access so the circular reference is only touched inside functions that run after evaluation completes.

// DANGER: a.js and b.js import each other
// a.js
import { b } from './b.js';
export const a = 'a';
console.log('a sees b as:', b); // undefined! b.js hasn't finished evaluating

// FIX: move shared state to c.js, imported by both
// c.js
export const shared = {};
// a.js and b.js each: import { shared } from './c.js';

File extensions and bare specifiers: browsers require relative paths with extensions; import 'lodash' (a bare specifier) only works with an import map or a bundler. If you ship native ES modules, add an <script type="importmap"> mapping bare names to URLs. JSON modules need an import attribute (import data from './data.json' with { type: 'json' }) in modern browsers — the old assert syntax is deprecated.

Finally, remember that import is hoisted and static: you cannot wrap it in if, compute its path, or catch its failure — that is what dynamic import() is for. And when mixing CommonJS and ESM in Node, know the friction points: require of an ES module is limited, __dirname doesn't exist in ESM (use import.meta.url), and named imports from CommonJS packages depend on static analysis that occasionally guesses wrong. When in doubt, default-import the CJS package and destructure.

6. Frequently Asked Questions (FAQs)

Do I need file extensions in import paths?

In browsers, yes: native ES modules require the full path including the extension, like './utils.js'. Bundlers such as Vite and webpack resolve extensionless paths at build time, but if you serve unbundled modules the browser performs no such resolution and the import will 404.

Can I use import inside a regular script tag?

No. The import statement is only valid inside modules. In HTML, add type="module" to your script tag, which also makes the script deferred by default. For conditional or lazy loading inside any script, use the dynamic import() expression instead.

What is the difference between default and named exports?

Named exports expose multiple values by their exact names and are refactoring-friendly; a module can have many. A default export provides one main value per module that importers can name freely. Prefer named exports for utilities and reserve default exports for single-purpose modules like a component or class.

What is tree-shaking and how do modules enable it?

Tree-shaking is the bundler's removal of unused exports from your final bundle. Because ES module imports and exports are static declarations, tools like Rollup and webpack can prove which exports are never imported and drop them. Dynamic property access and side-effectful modules can defeat it.

Can dynamic import() load modules conditionally?

Yes, that is its main purpose. Unlike static import, import() can appear inside functions, branches, and event handlers, takes a computed string, and returns a promise. Bundlers turn each dynamic import into a separate chunk loaded on demand, which powers route-based code splitting.
