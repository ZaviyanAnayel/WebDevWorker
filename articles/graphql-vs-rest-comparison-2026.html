1. REST in 60 Seconds: Endpoints and HTTP

REST exposes each resource at its own URL and uses HTTP methods as verbs: GET /api/users/7, POST /api/orders, PATCH /api/products/42. The server decides each endpoint's response shape, and HTTP itself provides the feature set — status codes for outcomes, verbs for actions, and headers that caches, proxies, and browsers natively understand.

REST's weakness is fixed response shapes. A mobile app showing a username and avatar still receives the full user object — over-fetching — while a dashboard needing a user plus their last five orders makes two or three round trips — under-fetching. Teams patch this with query params (?fields=id,name), dedicated summary endpoints, or backend-for-frontend layers, but each is hand-built per case.

Where REST shines is simplicity and infrastructure. Every developer knows HTTP; every cache, CDN, and load balancer speaks it; debugging is a curl command. For straightforward CRUD with stable clients, REST's fixed endpoints are a feature — predictable, cacheable, and boring in the best way.

# REST: one endpoint per resource, server decides the shape
GET /api/users/7
# → 200 OK
# {
#   "id": 7, "name": "Ava", "email": "ava@example.com",
#   "avatar": "https://cdn.acme.com/a7.png", "role": "admin",
#   "created_at": "2024-03-01", "last_login": "2026-10-13"
#   ... plus 20 more fields the mobile app never displays (over-fetching)
# }

# Dashboard needs user + recent orders → multiple round trips (under-fetching)
GET /api/users/7
GET /api/users/7/orders?limit=5
GET /api/products?ids=1,2,3          # and maybe a third call

2. GraphQL in 60 Seconds: Schema, Queries, Mutations

GraphQL exposes one endpoint (typically POST /graphql) and lets the client describe exactly what data it wants in a query. The API is defined by a schema — a typed contract listing every type, field, query, and mutation — and the server's resolvers fetch the data behind each field. The client gets precisely the fields it asked for: no more, no fewer.

This eliminates both REST pain points in one stroke. The mobile app requests { user { name avatar } } and receives two fields; the dashboard requests user plus nested orders in a single query and gets one round trip. The schema doubles as documentation and as a type source — tools generate TypeScript types and editor autocompletion directly from it, so frontend and backend stay in sync by construction.

Mutations handle writes (mutation { createOrder(...) { id total } }), and subscriptions push live updates over websockets. Introspection — querying the schema itself — powers GraphiQL and Apollo Studio explorers where you browse the entire API and test queries in the browser. The tradeoff: you trade HTTP's built-in semantics for application-level conventions you must design (caching, error shapes, and rate limiting all need deliberate answers).

# GraphQL schema: the typed contract of your entire API
type User {
  id: ID!
  name: String!
  avatar: String
  orders(limit: Int): [Order!]!
}
type Order {
  id: ID!
  total: Float!
  status: String!
}
type Query {
  user(id: ID!): User                 # read operations
}
type Mutation {
  createOrder(productId: ID!, quantity: Int!): Order   # writes
}

# One query, exact fields, nested data, single round trip
query Dashboard($id: ID!) {
  user(id: $id) {
    name
    avatar
    orders(limit: 5) {
      id
      total
      status
    }
  }
}

3. Head-to-Head Comparison

The fundamental difference is who decides the response shape: the server (REST) or the client (GraphQL). Everything else follows. GraphQL wins on network efficiency for varied clients — mobile, web, and third-party integrations each fetch exactly what they need from one endpoint. REST wins on simplicity and on leveraging three decades of HTTP infrastructure: caching, idempotency semantics, and status codes work out of the box.

Caching is the sharpest contrast. REST responses cache naturally at every layer — browser, CDN, proxy — keyed by URL, because each URL is a distinct resource. GraphQL's single endpoint defeats URL-keyed caching; production GraphQL relies on normalized client caches (Apollo Client), persisted queries, and server-side response caching keyed by query hash. Both work; REST's is free, GraphQL's is engineered.

Tooling and learning curve cut both ways. GraphQL's schema gives you generated types, validated queries, and self-documenting explorers — genuinely excellent DX once running. But someone must design the schema, write resolvers, guard against expensive nested queries (depth limiting, complexity analysis), and handle the N+1 problem (solved with DataLoader-style batching). REST asks less of you up front and more of you per client variation.

DimensionRESTGraphQL
Response shapeFixed by server per endpointChosen by client per query
Over/under-fetchingCommon — patched per endpointEliminated — exact fields, nested in one trip
EndpointsMany, one per resource/actionOne (POST /graphql)
CachingFree via HTTP (URL-keyed, CDN-friendly)Needs normalized client cache / persisted queries
Learning curveGentle — HTTP knowledge transfersSteeper — schema design, resolvers, query planning

Best atSimple CRUD, public APIs, cache-heavy readsVaried clients, complex data graphs, rapid UI iteration

4. When to Choose Which

Choose GraphQL when you serve multiple clients with different data needs (iOS, Android, web, partners) from one backend; when your UI iterates fast and you want frontend teams to fetch new fields without backend changes; when your data is a deeply connected graph (social networks, e-commerce catalogs); or when you're building a public developer platform where consumers' needs are unpredictable. Startups with a small backend team and an ambitious frontend often get the most leverage here.

Choose REST when your API is straightforward CRUD with stable, well-understood clients; when HTTP caching and CDN behavior are central to your performance story; when your team is small and the API surface is narrow — REST's lower operational overhead matters; or when you're exposing webhooks and simple integrations where every consumer speaks HTTP natively. Most internal microservice-to-microservice communication stays REST (or gRPC) for exactly these reasons.

You can also mix them: GraphQL as the client-facing gateway over REST or gRPC microservices is a mainstream architecture, and many teams migrate incrementally — new clients on GraphQL while existing REST endpoints keep running. The decision is rarely permanent, so optimize for the next 12 months of product needs, not for ideological purity.

# Decision shortcut — answer honestly:
#
# Many client types with different data needs?    → GraphQL
# Deeply nested relational data (social, catalog)? → GraphQL
# Frontend ships weekly, backend can't keep up?   → GraphQL
#
# Simple CRUD, stable clients?                    → REST
# CDN / HTTP caching is the performance plan?     → REST
# Small team, narrow API surface?                 → REST
# Service-to-service communication?               → REST (or gRPC)
#
# Migrating? GraphQL gateway in front, REST services behind.

5. Getting Started with GraphQL on Node.js

The fastest path to a working GraphQL server in Node.js is Apollo Server or graphql-yoga: define your schema with gql template literals, write resolvers (one function per field that needs custom fetching), and the library handles parsing, validation, and execution. Pair it with your existing Express app — both integrate as middleware — so you can add GraphQL alongside REST routes during a migration.

Resolvers are where backend work lives. A Query.user resolver loads the user; a User.orders resolver loads that user's orders. The classic performance trap is N+1: resolving orders separately for each of 50 users fires 50 queries. Solve it with DataLoader (or your ORM's batching), which coalesces per-request loads into single batched queries — one line of setup that routinely cuts database round trips by orders of magnitude.

Before going to production, harden the endpoint: enforce a max query depth and complexity (a malicious client can nest fields exponentially), require persisted queries or an allowlist for public APIs, put authentication in the request context so every resolver can check it, and return errors in the GraphQL errors[] array with coded extensions rather than HTTP 500s for expected failures. These four measures cover the vast majority of GraphQL security incidents.

// Minimal Apollo Server: schema + resolvers in ~30 lines
import { ApolloServer } from "@apollo/server";
import { startStandaloneServer } from "@apollo/server/standalone";

const typeDefs = `#graphql
  type User { id: ID!, name: String!, orders: [Order!]! }
  type Order { id: ID!, total: Float! }
  type Query { user(id: ID!): User }
`;

const users = { 7: { id: "7", name: "Ava" } };
const orders = [{ id: "o1", userId: "7", total: 59.98 }];

const resolvers = {
  Query: {
    user: (_, { id }) => users[id] ?? null,
  },
  User: {
    // In production: batch with DataLoader to avoid N+1
    orders: (user) => orders.filter((o) => o.userId === user.id),
  },
};

const server = new ApolloServer({ typeDefs, resolvers });
const { url } = await startStandaloneServer(server, { listen: { port: 4000 } });
console.log(`GraphQL ready at ${url}`);

6. Frequently Asked Questions (FAQs)

Is GraphQL replacing REST?

No — they're complementary tools. REST remains dominant for simple CRUD, public APIs, and cache-heavy workloads; GraphQL excels where clients vary and data is deeply connected. Many organizations run both, often with a GraphQL gateway in front of REST or gRPC microservices.

Does GraphQL use HTTP methods like GET and POST?

Typically everything goes through POST to a single /graphql endpoint, with the operation (query or mutation) in the body. Simple read queries can use GET with URL-encoded parameters, which also enables CDN caching for those operations.

How do you secure a GraphQL API?

Authenticate in the request context so every resolver can authorize, enforce max query depth and complexity to block malicious nested queries, use persisted queries or an allowlist for public endpoints, rate-limit by query cost rather than request count, and never expose stack traces in the errors array.

Can I use GraphQL and REST in the same project?

Absolutely — it's a common migration pattern. Run a GraphQL gateway that resolves fields by calling your existing REST endpoints or services, move new clients to GraphQL, and keep legacy REST endpoints running until their consumers migrate.

How does caching work with GraphQL?

REST-style URL caching doesn't apply to a single endpoint, so GraphQL uses different strategies: normalized client caches (Apollo Client stores each entity once by ID), persisted queries (hash-keyed, CDN-cacheable), and server-side response caching. Design your schema with stable IDs to make normalized caching effective.
