1. The 12-Factor Way: Why Config Belongs in the Environment

Database passwords, API keys, feature toggles, port numbers — every app has configuration that changes between environments. The 12-factor methodology (the blueprint behind modern app deployment) draws a hard line: code is identical across deploys; config lives in the environment.

Why does this matter? Because it means the exact artifact you tested in staging is the one running in production — no rebuilding with different settings, no “oops, the prod config was in a file someone forgot to copy.” One build, many environments, zero surprises.

Environment variables are the mechanism: key-value pairs injected by the operating system or platform, read by your app at runtime via process.env. They are language-agnostic, work identically in Docker, CI, and serverless, and keep secrets out of your codebase.

Contrast this with the old way: config files checked into Git, per-environment branches, or “just SSH in and edit the config.” Every one of those couples your code to a specific environment, making rollbacks risky and staging untrustworthy. Env vars decouple the two completely — the same container image runs everywhere, differing only in the variables it is handed at startup.

2. .env Files: Structure and Conventions

In development, juggling dozens of export commands is miserable. .env files solve this: a simple KEY=value file your app loads locally. Follow these conventions and your team will thank you:

# .env — local development only, NEVER committed
NODE_ENV=development
PORT=3000

# Group related keys; SCREAMING_SNAKE_CASE everywhere
DATABASE_URL=postgres://dev:dev@localhost:5432/myapp
REDIS_URL=redis://localhost:6379

# Third-party services
STRIPE_SECRET_KEY=sk_test_abc123
SENDGRID_API_KEY=SG.test_key

# Feature flags are config too
ENABLE_NEW_CHECKOUT=false

Always ship a .env.example with the same keys but placeholder values — it documents exactly what a new developer needs to fill in. And put .env in .gitignore on day one; adding it after a secret is committed does not erase history.

A few formatting rules keep .env files predictable: no spaces around the =, quote values that contain spaces or special characters, and never use export prefixes (some loaders choke on them). Comments start with # — use them to explain where each value comes from, so the next developer is not guessing.

3. Loading and Validating Variables in Node.js

The dotenv package loads .env into process.env in development. But loading is only half the job — validate at startup so a missing variable crashes loudly in seconds instead of mysteriously at 3 AM:

// config.js — load once, validate, export typed config
import 'dotenv/config';
import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
  STRIPE_SECRET_KEY: z.string().min(1),
});

export const config = envSchema.parse(process.env);
// Throws a clear error at startup if anything is missing

This fail-fast pattern is the single highest-value env practice: every required variable is checked in one place, with an error message naming exactly what is missing. Centralize access through this config module and never scatter raw process.env reads across your codebase.

For TypeScript teams, the validated config object doubles as documentation — its inferred type lists every setting your app accepts. And in Docker, remember that .env files are a development convenience only: pass real values with docker run -e or Compose's environment block so the image itself never contains secrets.

4. Secrets Management in Production

Production is where .env files end and real secret management begins. Every major platform — Vercel, Heroku, AWS, GitHub Actions — provides encrypted environment variable dashboards; use them instead of copying files to servers.

ApproachBest ForWatch Out For
Platform env dashboardVercel, Heroku, Render appsScope per environment (preview vs prod)
CI/CD secretsBuild-time and deploy credentialsNever log or echo them
Vault (1Password, AWS Secrets Manager)Teams, rotation, audit trailsAdded complexity and cost
.env on serverSingle VPS quick setupschmod 600, never in backups unencrypted

Whatever you choose, rotate secrets when team members leave and after any suspected exposure. Design your app to read secrets at startup so rotation is a restart, not a redeploy.

Document who owns each secret and where it lives — a simple inventory prevents the classic incident where nobody knows which dashboard holds the production Stripe key.

5. Common Mistakes That Leak Secrets

Most secret leaks are not hacks — they are accidents. The greatest hits: committing .env to Git (check with git log --all -- .env), embedding secrets in client-side bundles (any NEXT_PUBLIC_ variable ships to the browser — treat it as public), and printing config in logs or error messages.

# .gitignore — the minimum every project needs
.env
.env.local
.env.*.local
*.pem
*.key

If a secret is committed, revoke it immediately — then clean history with git filter-repo or BFG. Deleting the file in a later commit is not enough; the secret lives forever in history. Prevention (gitignore + pre-commit hooks like detect-secrets) beats cleanup every time.

Run a periodic audit, too: search your repos for committed secrets with tools like gitleaks or GitHub's secret scanning, and rotate anything older than your team's policy allows. Secrets, like passwords, have a shelf life — treat rotation as routine maintenance, not an emergency response.

6. Frequently Asked Questions (FAQs)

Should I commit my .env file to Git?

No, never. The .env file holds secrets like API keys and database passwords. Commit a .env.example with placeholder values instead, so teammates know what to configure without exposing real credentials.

What is the difference between a .env file and environment variables?

Environment variables are the actual mechanism your app reads at runtime. A .env file is just a convenient development tool that loads values into the environment locally. In production, set real environment variables on your platform instead.

How do I use environment variables safely in frontend code?

Assume anything bundled into client JavaScript is public. Only expose non-sensitive values (like a public API URL), and use your framework's public prefix convention deliberately. Secrets must stay on the server, accessed via API routes.

What should I do if I accidentally committed a secret?

Revoke and rotate the secret first — assume it is compromised. Then remove it from Git history with git filter-repo or BFG Repo-Cleaner, and force-push. Finally, add the file to .gitignore and consider a pre-commit secret scanner.

What is a .env.example file for?

It is a template listing every environment variable your project needs, with dummy values. New developers copy it to .env and fill in real values. It serves as living documentation of your app's configuration requirements.
