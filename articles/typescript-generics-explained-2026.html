1. What Are Generics and Why Bother?

Generics let you write code that works with many types while keeping full type safety for each of them. Without generics you face an unhappy choice: write the same logic three times (once per type), or type everything as any and lose all checking. Generics are the third option — a type parameter that the caller fills in.

The classic motivation is a utility like 'return the first element of an array.' Typed for strings it returns string; typed for numbers, number. With any it returns any and the compiler goes blind. With a generic <T>, the return type is the element type — the compiler tracks it through every call site, giving you precise types without duplicating code.

// ❌ Without generics: duplicated logic per type...
function firstString(arr: string[]): string { return arr[0]; }
function firstNumber(arr: number[]): number { return arr[0]; }

// ❌ ...or any, which erases all type information
function firstAny(arr: any[]): any { return arr[0]; }
const n = firstAny([1, 2, 3]);
n.toUpperCase(); // compiles fine, explodes at runtime 💥

// ✅ With generics: one implementation, precise types everywhere
function first<T>(arr: T[]): T {
  return arr[0];
}
const s = first(["a", "b"]);   // s: string  — autocomplete works
const m = first([1, 2, 3]);    // m: number  — m.toFixed() is known
// first([]) → T inferred from the argument; explicit first<string>(...) also works

2. Generic Functions

A generic function declares its type parameters in angle brackets before the regular parameters: function identity<T>(value: T): T. At the call site TypeScript usually infers T from the arguments, so you rarely write the type explicitly — identity("hi") just works, with T = string. Explicit annotation (identity<string>("hi")) is available when inference needs help, such as empty arrays.

Functions can take multiple type parameters: function pair<K, V>(key: K, value: V). Parameters can relate to each other — function get<T>(arr: T[], index: number): T ties the return type to the array's element type. You can also give type parameters defaults (<T = string>), useful in library APIs where most callers want the common case.

Arrow functions are generic too, with one syntactic wrinkle: in .tsx files, <T> alone parses as JSX, so write <T,> (trailing comma) or <T extends unknown>. In plain .ts files the plain form is fine. This is the only place generics syntax differs between the two extensions.

// Multiple type parameters with relationships between them
function zip<K, V>(keys: K[], values: V[]): Array<[K, V]> {
  return keys.map((k, i) => [k, values[i]]);
}
const entries = zip(["a", "b"], [1, 2]);  // Array<[string, number]>

// Type parameter defaults: common case stays ergonomic
function parseJson<T = unknown>(text: string): T {
  return JSON.parse(text) as T;
}
const data = parseJson<{ users: string[] }>('{"users":["ava"]}');
// data.users is string[] — no `any` anywhere

// Generic arrow functions (.tsx needs the trailing comma)
const wrap = <T,>(value: T): { value: T } => ({ value });
const numbers = [1, 2, 3].map(wrap);  // { value: number }[]

3. Generic Interfaces, Classes, and Constraints

Interfaces and classes take type parameters the same way: interface Box<T> { value: T }, class Store<T> { ... }. This is how collections, API envelopes, and state containers stay typed — Array<T>, Promise<T>, and Map<K, V> are all generic interfaces you already use daily.

Unconstrained, T could be anything — including types your logic can't handle. Constraints (<T extends ...>) narrow what T may be, which simultaneously unlocks what you can do with it: <T extends { id: string }> lets you read .id safely. The keyof operator pairs beautifully with constraints — <T, K extends keyof T> types a 'get property by key' helper so precisely that a wrong key is a compile error.

A constraint is a contract with the caller: 'give me anything, as long as it has this shape.' Prefer the narrowest constraint that lets your implementation work — over-constraining (demanding a full interface when you only read one field) makes the generic annoying to use; under-constraining forces unsafe casts inside.

PatternSyntaxUse case
Basic parameter<T>Identity-style utilities, wrappers
Multiple params<K, V>Maps, pairs, key-value helpers
Constraint<T extends { id: string }>Require a shape; unlock property access
keyof constraint<K extends keyof T>Type-safe property access by key
Default<T = unknown>Ergonomic library APIs
Conditional useT extends U ? X : YType-level branching (advanced)
// Generic interface + class: typed containers
interface ApiResponse<T> {
  data: T;
  meta: { page: number; total: number };
}

class Repository<T extends { id: string }> {
  private items = new Map<string, T>();
  save(item: T): void { this.items.set(item.id, item); }  // .id is safe: constraint guarantees it
  find(id: string): T | undefined { return this.items.get(id); }
}

// keyof constraint: property access that can't name a wrong key
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const user = { name: "Ava", age: 30 };
const name = getProp(user, "name");   // string ✅
const bad = getProp(user, "email");   // ❌ '"email"' is not assignable to '"name" | "age"'

4. Real-World Pattern: Typed API Responses

The highest-value generic in most codebases wraps API calls. A fetchJson<T> helper takes the expected payload type as its parameter, so every endpoint gets precise types from one shared implementation — loading states, error handling, and JSON parsing written once, type safety everywhere. Callers write fetchJson<User[]>("/api/users") and get User[] back, or a typed error.

For richer error handling, a Result<T, E> type (success/failure union, generic over both payload and error) makes the unhappy path impossible to ignore — the compiler forces callers to handle both variants. Libraries like neverthrow popularized this; hand-rolling a small version teaches the pattern and covers most apps.

Generics also shine in state management: a createStore<T> factory, a typed event emitter Emitter<Events> where event names constrain payloads, or form helpers generic over the form's shape. The pattern is always the same — identify the logic that's identical across types, parameterize the type, and let inference do the rest.

// One typed fetch helper for every endpoint
async function fetchJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${res.statusText}`);
  return (await res.json()) as T;
}

interface User { id: number; name: string; email: string }

const users = await fetchJson<User[]>("/api/users");
users.map(u => u.name);            // string[] — fully typed, zero duplication

// Result<T, E>: make error handling explicit and typed
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

async function safeFetch<T>(url: string): Promise<Result<T>> {
  try {
    return { ok: true, value: await fetchJson<T>(url) };
  } catch (error) {
    return { ok: false, error: error as Error };
  }
}

const result = await safeFetch<User[]>("/api/users");
if (result.ok) {
  console.log(result.value.length);  // User[]
} else {
  console.error(result.error.message); // Error — must be handled
}

5. Common Mistakes and Best Practices

The most common mistake is over-genericizing: adding <T> to a function used with exactly one type. Generics pay for themselves at two or more use sites with different types; below that they're abstraction without a customer. Write the concrete version first, generalize when the second use case appears.

Second, don't let any leak through your generics. A signature like function f<T>(x: any): T promises type safety it can't deliver — constrain the input or type it honestly as unknown and narrow inside. Third, name type parameters meaningfully in public APIs: single letters (T, K, V) are fine for tiny utilities, but <TItem> or <TPayload> read better in library signatures.

Finally, remember generics are erased at compile time — there is no runtime T to inspect, so you can't do typeof T or new T() without passing a constructor explicitly. Design accordingly: if runtime behavior must vary by type, pass a discriminator value or a factory function alongside the type parameter.

// ❌ Over-genericized: only ever called with string
function firstStringVersion<T>(arr: T[]): T { return arr[0]; }
// ✅ Just write it concretely until a second type shows up
function firstString(arr: string[]): string { return arr[0]; }

// ❌ any leaking through a generic — a lie in the signature
declare function parseUnsafe<T>(input: any): T;
// ✅ unknown in, narrowed inside — honest about what it knows
function parseSafe<T>(input: unknown): T {
  if (typeof input !== "string") throw new Error("expected string");
  return JSON.parse(input) as T;
}

// Runtime needs a value, not just a type: pass the constructor
function create<T>(Ctor: new () => T): T {
  return new Ctor();   // ✅ constructor is a real runtime value
}

6. Frequently Asked Questions (FAQs)

When should I actually use generics?

When the same logic operates on multiple types and you want each use to stay precisely typed — utility functions, collections, API wrappers, and state containers. If a function is only ever used with one type, write it concretely; generalize when the second use case appears.

What is the difference between and any?

any disables type checking: anything goes in, anything comes out, and errors surface at runtime. A generic preserves the relationship between input and output types, so first(...) returns string and the compiler verifies every downstream use. Generics are type-safe; any is type-blind.

How do I constrain a generic type parameter?

With extends: requires T to have an id property, which lets your implementation safely read item.id. Constraints are contracts with the caller — require the narrowest shape your logic actually needs.

What does keyof do in generic code?

keyof T produces a union of T's property names as literal types. Combined with a constraint — — it types helpers like getProperty(obj, key) so precisely that passing a non-existent key is a compile-time error.

Do generics exist at runtime?

No. TypeScript erases all type parameters during compilation, so there is no runtime T to inspect — you cannot do new T() or typeof T. If runtime behavior must vary by type, pass a constructor, discriminator value, or factory function as a regular argument.
