1. Documents, Collections & Connecting

MongoDB stores data as documents — JSON-like structures (technically BSON) grouped into collections. Where a relational database has tables, rows, and columns, MongoDB has collections, documents, and fields. A user document can contain nested address objects and arrays of order references without any JOINs, because related data simply lives inside the document.

The flexible schema is MongoDB's signature: documents in the same collection need not share identical fields, so adding a new optional field requires no migration. Freedom demands discipline, though — production teams enforce shape with Mongoose schemas or MongoDB's JSON Schema validation, because "schemaless" without conventions becomes chaos within months.

Connect with mongosh, the modern shell: mongosh "mongodb://localhost:27017/myapp" drops you into a JavaScript REPL against your database. For a visual alternative, MongoDB Compass provides a GUI for exploring collections, building queries, and inspecting query plans. Both connect to local servers and Atlas cloud clusters identically.

// Connect: mongosh "mongodb://localhost:27017/shop"

// Documents are just JSON-like objects
db.users.insertOne({
  name: "Ayesha Khan",
  email: "ayesha@example.com",
  address: { city: "Lahore", country: "PK" },  // nested object
  tags: ["vip", "early-adopter"],              // array field
  createdAt: new Date()
});
// { acknowledged: true, insertedId: ObjectId("...") }

2. Create & Read: insertOne, insertMany & find

Creating documents is insertOne for a single document and insertMany for batches — the latter being dramatically faster for seeding data since it makes one round trip. Every document gets an _id automatically, an ObjectId that is unique and roughly time-ordered, which makes a fine default primary key without any configuration.

Reading is db.collection.find(filter), where the filter is a document describing what to match: { city: "Lahore" } matches exactly, while operators add power — { age: { $gte: 18 } }, { tags: { $in: ["vip"] } }, { name: { $regex: "^ali", $options: "i" } }. Chain .sort({ createdAt: -1 }).limit(10) for newest-first pagination, and pass a projection like { name: 1, email: 1 } to return only needed fields.

Two methods deserve memorization: findOne() returns the first match (or null) for single-document lookups, and countDocuments(filter) counts matches efficiently. Both accept the same filter syntax, so everything you learn about find() transfers directly.

// Bulk insert
db.products.insertMany([
  { sku: "W-1", title: "Widget", price: 19.99, stock: 120 },
  { sku: "G-2", title: "Gadget", price: 49.99, stock: 0 },
  { sku: "D-3", title: "Doohickey", price: 9.99, stock: 500 }
]);

// Find in-stock products under $50, cheapest first, fields limited
db.products.find(
  { price: { $lt: 50 }, stock: { $gt: 0 } },
  { title: 1, price: 1, _id: 0 }
).sort({ price: 1 }).limit(10);

// Single lookup + count
db.products.findOne({ sku: "W-1" });
db.products.countDocuments({ stock: 0 });  // out-of-stock count

3. Update: $set, Upserts & Array Operators

Updates never replace blindly: updateOne(filter, update) modifies the first match, updateMany the whole set, and the update document uses operators describing the change. $set changes specific fields while leaving everything else intact — the operation you will use 90% of the time. Without an operator, MongoDB replaces the entire document, a classic beginner footgun worth stating plainly.

Specialized operators handle common mutations atomically: $inc adjusts counters (page views, stock levels) safely under concurrency, $push appends to arrays, $pull removes matching array elements, and $addToSet appends only if absent. These run server-side, so concurrent requests cannot clobber each other's increments the way read-modify-write cycles do.

The upsert option ({ upsert: true }) turns an update into "update if present, insert if absent" — perfect for sync jobs and counters. And findOneAndUpdate returns the document before or after modification, which is ideal for queues and reservation patterns where you must claim exactly one item.

// $set: change fields, keep the rest
db.products.updateOne(
  { sku: "W-1" },
  { $set: { price: 17.99, updatedAt: new Date() } }
);

// Atomic counter decrement (safe under concurrency)
db.products.updateOne({ sku: "W-1" }, { $inc: { stock: -1 } });

// Array operators
db.users.updateOne(
  { email: "ayesha@example.com" },
  { $push: { tags: "newsletter" }, $pull: { tags: "trial" } }
);

// Upsert: update the daily stat, or create it
db.stats.updateOne(
  { day: "2026-10-14" },
  { $inc: { visits: 1 } },
  { upsert: true }
);

4. Delete: Removing Documents Safely

deleteOne removes the first matching document; deleteMany removes every match. The critical safety rule: an empty filter {} matches everything, so db.users.deleteMany({}) empties the collection. Always run the same filter through find() or countDocuments() first to see exactly what you are about to destroy — thirty seconds of caution versus restoring from backup.

Many applications should not hard-delete at all. Soft deletes — setting { deleted: true, deletedAt: new Date() } and filtering it in queries — preserve history, survive "oops" moments, and satisfy audit requirements. Reserve true deletion for GDPR-style erasure requests and retention-policy jobs.

In application code, the Node.js driver's async/await API mirrors the shell: collection.deleteOne({ _id }) inside a try/catch, checking deletedCount to confirm. The example below wires a complete CRUD flow in Node.js — connect, create, read, update, delete — the pattern every MongoDB-backed service repeats.

// Node.js driver: full CRUD flow
import { MongoClient, ObjectId } from "mongodb";

const client = new MongoClient("mongodb://localhost:27017");
await client.connect();
const users = client.db("shop").collection("users");

// Create
const { insertedId } = await users.insertOne({ name: "Bilal", email: "b@example.com" });

// Read
const user = await users.findOne({ _id: insertedId });

// Update
await users.updateOne({ _id: insertedId }, { $set: { name: "Bilal Ahmed" } });

// Delete (check the count!)
const { deletedCount } = await users.deleteOne({ _id: insertedId });
console.log("deleted:", deletedCount);

await client.close();

5. Indexes & Query Patterns That Scale

Unindexed MongoDB queries scan every document — fine for hundreds, fatal for millions. db.collection.createIndex({ email: 1 }) builds an ascending B-tree index making equality lookups and sorts on email instant. Compound indexes like { status: 1, createdAt: -1 } serve multi-field queries, following the same leftmost-prefix logic as relational composite indexes.

MongoDB's ESR rule guides compound index design: Equality fields first, then Sort fields, then Range fields. An index on { status: 1, createdAt: -1 } perfectly serves find({ status: "active" }).sort({ createdAt: -1 }). Verify with explain("executionStats"): winningPlan should show IXSCAN (index scan), and totalDocsExamined should be close to the returned count — a wide gap means the index is not selective enough.

Schema design is the deeper performance lever: embed data that is accessed together (a post with its comments), reference data that grows unboundedly or is shared (users referenced by many orders). Embedding avoids $lookup joins entirely; referencing keeps documents small. Choose per relationship, not per database — most real schemas mix both deliberately.

// Essential indexes
db.users.createIndex({ email: 1 }, { unique: true });
db.orders.createIndex({ status: 1, createdAt: -1 });  // ESR order
db.products.createIndex({ title: "text", description: "text" });  // text search

// Verify the query actually uses the index
db.orders.explain("executionStats").find({ status: "active" })
  .sort({ createdAt: -1 });
// Look for: stage "IXSCAN", low totalDocsExamined

6. Frequently Asked Questions (FAQs)

Should I learn MongoDB or SQL first?

Learn SQL fundamentals first — relational thinking transfers everywhere, and most jobs still expect it. Then learn MongoDB for what it does best: rapidly evolving, document-shaped data. Knowing both lets you pick the right tool instead of forcing one onto every problem.

Does MongoDB require a schema?

The database does not enforce one, but production applications should. Use Mongoose schemas in Node.js or MongoDB's built-in JSON Schema validation to guarantee document shape. Schemaless without discipline quietly becomes chaos as the app grows.

What is an ObjectId?

A 12-byte identifier MongoDB auto-generates as each document's _id: unique across collections and roughly time-ordered, so recent documents sort naturally. It works well as a default primary key with zero configuration.

Does MongoDB support transactions?

Yes — multi-document ACID transactions have been supported since version 4.0 on replica sets. They work, but the idiomatic approach is designing documents so most operations stay single-document and atomic by default, reaching for transactions only when genuinely needed.

When should I avoid MongoDB?

When your workload is heavy ad-hoc joins across many collections, demands strict relational integrity, or centers on complex reporting — a relational database fits those better. MongoDB excels at document-shaped, read-mostly, and rapidly evolving data models.
