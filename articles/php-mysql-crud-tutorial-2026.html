1. Connecting to MySQL with PDO

PDO (PHP Data Objects) is the modern database layer for PHP: a consistent object-oriented API that works across MySQL, PostgreSQL, and SQLite, with first-class support for prepared statements. The older mysqli extension is MySQL-only and clunkier; for any new project, PDO is the right default and this guide assumes it throughout.

A connection needs three things: a DSN string describing the driver, host, database, and charset; a username; and a password. Wrap the connection in try/catch because PDO throws on failure, and set three attributes every time: ERRMODE_EXCEPTION so errors throw instead of failing silently, DEFAULT_FETCH_MODE to FETCH_ASSOC for clean associative arrays, and utf8mb4 charset so emoji and full Unicode store correctly.

Keep credentials out of your code's logic: a single db.php that returns the PDO instance, reading credentials from environment variables or a config file outside the document root. Every page that needs the database requires this one file — one place to update when passwords rotate or hosts change.

<?php // db.php — require this wherever you need the database
declare(strict_types=1);

$host = getenv("DB_HOST") ?: "127.0.0.1";
$db   = getenv("DB_NAME") ?: "myapp";
$user = getenv("DB_USER") ?: "root";
$pass = getenv("DB_PASS") ?: "";

try {
    $pdo = new PDO(
        "mysql:host=$host;dbname=$db;charset=utf8mb4",
        $user,
        $pass,
        [
            PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
            PDO::ATTR_EMULATE_PREPARES => false, // use real prepared statements
        ]
    );
} catch (PDOException $e) {
    error_log("DB connection failed: " . $e->getMessage());
    http_response_code(500);
    exit("Database unavailable. Please try again later.");
}
?>

2. Create: Inserting Records Safely

Inserting data is where SQL injection attacks are born — and where prepared statements kill them. Instead of interpolating variables into SQL strings, you write placeholders (:name) and pass values separately to execute(). The database receives the query structure and the data through different channels, so a malicious input like '; DROP TABLE users; -- is stored as a harmless string instead of executed.

Named placeholders (:title, :price) beat positional question marks for readability once a query has more than two or three parameters. After a successful insert, lastInsertId() returns the auto-increment ID of the new row — exactly what you need to redirect the user to their new record's page.

Validate before you insert, not after. Check required fields, verify email formats, and enforce business rules (price > 0) in PHP first; the database's NOT NULL and CHECK constraints are your second line of defense, not your first. Clean data in means trustworthy data out.

<?php // create.php — handle the “new product” form
require __DIR__ . "/db.php";

$title = trim($_POST["title"] ?? "");
$price = (float)($_POST["price"] ?? 0);

if ($title === "" || $price <= 0) {
    exit("A title and a positive price are required.");
}

$stmt = $pdo->prepare(
    "INSERT INTO products (title, price, created_at)
     VALUES (:title, :price, NOW())"
);
$stmt->execute([":title" => $title, ":price" => $price]);

$newId = (int)$pdo->lastInsertId();
header("Location: view.php?id=" . $newId); // Post/Redirect/Get
exit;
?>

3. Read: Fetching and Displaying Records

Reading is the most common operation your app will perform, so make it boring and predictable. For queries with no user input, $pdo->query() runs the SQL directly; the moment a WHERE clause depends on input — an ID from $_GET, a search term — switch to prepare() plus execute() exactly as with inserts. Consistency here is a security feature: developers who always prepare never forget to.

fetchAll() returns every row as an array of associative arrays, perfect for looping into an HTML table. For a single record, fetch() returns just one row (or false when nothing matches — always check before accessing fields). Both respect the FETCH_ASSOC default you set in db.php, so $row["title"] works and numeric indexes stay out of your way.

Every value printed into HTML passes through htmlspecialchars(). Database content is user input with extra steps: a product title containing <script> becomes a stored XSS attack the moment you echo it raw. Escape on output, every time, and the problem disappears permanently.

<?php // list.php — show all products, newest first
require __DIR__ . "/db.php";

$products = $pdo->query(
    "SELECT id, title, price FROM products ORDER BY created_at DESC"
)->fetchAll();
?>
<table>
<?php foreach ($products as $p): ?>
  <tr>
    <td><?= htmlspecialchars($p["title"], ENT_QUOTES) ?></td>
    <td>$<?= number_format((float)$p["price"], 2) ?></td>
    <td><a href="view.php?id=<?= (int)$p["id"] ?>">View</a></td>
  </tr>
<?php endforeach; ?>
</table>

<?php // view.php — one record by ID from the URL
require __DIR__ . "/db.php";
$id = (int)($_GET["id"] ?? 0);
$stmt = $pdo->prepare("SELECT * FROM products WHERE id = :id");
$stmt->execute([":id" => $id]);
$product = $stmt->fetch();
if (!$product) { http_response_code(404); exit("Product not found."); }
?>

4. Update & Delete: Modifying Records

Updates follow the identical prepare-and-execute rhythm: an UPDATE statement with named placeholders, a WHERE clause pinning the exact row, and bound values. Always check rowCount() afterward — it tells you whether anything actually changed, which distinguishes "saved" from "that ID doesn't exist" in your UI feedback.

Deletes demand extra respect because they are irreversible. Require a confirmation step (a dedicated form posting the ID, not a GET link that crawlers or prefetchers can trigger), and consider soft deletes — an is_deleted flag or deleted_at timestamp — for anything users might want back. Real DELETE statements belong to admin tools and data-retention jobs, not casual UI buttons.

Both operations share one non-negotiable rule: the WHERE clause must come from validated, cast input — (int)$_GET["id"] — never raw strings concatenated into SQL. A missing or malformed WHERE on an UPDATE rewrites your whole table; on a DELETE it empties it. Prepared statements plus integer casting make both accidents nearly impossible.

<?php // update.php
require __DIR__ . "/db.php";
$id    = (int)($_POST["id"] ?? 0);
$title = trim($_POST["title"] ?? "");
$price = (float)($_POST["price"] ?? 0);

$stmt = $pdo->prepare(
    "UPDATE products SET title = :title, price = :price WHERE id = :id"
);
$stmt->execute([":title" => $title, ":price" => $price, ":id" => $id]);
echo $stmt->rowCount() ? "Product updated." : "No changes made.";
?>

<?php // delete.php — POST-only, with confirmation form
require __DIR__ . "/db.php";
$id = (int)($_POST["id"] ?? 0);
$stmt = $pdo->prepare("DELETE FROM products WHERE id = :id");
$stmt->execute([":id" => $id]);
header("Location: list.php?deleted=1");
exit;
?>

5. Going Further: Transactions, Errors & Passwords

Some operations are only correct when several writes succeed or fail together: creating an order and its line items, or moving money between accounts. Transactions give you that atomicity — beginTransaction(), run your statements, then commit(). If anything throws, rollBack() in the catch block undoes every partial write, leaving the database exactly as it was. Without transactions, a crash mid-sequence leaves corrupt half-finished data.

Your error strategy should be deliberate: log the full technical detail with error_log() for yourself, and show visitors a generic message. Database error text can reveal table names, column names, and query structure — a roadmap for attackers. In development, display errors freely; in production, log them and show a friendly page.

If your CRUD app has users, passwords get special treatment: password_hash($password, PASSWORD_DEFAULT) produces a bcrypt hash (automatically salted, future-proofed by PHP), and password_verify() checks logins. Never use MD5 or SHA1, never encrypt passwords reversibly, and never write your own hashing scheme — PHP's built-in functions are reviewed by cryptographers and yours are not.

<?php // checkout.php — order + items must succeed together
require __DIR__ . "/db.php";

try {
    $pdo->beginTransaction();

    $stmt = $pdo->prepare(
        "INSERT INTO orders (user_id, total) VALUES (:uid, :total)"

6. Frequently Asked Questions (FAQs)

PDO vs mysqli — which should I use?

Use PDO for new projects. It works with MySQL, PostgreSQL, and SQLite through one consistent API, supports named placeholders, and has a cleaner object-oriented interface. mysqli is MySQL-only and mostly relevant for maintaining legacy code.

Are prepared statements really necessary?

Yes — they are the single most important defense against SQL injection. Prepared statements send the query structure and the data separately, so user input can never alter what the query does. Make prepare-then-execute your unbreakable habit for every query containing input.

How should I handle PDO errors?

Set PDO::ATTR_ERRMODE to ERRMODE_EXCEPTION, wrap risky blocks in try/catch, log the full error server-side with error_log(), and show visitors only a generic message. Never print raw database errors to the browser — they leak schema details to attackers.

When do I need transactions?

Whenever multiple writes must succeed or fail as a unit: an order with its line items, a money transfer's debit and credit, or any batch import. Wrap them in beginTransaction() and commit(), with rollBack() in the catch block so partial writes never persist.

How do I store user passwords safely?

Hash with password_hash() using PASSWORD_DEFAULT (currently bcrypt) and verify logins with password_verify(). The functions handle salting and algorithm upgrades automatically. Never store plain text, never use MD5 or SHA1, and never invent your own hashing scheme.
