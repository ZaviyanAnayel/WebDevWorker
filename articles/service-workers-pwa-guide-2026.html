1. The Service Worker Lifecycle: Install, Activate, and Waiting

A service worker is a JavaScript file that runs on a separate thread from your page, with no access to the DOM. It acts as a programmable network proxy: every fetch your page makes can be intercepted, served from a cache, modified, or queued. Because it lives outside any single page, it keeps running logic — like caching and background sync — even after the tab closes.

The lifecycle has three main phases. During install, the worker typically precaches the app shell — the HTML, CSS, and JavaScript needed for the first paint. Installation only succeeds if every precache request succeeds, which makes it an all-or-nothing transaction. Calling skipWaiting() here lets the new worker activate immediately instead of waiting for old tabs to close.

During activate, you clean up caches from previous versions and can call clients.claim() to take control of open pages right away. If you skip these steps, the new worker sits in the waiting state until every tab using the old version is closed — the number one reason developers think their service worker update is broken when it is actually behaving exactly as designed.

// sw.js — install, precache, and activate with cleanup
const CACHE = "app-v3";
const APP_SHELL = ["/", "/styles.css", "/app.js", "/offline.html"];

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE).then((cache) => cache.addAll(APP_SHELL))
      .then(() => self.skipWaiting())
  );
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys()
      .then((keys) => Promise.all(
        keys.filter((k) => k !== CACHE).map((k) => caches.delete(k))
      ))
      .then(() => self.clients.claim())
  );
});

2. Registering and Updating Service Workers Safely

Registration happens from your page JavaScript, and scope matters: a worker registered at /sw.js controls the whole origin, while one at /blog/sw.js only controls /blog/*. Register after the page loads so the worker's installation never competes with your critical rendering path, and always guard the call with a feature check.

Updates are byte-compared: the browser re-fetches the worker script on navigation and installs a new version only if the bytes differ. The new worker then waits until all controlled tabs close, unless you call skipWaiting(). For the best user experience, listen for the updatefound event and show a discreet toast — new version available, refresh to update — instead of force-reloading under the user's feet.

One critical rule: never cache the service worker script itself with long TTLs. Serve it with Cache-Control: no-cache (or a very short max-age) so the browser's byte-difference check sees fresh code. A cached worker script is the classic way to strand users on an old version for days.

// Register after load; prompt the user when an update is waiting
if ("serviceWorker" in navigator) {
  window.addEventListener("load", async () => {
    const reg = await navigator.serviceWorker.register("/sw.js");
    reg.addEventListener("updatefound", () => {
      const worker = reg.installing;
      worker.addEventListener("statechange", () => {
        if (worker.state === "installed" && navigator.serviceWorker.controller) {
          showToast("New version available — refresh to update.");
        }
      });
    });
  });
}

3. Caching Strategies: Choosing the Right One

There is no single best caching strategy — the right choice depends on how often the resource changes and how stale it is allowed to be. Five patterns cover nearly every case: cache-first, network-first, stale-while-revalidate, network-only, and cache-only. A well-built worker routes different request types to different strategies inside one fetch handler.

Use cache-first for versioned, fingerprinted assets that never change without a new URL — it is the fastest option and cannot serve stale content by construction. Use network-first for HTML navigations and API calls where freshness matters; fall back to the cache when the network fails so the app still works offline.

Stale-while-revalidate is the balanced default for resources like user avatars, stylesheets, or product data: serve the cached copy instantly while refreshing it in the background for next time. Reserve network-only for non-GET requests and analytics beacons, and cache-only for precached app-shell assets you know are always present.

StrategyBest forStrengthWatch out for
Cache-firstFingerprinted JS, CSS, fontsFastest; never staleNeeds versioned URLs
Network-firstHTML pages, API dataAlways fresh when onlineSlower; needs offline fallback
Stale-while-revalidateAvatars, feeds, configInstant plus fresh next timeFirst load after change is stale
Network-onlyPOST requests, analyticsSimple and correctNo offline support
Cache-onlyPrecached app shellGuaranteed instantBreaks if precache missed it
// Strategy router inside the fetch handler
self.addEventListener("fetch", (event) => {
  const { request } = event;
  const url = new URL(request.url);

  if (request.method !== "GET") return; // let POSTs pass through

  if (/\.[a-f0-9]{8}\.(js|css|woff2)$/.test(url.pathname)) {
    event.respondWith(cacheFirst(request));            // versioned assets
  } else if (url.pathname.startsWith("/api/")) {
    event.respondWith(networkFirst(request));          // fresh data, offline fallback
  } else {
    event.respondWith(staleWhileRevalidate(request));   // everything else
  }
});

async function cacheFirst(request) {
  const cached = await caches.match(request);
  if (cached) return cached;
  const res = await fetch(request);
  const cache = await caches.open(CACHE);
  cache.put(request, res.clone());
  return res;
}

async function networkFirst(request) {
  try {
    const res = await fetch(request);
    const cache = await caches.open(CACHE);
    cache.put(request, res.clone());
    return res;
  } catch (err) {
    const cached = await caches.match(request);
    return cached || caches.match("/offline.html");
  }
}

async function staleWhileRevalidate(request) {
  const cached = await caches.match(request);
  const network = fetch(request).then(async (res) => {
    const cache = await caches.open(CACHE);
    cache.put(request, res.clone());
    return res;
  });
  return cached || network;
}

4. Offline Fallbacks and Background Sync

A cache without a fallback plan still shows a blank screen when both network and cache miss. Ship an offline.html page and serve it for failed navigations, return a placeholder SVG for failed images, and return empty-but-valid JSON for failed API calls so your UI can render its empty states instead of crashing.

Background Sync solves the harder problem: mutations made while offline. When the user submits a form with no connection, store the payload in IndexedDB and register a sync event. The browser retries the sync when connectivity returns — even if the tab was closed — and your worker replays the queued requests in order.

Design your sync queue to be idempotent: give each queued mutation a client-generated ID so a retried request cannot create duplicates server-side. On supporting browsers, Periodic Background Sync can also refresh content silently on a schedule, which is perfect for news or dashboard apps that should feel fresh on every open.

// Queue a mutation while offline, replay on sync
async function queueMutation(payload) {
  const db = await openQueueDb();
  await db.add("outbox", { id: crypto.randomUUID(), payload, ts: Date.now() });
  const reg = await navigator.serviceWorker.ready;
  await reg.sync.register("replay-outbox");
}

// Inside the service worker:
self.addEventListener("sync", (event) => {
  if (event.tag === "replay-outbox") {
    event.waitUntil(replayOutbox());
  }
});

async function replayOutbox() {
  const db = await openQueueDb();
  const items = await db.getAll("outbox");
  for (const item of items) {
    await fetch("/api/mutations", {
      method: "POST",
      headers: { "Content-Type": "application/json", "X-Idempotency-Key": item.id },
      body: JSON.stringify(item.payload)
    });
    await db.delete("outbox", item.id);
  }
}

5. Debugging, Pitfalls, and Production Checklist

Browser DevTools is your service worker laboratory: the Application panel shows registrations, lets you update, unregister, and simulate offline mode, and exposes Cache Storage contents for inspection. During development, enable Update on reload so every refresh installs the latest worker, and keep the console filter on the worker's context to see its logs separately from the page.

The classic production pitfalls are all avoidable. Scope mistakes happen when the worker file lives in a subdirectory but needs to control the whole site — keep it at the root. Opaque responses from cross-origin no-cors requests consume quota without being readable, so cache them deliberately or not at all. And storage quota is shared per origin: always wrap cache writes so a QuotaExceededError degrades gracefully instead of breaking the worker.

Before you ship, run the checklist: versioned precache list, old-cache cleanup in activate, update prompt UX, offline fallback page, idempotent background sync, short cache TTL on the worker script itself, and a kill-switch plan — a no-op worker you can deploy instantly if a bad version ever ships to production.

// Defensive cache write: never let quota errors break the worker
async function safeCachePut(request, response) {
  try {
    const cache = await caches.open(CACHE);
    await cache.put(request, response);
  } catch (err) {
    if (err.name === "QuotaExceededError") {
      // Evict the oldest runtime entries and retry once
      const cache = await caches.open(CACHE);
      const keys = await cache.keys();
      await Promise.all(keys.slice(0, 10).map((k) => cache.delete(k)));
      try { await cache.put(request, response); } catch (_) { /* give up gracefully */ }
    }
  }
}

// Check how much storage your origin is using
if (navigator.storage && navigator.storage.estimate) {
  const { usage, quota } = await navigator.storage.estimate();
  console.log(`Using ${(usage / 1048576).toFixed(1)} MB of ${(quota / 1048576).toFixed(0)} MB`);
}

6. Frequently Asked Questions (FAQs)

Do service workers work on iOS Safari?

Yes. Safari has supported service workers since iOS 11.3, so caching and offline pages work on iPhones. Historically, background sync and push notifications were limited or unavailable on iOS, so verify current platform support before depending on those features.

Why is my service worker update not taking effect?

Three usual causes: the browser only installs a new version when the script bytes differ, the new worker waits in the waiting state until all controlled tabs close unless you call skipWaiting, or the worker script itself is being cached by HTTP headers so the browser never sees the new bytes.

Can a service worker access the DOM?

No. Service workers run on a separate thread with no DOM or localStorage access. They communicate with pages via postMessage and persist data with the Cache API and IndexedDB, which are both available in the worker context.

How much can a service worker cache?

Cache Storage shares the origin storage quota, which is typically hundreds of megabytes to several gigabytes depending on the browser and disk space. Prioritize the app shell and critical assets, and handle QuotaExceededError gracefully.

Do I need HTTPS for service workers?

Yes, service workers require a secure context. The only exception is localhost, which browsers treat as secure for development. This requirement exists because a worker can intercept all of an origin's network traffic.

Keep leveling up

Service workers reward careful versioning and thorough testing. Nail the lifecycle once and every PWA you build afterwards gets offline support almost for free.
