1. Lexical Scope and the Scope Chain

Scope answers one question: where in the code can this variable be seen? JavaScript uses lexical scope, meaning the answer is decided by where the code is written — not where it runs. A function can read variables from its own body, from the function that contains it, and all the way out to the global scope; it can never see into the bodies of functions defined beside or inside it. This nesting of visible scopes is the scope chain.

When you reference a variable, the engine walks the chain outward from the current function until it finds the name. That lookup happens at the position where the function was defined, which is why moving a function to a different file or nesting level can change what it sees — a frequent source of confusion when refactoring. Shadowing (declaring the same name in an inner scope) is legal but usually a readability bug waiting to happen; linters flag it for a reason.

Block scope (let/const inside {}) and function scope are the two flavors that matter day to day. The practical upshot: keep variables as local as possible, declare them where they are used, and prefer parameters over reaching into outer scopes — explicit inputs make functions testable and their dependencies visible.

const appName = 'ShopApp'; // global scope

function createOrder() {
  const orderId = 101;            // function scope
  if (orderId > 100) {
    const label = 'priority';     // block scope: only inside this if
    console.log(appName, orderId, label); // all visible here
  }
  // console.log(label); // ReferenceError: label is block-scoped
  return function getSummary() {
    // inner function sees outward: appName + orderId, but NOT label
    return `${appName} order #${orderId}`;
  };
}

const summary = createOrder();
console.log(summary()); // 'ShopApp order #101'

2. What a Closure Actually Is

A closure is a function bundled together with the variables from its surrounding scope at the time it was created. Every function in JavaScript is technically a closure — but the term matters when the function outlives its outer scope: returned from a function, passed as a callback, stored for later. The outer function's local variables would normally be garbage-collected when it returns; the closure keeps alive exactly the ones the inner function references.

The canonical example is the counter: an outer function declares let count = 0 and returns an inner function that increments and returns it. Each call to the outer function creates a fresh count variable and a fresh closure over it, so two counters are fully independent. No objects, no classes, no this — just a function remembering its birthplace.

This “memory” is also why closures are the mechanism behind callbacks that reference loop variables, event handlers that remember configuration, and module patterns that hide private state. Once you see the pattern — inner function + captured variables + outliving the outer call — you will spot closures everywhere in real codebases.

function makeCounter(start = 0) {
  let count = start; // private: only the closure can touch it
  return {
    next()  { return ++count; },
    reset() { count = start; },
    value() { return count; },
  };
}

const a = makeCounter();
const b = makeCounter(100);
a.next(); a.next();
console.log(a.value(), b.value()); // 2 100  <- independent state
// There is NO way to reach `count` except through these methods.
// That privacy — without classes — is the closure at work.

3. Practical Closures: Private State and Factories

Before private class fields existed, closures were JavaScript's only true privacy mechanism — and they remain the simplest. A factory function returns an object of methods sharing hidden variables: rate limiters, caches, id generators, and configuration-bound handlers all fit this shape. The state cannot be tampered with from outside because it is not a property on anything; it exists only in the closure.

Function factories are the second everyday use: a function that builds specialized functions. makeMultiplier(3) returns x => x * 3; withAuth(token) returns a fetch wrapper with the token baked in; createLogger('DB') returns a logger that prefixes every message. Each produced function carries its configuration in its closure, so call sites stay clean while behavior stays customizable.

Memoization shows the performance angle: wrap an expensive pure function so the closure holds a Map of past arguments to results. Repeated calls with the same inputs skip the computation entirely. Libraries do this internally, but writing it once yourself cements how closures store state across calls.

// Factory: bake configuration into specialized functions
function withAuth(token) {
  return async function authedFetch(url, options = {}) {
    const res = await fetch(url, {
      ...options,
      headers: { ...options.headers, Authorization: `Bearer ${token}` },
    });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
  };
}

const api = withAuth('secret-token-123');
const me = await api('https://api.example.com/me'); // token attached

// Memoize: closure holds the cache between calls
function memoize(fn) {
  const cache = new Map();
  return function (...args) {
    const key = JSON.stringify(args);
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key);
  };
}
const fastFib = memoize(n => (n < 2 ? n : fastFib(n - 1) + fastFib(n - 2)));

4. The Classic Loop Gotcha and Memory Notes

The most famous closure bug: var i in a for loop with setTimeout callbacks. Because var is function-scoped, all iterations share one i, and by the time the timers run the loop has finished — every callback logs the final value. The ES6 fix is let, which creates a fresh binding per iteration so each closure captures the value you expect. The pre-ES6 fix was an IIFE (immediately invoked function expression) creating a new scope per pass — worth recognizing in legacy code.

Do closures cause memory leaks? Only when they capture more than they need and live too long. A closure keeps its entire scope chain alive, so a long-lived handler that closes over a huge object retains that object even if it uses one property. The fix is boring: capture narrowly (destructure what you need into locals), and removeEventListener / clear timers when components unmount.

In practice, leaks from closures are rare in modern code — the infamous ones came from old IE's DOM/JS circular references, long extinct. Write natural code, clean up long-lived listeners in single-page apps, and profile with the browser's memory tools if you suspect a problem rather than contorting your code preemptively.

// THE classic bug: var shares one binding across iterations
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var i =', i), 0); // 3, 3, 3
}

// Fix 1 (modern): let gives each iteration its own binding
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log('let j =', j), 0); // 0, 1, 2
}

// Fix 2 (legacy pattern you'll see in old code): IIFE per iteration
for (var k = 0; k < 3; k++) {
  (function (n) {
    setTimeout(() => console.log('iife n =', n), 0); // 0, 1, 2
  })(k);
}

6. Frequently Asked Questions (FAQs)

What is a closure in simple terms?

A function that remembers the variables from where it was created, even after that surrounding code has finished running. If an inner function uses a variable from its outer function and the inner function outlives the outer call (returned, passed as callback), you have a closure.

Do closures cause memory leaks?

Rarely in modern code. A closure keeps the variables it references alive, which is usually exactly what you want. Leaks happen only when a long-lived closure (e.g. a never-removed event listener) captures large objects it barely uses — capture narrowly and clean up listeners to avoid it.

Why does var in a loop break setTimeout?

Because var is function-scoped: all iterations share a single i, and by the time the timers execute, the loop has finished and i holds its final value. Using let gives each iteration its own binding, so every callback captures the value from its own pass.

Can I create private variables without classes?

Yes — declare them as locals in a factory function and return only methods that use them. Nothing outside can reach those variables because they are not properties on any object; they exist solely inside the closure. This was JavaScript's original privacy pattern.

Are closures the same as callbacks?

No, though they overlap. A callback is any function passed to run later; a closure is a function plus its captured surrounding variables. Many callbacks happen to be closures (they reference outer variables), but a callback using only its parameters closes over nothing.
