1. From Pages to App: The New Mental Model

The App Router (in the app/ directory) replaced the Pages Router's simple "file = route" model with something more powerful: every component is a server component by default, routes are defined by folders, and special files (page.js, layout.js, loading.js, error.js) declare UI states conventionally. The mental shift is from "fetch in the browser, then render" to "render on the server with data already in hand."

Why it matters: server components send zero JavaScript for themselves to the browser, fetch data with direct backend access (no API round-trip from the client), and keep secrets server-side. The result is smaller bundles, faster first paints, and SEO-friendly HTML without giving up interactivity — you add 'use client' precisely where interactivity lives.

If you're coming from the Pages Router, map the concepts: getServerSideProps becomes an async server component, getStaticProps becomes fetch with caching options, and _app.js becomes the root layout.js. The two routers can coexist during migration, but new projects should start on the App Router — it's where all framework investment goes.

2. Server vs Client Components

The single most important App Router concept: server components run on the server (no useState, no event handlers, no browser APIs), while client components (marked with 'use client') hydrate in the browser and get all the interactivity. The art is pushing client boundaries as deep as possible — a page can be a server component that renders one small interactive widget:

// app/products/page.js — SERVER component (default, no directive)
import AddToCart from './AddToCart'; // client component, used below

async function getProducts() {
  // Runs on the server: direct DB/API access, secrets stay secret
  const res = await fetch('https://api.example.com/products', {
    next: { revalidate: 60 }, // cache 60s, then regenerate (ISR)
  });
  return res.json();
}

export default async function ProductsPage() {
  const products = await getProducts(); // await directly in the component!
  return (
    <main>
      <h1>Products</h1>
      {products.map((p) => (
        <article key={p.id}>
          <h2>{p.name}</h2>
          {/* Only this button ships JavaScript */}
          <AddToCart productId={p.id} />
        </article>
      ))}
    </main>
  );
}
// app/products/AddToCart.js — CLIENT component (interactive island)
'use client';

import { useState } from 'react';

export default function AddToCart({ productId }) {
  const [added, setAdded] = useState(false);
  return (
    <button onClick={() => { api.cart.add(productId); setAdded(true); }}
            disabled={added}>
      {added ? 'Added ✓' : 'Add to cart'}
    </button>
  );
}

Data flows one way across the boundary: server components can pass props (including serializable data) down to client components, but a client component can never import a server component — doing so would drag server code into the browser bundle. Composition inverts instead: the server component renders the client component and passes other server components to it as children.

3. File-Based Routing: Layouts, Pages, and Loading States

In the App Router, folders define routes and special files define UI: page.js is the route's content, layout.js wraps it (and persists across navigation), loading.js shows during loads, and error.js catches failures. Dynamic segments use brackets — app/blog/[slug]/page.js:

// app/dashboard/layout.js — persists while children navigate
export default function DashboardLayout({ children }) {
  return (
    <div className="dashboard">
      <Sidebar />      {/* mounted once, never refetched on tab switches */}
      <section>{children}</section>
    </div>
  );
}

// app/dashboard/reports/loading.js — instant skeleton UI
export default function Loading() {
  return <div className="skeleton-list">Loading reports…</div>;
}

// app/blog/[slug]/page.js — dynamic route with metadata
export async function generateMetadata({ params }) {
  const post = await getPost(params.slug);
  return { title: post.title, description: post.excerpt };
}

export default async function PostPage({ params, searchParams }) {
  const post = await getPost(params.slug); // params from the URL
  return <article><h1>{post.title}</h1>{post.body}</article>;
}

Layouts preserve state — navigating between /dashboard/reports and /dashboard/settings keeps the layout mounted, unlike the old pattern of re-rendering shared UI per page. Loading states stream: wrap slow parts in <Suspense> and Next.js sends the fast HTML first, streaming the rest in — the loading.js convention is just Suspense with file-based ergonomics.

Route groups ((marketing)) organize files without affecting URLs, and page.js files are required for a route to be publicly accessible — folders with only a layout don't create pages. Colocate route-specific components next to their pages (private folders prefixed with _ are excluded from routing) so each route's code lives with its URL.

4. Data Fetching, Caching, and Server Actions

Server components fetch with the extended fetch API, where caching is declarative: cache: 'force-cache' (default — static), next: { revalidate: N } (ISR — refresh every N seconds), or cache: 'no-store' (always dynamic). Identical requests are automatically deduped within a render, so multiple components can each fetch what they need without waterfalling:

// Static (cached until redeploy), revalidated, and dynamic patterns
const static_ = await fetch('https://api.example.com/docs'); // force-cache default
const fresh = await fetch('https://api.example.com/prices',
  { next: { revalidate: 30 } });            // ISR: at most 30s stale
const live = await fetch('https://api.example.com/session',
  { cache: 'no-store' });                   // dynamic: never cached

// Server Action: mutate data without an API route ('use server')
async function subscribe(formData) {
  'use server';
  const email = formData.get('email');
  if (typeof email !== 'string' || !email.includes('@')) {
    return { error: 'Enter a valid email address.' };
  }
  await db.subscribers.create({ email }); // direct DB access, secrets safe
  revalidatePath('/newsletter');          // refresh cached pages showing this
}

// Used directly as a form action — progressive enhancement included
export default function NewsletterForm() {
  return (
    <form action={subscribe}>
      <input type="email" name="email" required />
      <button type="submit">Subscribe</button>
    </form>
  );
}

Server Actions replace API routes for mutations: async functions marked 'use server'` that forms and event handlers call directly, with direct database access and no client bundle cost. They work with plain HTML forms too (progressive enhancement), and revalidatePath/revalidateTag refresh affected caches after writes.

Choose your rendering per route, not per app: static for marketing pages, ISR for catalogs and blogs, dynamic for personalized dashboards. The App Router's granularity — down to individual fetch calls — means one page can mix cached product data with a live cart without compromise.

5. Common Gotchas and Migration Tips

"You're importing a component that needs useState" — you used a hook or event handler in a server component. Add 'use client' at the top of the file containing the interactivity, and push that boundary as deep as the component tree allows. Event handlers silently not working is the same root cause: server components never hydrate, so onClick there does nothing.

Stale data after mutations: cached fetches don't know your database changed — call revalidatePath or revalidateTag in the server action that performed the write. Client components can't be async and can't await data; fetch in the parent server component and pass data down as props. Third-party libraries that touch window during import must live behind 'use client' — or dynamic import with ssr: false for browser-only widgets like maps.

Migration strategy: run both routers side by side (App Router takes precedence on conflicting paths), migrate leaf routes first, and keep shared UI in the root layout last. Move data fetching out of useEffect into server components as you go — that's where the biggest performance wins hide. And test the production build early: caching behavior only fully manifests in next build, not in dev mode where everything is dynamic.

6. Frequently Asked Questions (FAQs)

When do I need 'use client' in Next.js?

Add 'use client' to any file using hooks (useState, useEffect), event handlers, or browser APIs. Everything else should stay a server component: they ship zero JavaScript, fetch data directly, and keep secrets server-side. Push the client boundary as deep as possible — often just the interactive widget, not the whole page.

Can server components use hooks like useState?

No. Server components run once on the server and never hydrate, so hooks, event handlers, and browser APIs are unavailable. Fetch data with async/await directly in the component instead, and delegate interactivity to a 'use client' child component.

How does caching work with fetch in the App Router?

Extended fetch options control it: the default caches statically until redeploy, next: { revalidate: N } enables Incremental Static Regeneration refreshing every N seconds, and cache: 'no-store' forces dynamic rendering. Identical requests within a render are automatically deduped.

What are server actions?

Async functions marked 'use server' that mutate data directly — database writes, form processing — without an API route. They run on the server with secret access, can be used as form actions with progressive enhancement, and pair with revalidatePath to refresh cached pages after writes.

Should I migrate from the Pages Router to the App Router?

For new projects, start with the App Router — it receives all framework investment. For existing apps, migrate incrementally: both routers coexist, so move leaf routes first and shared layouts last. The biggest wins come from replacing useEffect data fetching with server components.
