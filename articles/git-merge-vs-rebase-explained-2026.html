1. What Merge and Rebase Actually Do

Both git merge and git rebase solve the same problem: combining work from two branches. They differ in how the combined history looks afterward. Merge preserves history exactly as it happened; rebase rewrites it into a cleaner story.

Imagine main moved forward while you worked on feature:

main:     A --- B --- C
                   \
feature:            D --- E

A merge creates a new commit F with two parents, tying the timelines together: A-B-C-F with D-E feeding into F. The history is honest — it shows exactly when branches diverged and reunited. A rebase instead lifts D and E off and replays them on top of C, producing a straight line: A-B-C-D'-E'. Same final code, completely different story.

Neither is universally better. The right choice depends on whether the branch is private or shared, and whether you value historical accuracy or readability.

Developers argue about this endlessly, but the debate usually dissolves once you learn the one rule that governs everything: rewrite history freely on branches only you use, and preserve history faithfully everywhere else. The rest of this guide shows you exactly how.

2. Git Merge: Keeping a Faithful History

Merging is the default, safest way to combine branches. When you run git merge feature from main, Git performs a three-way merge using the two branch tips and their common ancestor, then records a merge commit — unless the merge can fast-forward.

# Merge a feature branch into main
git checkout main
git pull origin main
git merge feature-login

# Force a merge commit even when fast-forward is possible
git merge --no-ff feature-login

A fast-forward happens when main has not moved since you branched: Git simply slides the pointer forward, and no merge commit is created. Teams that want every merge visible pass --no-ff, which always creates a merge commit — useful when you want the history to show exactly which commits shipped as one feature.

If both branches touched the same lines, Git pauses and marks conflicts. Open the files, resolve the markers, git add them, and git commit to finish. Merge conflicts are normal; they are Git asking a human to decide what the code should look like.

3. Git Rebase: A Clean, Linear History

Rebasing replays your commits on top of the latest main, as if you had started your feature five minutes ago. The history becomes a single straight line — no merge commits, no diamond shapes.

# Rebase your feature onto the latest main
git checkout feature-login
git fetch origin
git rebase origin/main

# If conflicts appear: fix files, then
git add .
git rebase --continue
# To bail out and return to the pre-rebase state
git rebase --abort

During a rebase, Git stops at each conflicting commit so you can resolve it in small steps. This is actually easier to reason about than one giant merge conflict, because you fix problems commit by commit.

The trade-off: rebase rewrites commit hashes. Your commits D and E become new commits D' and E'. That is harmless on a private branch — but catastrophic if someone else has already pulled the old commits, because their history and yours now disagree.

4. Interactive Rebase: Squash, Reword, and Polish

git rebase -i (interactive) opens an editor listing your commits, letting you rewrite history before sharing it. This is how experienced developers turn a messy work-in-progress into a clean, reviewable series of commits.

# Rewrite the last 4 commits interactively
git rebase -i HEAD~4

# In the editor, change 'pick' to:
#   reword  - edit a commit message
#   squash  - fold commit into the previous one
#   fixup   - fold in, discarding its message
#   drop    - delete the commit entirely

A common workflow: commit freely while experimenting (“wip”, “fix typo”, “actually fix it”), then squash the noise into one or two meaningful commits before opening a pull request. Reviewers see a logical story instead of your debugging diary.

Interactive rebase is also how you split an accidental mega-commit or reorder commits. Just remember: this is history rewriting, so it belongs on your private branch only, before the pull request is merged.

5. The Golden Rule: When to Merge and When to Rebase

The golden rule of rebasing: never rebase commits that exist outside your own local repository. If you pushed a branch and a teammate pulled it, rebasing rewrites the history they already have, and recovery is painful for everyone.

git mergegit rebase
HistoryPreserved as it happenedRewritten as a straight line
Merge commitsYes (unless fast-forward)None
Safe on shared branchesYesNo — never rebase public history
ConflictsResolved once, in one commitResolved per commit
Best formain, shared branchesPrivate feature branches

The practical workflow most teams settle on: rebase your private feature branch onto the latest main to keep it fresh and resolve conflicts early, then merge (or squash-merge) the pull request into main. You get a clean, conflict-free PR and an honest record of what shipped.

If you only remember one thing: rebase to clean up your own work, merge to combine shared work.

6. Frequently Asked Questions (FAQs)

Is git rebase dangerous?

Rebase is safe on branches only you use. It becomes dangerous when applied to shared branches like main, because rewriting published history forces everyone else to recover from divergent timelines. Follow the golden rule and you will be fine.

What happens if I rebase a branch my teammate already pulled?

Your teammate's copy still references the old commits while your branch has rewritten ones, so Git sees two divergent histories. They will face confusing conflicts on their next pull. Fix it by communicating: have them reset to the new branch state with git fetch followed by git reset --hard origin/branch-name.

Should I merge or rebase when updating my pull request?

Rebase. Running git pull --rebase or git rebase origin/main keeps your PR history linear and surfaces conflicts early, making the final merge trivial. GitHub's Update branch button does a merge by default, which is also fine if you prefer merge commits.

How do I undo a rebase that went wrong?

Use the reflog, which records every move your branch pointer made. Run git reflog to find the commit hash from before the rebase, then git reset --hard to that hash. As long as you have not garbage-collected, your pre-rebase state is recoverable.

What is the difference between rebase and squash merge?

Rebase replays each of your commits onto the target branch, preserving them as separate commits. Squash merge compresses the entire branch into a single commit on the target. Squash gives the cleanest main history but erases the individual steps; rebase keeps the steps but rewrites their hashes.
