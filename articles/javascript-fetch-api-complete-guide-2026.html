1. Making Your First GET Request

fetch() is the modern way to make HTTP requests: pass it a URL and it returns a promise that resolves to a Response object. That response is just metadata plus a readable body stream — you then call .json(), .text(), .blob(), or .formData() to actually consume the body, each returning its own promise. The two-step shape (response, then body) surprises newcomers, but it lets you inspect status and headers before committing to parsing.

The single most misunderstood fetch behavior: it only rejects on network failures — DNS errors, refused connections, CORS blocks. An HTTP 404 or 500 still resolves successfully, because from fetch's perspective the server answered. You must check response.ok (true for 200–299) or the status code yourself and throw when the application considers it an error. Every production fetch wrapper starts with this check.

Because fetch is promise-based, it composes naturally with async/await: const data = await (await fetch(url)).json(). Extract that into a small helper early — getJSON(url) with the ok-check baked in — and every call site in your app becomes one clean line instead of five lines of ceremony.

// Minimal GET with proper error checking
async function getJSON(url) {
  const res = await fetch(url);
  if (!res.ok) {
    throw new Error(`Request failed: ${res.status} ${res.statusText}`);
  }
  return res.json(); // parses body as JSON
}

// Usage: one clean line per call
try {
  const user = await getJSON('https://api.example.com/users/7');
  console.log(user.name);
} catch (err) {
  console.error('Could not load user:', err.message);
}

2. POST Requests: Sending JSON and Form Data

POST (and PUT, PATCH, DELETE) requests pass a second argument to fetch: an init object with method, headers, and body. For JSON APIs the recipe is fixed — method: 'POST', a Content-Type: application/json header, and body: JSON.stringify(payload). The header matters: without it, many servers will not parse the body as JSON at all.

For file uploads and traditional forms, use FormData instead. Construct it with new FormData(formElement) to capture a whole form, or append fields manually — including File objects from <input type="file">. Crucially, do NOT set Content-Type yourself for FormData: the browser generates a multipart boundary automatically, and a hand-set header will break the upload.

Idempotency is worth internalizing: GET, PUT, and DELETE should be safe to retry; POST generally is not (it may create duplicates). Design your client retries accordingly — retry a failed GET freely, but only retry POSTs when the API documents idempotency keys or you can tolerate duplicates.

// POST JSON: the standard API recipe
async function postJSON(url, payload) {
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload),
  });
  if (!res.ok) throw new Error(`POST failed: ${res.status}`);
  return res.json();
}

await postJSON('https://api.example.com/users', {
  name: 'Ayesha',
  email: 'ayesha@example.com',
});

// File upload with FormData (browser sets Content-Type itself)
async function uploadAvatar(file) {
  const form = new FormData();
  form.append('avatar', file, file.name);
  const res = await fetch('/api/avatar', { method: 'POST', body: form });
  if (!res.ok) throw new Error('Upload failed');
  return res.json();
}

3. Headers, Authentication, and CORS

Headers ride along in the init object and cover authentication, content negotiation, and caching. The dominant auth pattern is the Bearer token: headers: { Authorization: 'Bearer ' + token }. Tokens usually come from a login response and live in memory or secure storage — never hardcode them in client-side code that ships to browsers, where anyone can read them.

The Accept header tells the server what response format you want (Accept: application/json), while Content-Type describes what you are sending — confusing the two is a classic bug. Custom headers like X-Request-Id are fine, but know that non-simple headers trigger a CORS preflight (an automatic OPTIONS request), so the server must explicitly allow them.

CORS errors — the infamous “blocked by CORS policy” — are server-side configuration issues, not fetch bugs: the browser is protecting the user by requiring the server's opt-in (Access-Control-Allow-Origin) before exposing a cross-origin response to your script. During development, proxy the API through your dev server rather than disabling browser security. For cookies and HTTP auth on cross-origin requests, set credentials: 'include' — fetch omits credentials by default.

// Authenticated request with custom headers
const token = sessionStorage.getItem('api_token');

const res = await fetch('https://api.example.com/me', {
  headers: {
    'Authorization': `Bearer ${token}`,
    'Accept': 'application/json',
    'X-Request-Id': crypto.randomUUID(),
  },
  credentials: 'include', // send cookies on cross-origin requests
});

// Reading response headers (e.g. pagination, rate limits)
const totalPages = res.headers.get('X-Total-Pages');
const remaining  = res.headers.get('X-RateLimit-Remaining');
console.log(`Page 1 of ${totalPages} \u2014 ${remaining} requests left`);

4. Bulletproof Error Handling and Timeouts

A production-grade fetch wrapper handles four failure modes: network errors (fetch rejects), HTTP errors (check response.ok), malformed bodies (res.json() throws on invalid JSON), and hangs (no response ever arrives). The first three are handled with try/catch plus the ok-check; hangs need AbortController, because fetch has no built-in timeout.

AbortController pairs a signal with the request: pass signal into fetch, then call controller.abort() from a setTimeout to cancel. Aborting rejects the fetch promise with an AbortError (name === 'AbortError'), which you detect and translate into a friendly “request timed out” message. Always clearTimeout in a finally block so successful requests do not leak timers.

Add retries only where they are safe: retry idempotent GETs with exponential backoff (1s, 2s, 4s), never blindly retry POSTs. And surface failures honestly in the UI — a skeleton that never resolves is worse than an error message with a retry button. The wrapper below bundles all of this into one reusable function.

// fetch with timeout + retries for idempotent requests
async function fetchJSON(url, { timeout = 8000, retries = 2 } = {}) {
  for (let attempt = 0; attempt <= retries; attempt++) {
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), timeout);
    try {
      const res = await fetch(url, { signal: controller.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return await res.json();
    } catch (err) {
      const isTimeout = err.name === 'AbortError';
      const lastAttempt = attempt === retries;
      if (lastAttempt) {
        throw new Error(isTimeout ? `Timed out after ${timeout}ms: ${url}`
                                  : `Failed: ${err.message}`);
      }
      await new Promise(r => setTimeout(r, 1000 * 2 ** attempt)); // backoff
    } finally {
      clearTimeout(timer);
    }
  }
}

5. Fetch Options Quick Reference

The init object is fetch's entire configuration surface. Most requests need only method, headers, and body — but knowing the rest lets you handle caching, redirects, credentials, and cancellation correctly instead of cargo-culting snippets. The table below summarizes every option with its common values and the exact situation that calls for each one.

Two options deserve special attention. cache controls the HTTP cache interaction ('no-store' for always-fresh data like stock prices, 'force-cache' for immutable assets). redirect: 'manual' versus 'follow' matters when you need to inspect redirect responses yourself, such as OAuth flows.

Keep this table as a reference card. Combined with the timeout wrapper above and the ok-check discipline from section one, you now have everything needed for reliable browser-to-API communication — no library required.

6. Frequently Asked Questions (FAQs)

Why doesn't fetch throw an error on 404 or 500 responses?

By design, fetch only rejects on network-level failures (DNS, connection refused, CORS blocks). HTTP error statuses still resolve because the server responded. Always check response.ok or the status code yourself and throw when your application treats it as an error.

How do I add a timeout to a fetch request?

Use AbortController: create a controller, pass its signal into fetch, and call controller.abort() from a setTimeout. The fetch rejects with an AbortError, which you catch and convert into a timeout message. Remember to clearTimeout in a finally block.

How do I send cookies with fetch?

Set credentials: 'include' in the init object for cross-origin requests (same-origin requests send cookies by default with 'same-origin'). The server must also respond with Access-Control-Allow-Credentials: true, and its Allow-Origin header cannot be a wildcard when credentials are involved.

Should I use fetch or Axios in 2026?

For most projects, native fetch is enough — it is promise-based, universally supported, and needs no dependency. Axios still earns its place when you want automatic JSON transforms, request/response interceptors, or built-in timeout and upload-progress handling without writing wrappers yourself.

How do I cancel an in-flight fetch request?

Keep the AbortController you passed in via signal and call controller.abort() — from a cancel button, a component unmount, or a newer request superseding the old one (e.g. typeahead). The promise rejects with an AbortError you can safely ignore or handle.
