1. Promises: The Foundation

A Promise is JavaScript's standard container for a value that does not exist yet: the result of a network request, a file read, a timer. Every promise lives in one of three states — pending, fulfilled, or rejected — and moves from pending to exactly one settled state, once. That single-settlement guarantee is what makes promises trustworthy: unlike raw callbacks, a promise cannot resolve twice or silently swallow its outcome.

You consume promises with .then() for the success value and .catch() for failures, and each .then() returns a new promise — which is what enables chaining. A value returned from one .then() becomes the input of the next, so a multi-step pipeline (fetch user → fetch their orders → render) reads as a vertical chain instead of nested callbacks. The chain also centralizes errors: a single .catch() at the end handles a rejection from any step.

You will also create promises, most often to wrap older callback APIs. The Promise constructor takes an executor function with resolve and reject callbacks — call resolve(value) on success, reject(error) on failure. Wrap setTimeout-based utilities, geolocation, or IndexedDB calls this way and they compose cleanly with the rest of your async code.

// Creating a promise: wrap a callback API
function delay(ms, value) {
  return new Promise((resolve, reject) => {
    if (ms < 0) return reject(new Error('ms must be positive'));
    setTimeout(() => resolve(value), ms);
  });
}

// Chaining: each .then() feeds the next
delay(300, 21)
  .then(n => n * 2)          // 42
  .then(n => `Answer: ${n}`) // 'Answer: 42'
  .then(console.log)
  .catch(err => console.error('Failed:', err.message));
// One .catch() handles a rejection from ANY step above

2. async/await: Writing Async Code That Reads Sync

async/await is syntax sugar over promises that removes the chaining ceremony. Mark a function async and it always returns a promise; inside it, await pauses execution until a promise settles, then unwraps its value. Code that needed three nested .then() calls becomes three sequential-looking lines — same behavior, dramatically easier to read, debug, and step through.

The mental model that prevents most mistakes: await only pauses the current async function, never the whole program. While one function waits on a network response, the event loop keeps running timers, handling clicks, and painting frames. And because async functions return promises, they compose with everything else — you can await an async function, .then() it, or feed it to Promise.all without any adapter code.

Use await for sequential dependencies (you need the user before you can fetch their orders) and reach for the parallel combinators in the next sections when steps are independent. A common performance bug is awaiting independent requests one after another — three 200ms requests become 600ms instead of ~200ms. Start all the promises first, then await them together.

// The same pipeline, written with async/await
async function getOrderSummary(userId) {
  const user = await fetch(`/api/users/${userId}`).then(r => r.json());
  // ^ sequential: we need the user first
  const orders = await fetch(`/api/users/${user.id}/orders`).then(r => r.json());
  return { name: user.name, total: orders.length };
}

// Independent requests: start together, await together
async function getDashboard() {
  const usersP = fetch('/api/users').then(r => r.json());
  const statsP = fetch('/api/stats').then(r => r.json());
  const [users, stats] = await Promise.all([usersP, statsP]);
  return { users, stats }; // ~1x slowest, not the sum
}

3. Error Handling Done Right

With async/await, error handling looks like synchronous code: wrap awaits in try/catch. A rejected promise inside the try block jumps straight to catch, where you get a normal Error object with a stack trace pointing at the failing await — far more debuggable than a rejection surfacing three .then() calls away from its cause.

Structure your catches deliberately. Catch around the narrowest unit you can meaningfully recover from: per-request handling lets one failed fetch fall back to cached data while the rest of the flow continues, while a single outer catch is right for “if anything fails, show the error screen” flows. Always rethrow (or return a rejected promise) when you cannot actually recover — silently swallowing errors is how “blank page, no error” bugs are born.

Unhandled rejections are the async equivalent of uncaught exceptions: in modern runtimes they log loud warnings and in Node.js they crash the process. Every promise chain needs a terminal .catch(), and every top-level async call needs a try/catch or .catch(). A global safety net — window.addEventListener('unhandledrejection') — is worth adding in production apps so nothing fails silently.

async function loadProfile(userId) {
  try {
    const res = await fetch(`/api/users/${userId}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (err) {
    // Narrow recovery: fall back to cached data for network errors
    console.warn('Live fetch failed, using cache:', err.message);
    const cached = localStorage.getItem('profile:' + userId);
    if (cached) return JSON.parse(cached);
    throw err; // cannot recover -> let the caller handle it
  }
}

// Global safety net: never let a rejection die silently
window.addEventListener('unhandledrejection', (e) => {
  console.error('Unhandled rejection:', e.reason);
});

4. Running Things in Parallel: all, allSettled, race, any

Promise.all takes an array of promises and resolves with an array of their results in order — but it is all-or-nothing: the first rejection rejects the whole thing, discarding the other results. That is exactly right for “everything must succeed” flows like loading the pieces of a dashboard, and exactly wrong when partial results are acceptable.

Promise.allSettled never rejects. It waits for every promise to settle and reports each outcome as { status: 'fulfilled', value } or { status: 'rejected', reason }. It is the tool for batch jobs where one failure must not poison the rest — syncing ten feeds, validating a form's independent checks, or preloading assets where you want to know which ones failed.

Promise.race settles with the first promise to settle, win or lose — the classic use is racing a fetch against a timeout. Promise.any is its optimistic sibling: it resolves with the first fulfillment and only rejects if everything fails, which suits “first healthy mirror wins” patterns. Pick the combinator that matches your failure semantics and half your async bugs disappear.

// allSettled: batch job where partial failure is OK
const urls = ['/api/a', '/api/b', '/api/c'];
const results = await Promise.allSettled(urls.map(u => fetch(u).then(r => r.json())));
const good = results.filter(r => r.status === 'fulfilled').map(r => r.value);
const failed = results.filter(r => r.status === 'rejected');
console.log(`Loaded ${good.length}, failed ${failed.length}`);

// race: fetch with a timeout
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Timed out')), ms));
  return Promise.race([promise, timeout]);
}

const data = await withTimeout(fetch('/api/slow').then(r => r.json()), 5000);

5. Async Patterns and Pitfalls

The most common async/await bug is using it inside forEach: arr.forEach(async x => { await work(x); }) fires all the callbacks without waiting for any of them, because forEach ignores the promises your callback returns. When order or completion matters, use for...of with await inside — it genuinely waits per iteration — or map to an array of promises and await Promise.all for parallelism.

Sequential awaits in a loop are sometimes correct (rate-limited APIs, dependent steps) but often an accidental performance cliff: five 300ms requests become 1.5 seconds instead of ~300ms. Default to starting all promises first and awaiting them together; drop to sequential only when the steps truly depend on each other or the API demands it.

Finally, keep async boundaries thin. Marking everything async “just in case” litters code with pointless awaits and makes stack traces harder to read. Async functions should sit at I/O boundaries — fetching, timers, storage — while pure computation stays synchronous. The table below is a quick reference for the patterns in this guide.

6. Frequently Asked Questions (FAQs)

What is the difference between a promise and async/await?

A promise is the underlying object representing a future value; async/await is syntax for working with promises. An async function always returns a promise, and await unwraps a promise's value. They are the same machinery — async/await just reads like synchronous code.

How do I handle one failing request in Promise.all?

You cannot — Promise.all rejects entirely on the first failure. For partial-failure tolerance, use Promise.allSettled (which reports every outcome) or attach a .catch() to each individual promise before passing them to Promise.all so none of them reject.

Does await block the main thread?

No. await pauses only the current async function; the event loop keeps processing timers, events, and rendering while it waits. True blocking comes only from long synchronous computation, which await does nothing to fix.

Can I use await at the top level of a module?

Yes, in ES modules — top-level await is supported in all modern browsers and Node.js. In classic scripts you still need to wrap the code in an async function (or an async IIFE) because await is only valid inside async functions there.

What happens if I forget .catch() on a promise?

The rejection becomes “unhandled”: browsers log a loud console warning and Node.js may terminate the process. Add a global unhandledrejection listener as a safety net, but fix the root cause — every promise chain needs a terminal error handler.
