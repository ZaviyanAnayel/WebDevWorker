1. Declaring and Using Variables

Custom properties are declared with a -- prefix and consumed with var(): --brand: #eab308; then color: var(--brand). Unlike Sass variables, they are live — they cascade, inherit, and can change at runtime without recompilation.

Always provide fallbacks for resilience: var(--brand, #eab308) uses the fallback when the variable is undefined. This is essential for component libraries consumed in unpredictable contexts.

:root {
  --brand: #eab308;
  --brand-dark: #ca8a04;
  --text: #0f172a;
  --radius: 8px;
}
.btn {
  background: var(--brand);
  color: var(--text);
  border-radius: var(--radius, 6px); /* fallback */
}

2. Scoping and the Cascade

Custom properties follow normal cascade rules: a variable declared on .card is visible to the card and its descendants, but not to siblings. This makes them perfect for component-scoped theming — override a handful of variables per variant instead of rewriting entire rule sets.

Declare global tokens on :root (which is the <html> element), component tokens on the component selector, and state overrides on modifiers. This three-layer structure scales from side projects to design systems.

3. Theming: Dark Mode and Beyond

Theming is the killer app. Define semantic tokens (--bg, --text, --border) once, then redefine their values under [data-theme="dark"] or @media (prefers-color-scheme: dark). Every component updates instantly with zero additional CSS.

This beats class-per-component theming by an order of magnitude: one variable block per theme, and components stay theme-agnostic. Brand theming (white-label products) works the same way — swap the token values, keep the components.

:root {
  --bg: #ffffff; --text: #0f172a; --border: #e2e8f0;
}
[data-theme="dark"] {
  --bg: #0f172a; --text: #f8fafc; --border: #334155;
}
body { background: var(--bg); color: var(--text); }

4. JavaScript Integration

JavaScript can read and write custom properties at runtime via getComputedStyle() and element.style.setProperty(). This enables theme toggles, dynamic spacing controls, and scroll-driven effects without touching stylesheets.

A classic pattern: store the user's theme choice in localStorage, set data-theme on <html> before first paint (to avoid flashing), and let CSS variables do the rest. The WebDevWorker template you are reading does exactly this.

5. Design Tokens Architecture

At scale, organize variables as design tokens: primitive tokens (raw values like --yellow-500), semantic tokens (--brand referencing primitives), and component tokens (--btn-bg referencing semantic). Changes flow downward; a rebrand touches primitives only.

Keep token names semantic, not presentational: --color-danger beats --color-red because danger stays meaningful if the hue changes. Document tokens alongside components — undocumented variables become tribal knowledge.

6. Frequently Asked Questions (FAQs)

What is the difference between CSS variables and Sass variables?

CSS custom properties are live in the browser: they cascade, inherit, and can change at runtime via JavaScript. Sass variables are compile-time only and vanish from the output CSS.

Can I use var() inside media queries?

No — custom properties cannot be used in media query conditions themselves, but they work everywhere inside the rules those queries contain.

Do CSS variables work in all browsers?

Yes, all modern browsers support them. For legacy IE support you would need fallbacks, but that is rarely a 2026 concern.

How do I provide a fallback value?

Use the second argument: var(--brand, #eab308). The fallback applies when the variable is undefined or invalid.

Should tokens live on :root?

Global tokens yes. But prefer the narrowest scope that works — component tokens on the component keep the global namespace clean.
